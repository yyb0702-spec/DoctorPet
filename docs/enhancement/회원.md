# 고도화 — 회원 (담당: @yyb0702-spec)

> 이 문서는 동결된 MVP 정본에 대한 **델타(변경분)**다. 아래 `전제` 절에 적힌 SA·PRD 절만 함께 읽으면 되고, 그 밖의 MVP 문서는 읽지 않는다.
> 충돌 시: 이 문서가 `override 범위`에 선언한 것 안에서는 이 문서 > 동결 SA. 범위 밖은 동결 SA가 정본. (레이어 규칙: [README](README.md))

## 메타

- **상태:** 초안
- **담당:** @yyb0702-spec
- **관련 이슈:** #
- **전제(동결 baseline — 이 절만 함께 읽는다):** SA §6(인증·인가), SA §6-3(탈퇴와 재가입), SA §6-4(이메일 인증·비밀번호 재설정), SA §6-5(SNS 로그인), SA §6-6(연락처), SA 부록 A(미확정 결정)·부록 A-1(토큰 소비 순서 상세 설계), PRD §3(사용자·요구사항)
- **override 범위(이 문서가 바꾸는 계약):** ① 미인증 계정 정리 정책·배치, ② SNS 로그인(OAuth2 프로바이더 추상화), ③ 이메일 인증·비밀번호 재설정 토큰 소비 순서(claim 패턴), ④ 탈퇴 시 Redis 부수효과 순서
- **건드리지 않는 것:** JWT 저장·회전(§6-1)·역할 인가(§6-2)는 유지. 기존 가입 흐름(이메일·휴대폰·비밀번호·닉네임 모두 필수 — PRD v3.23·SA §6-6, #122 반영) 유지. SA 부록 A의 `[결정 필요]`/미착수 항목은 확정 전 임의 구현하지 않는다(AGENTS).

SA 부록 A에 회원 도메인으로 남은 미확정 4개를 범위·근거와 함께 정리한다. (SA/PRD 버전은 각 정본 헤더가 단일 정본)

---

## 1. 미인증 계정 처리 정책 — 정책결정필요
**근거:** 가입 직후 `email_verified=false`로 생성되고 인증 전에는 로그인이 403 차단된다. 인증 링크를 끝까지 클릭하지 않는 계정은 로그인도 삭제도 안 된 채 DB에 영구 잔존한다. 인증 토큰은 Redis 24h TTL로 소멸하지만 `members` 행은 그대로다.
**범위(택1):**
- **무기한 방치:** 구현 0. 단 미인증 계정이 이메일 UNIQUE를 계속 점유해 같은 이메일 재가입이 영구 차단되는 부작용을 감수.
- **N일 경과 자동 삭제:** N(예: 7·30일) 확정 + 미인증·기한초과 정리 배치 신규. 배치 주기, 하드 삭제 vs 탈퇴와 동일한 익명화, 판별 쿼리(`email_verified=false AND created_at < now()-N일`) 설계 필요.
**관련:** SA §6-4, SA 부록 A.

## 2. SNS 로그인 (구글·카카오) — 신규 / 정책결정필요
**근거:** 현재 이메일·휴대폰·비밀번호·닉네임 가입만 지원(PRD v3.23·SA §6-6). OAuth2로 구글/카카오가 검증한 신원·이메일을 위임받으면 서버가 비밀번호를 저장할 필요가 없고 이 경로 가입자는 이메일 인증 절차 자체가 불필요. 기존 방식 대체가 아니라 로그인 수단 추가(병행).
**착수 전 팀 합의 3가지:**
- **계정 연동:** 같은 이메일의 기존 회원과 SNS 로그인을 같은 `Member`로 볼지, 별도로 둘지.
- **프로바이더 범위:** 구글만 vs 카카오까지. 카카오 이메일 스코프(`account_email`)는 비즈 앱 전환(검수)이 필요, 미전환 시 닉네임·프로필 이미지만 수신.
- **가입 스펙 변경:** 현재 가입 정의(이메일·휴대폰·비밀번호·닉네임 모두 필수, PRD v3.23) 대비 SNS 추가는 코드 격리는 가능해도 PRD/SA 범위·일정에 영향. 특히 휴대폰 필수 계약과 SNS 프로바이더가 주는 정보(구글은 전화번호 미제공)의 정합을 함께 정해야 한다.
**설계:** `EmailGateway`(§6-4)와 같은 추상화로 `OAuth2Gateway` 인터페이스부터 확정하고 세부는 그때 결정.
**관련:** SA §6-5.

## 3. 토큰 소비 순서 개선 (claim 패턴) — 설계안 (정책결정필요)
**근거:** 현재 "① Redis GET+DEL 원자 소비 → ② memberId로 회원 조회 → ③ 상태 변경 후 DB 커밋". ①과 ②~③ 사이 회원 조회/커밋이 실패하면 토큰이 이미 사라져 같은 링크로 재시도 불가(복구성 문제, 보안 구멍 아님). 단순히 "DB 처리 후 삭제"로 순서만 뒤집으면 동시 재사용 창이 다시 열린다 — "먼저 지우고 처리"(보안 O·복구성 X)와 "처리 후 지우기"(복구성 O·보안 X)는 트레이드오프.
**상태:** SA 부록 A는 이 항목(토큰 소비 순서)을 여전히 **미확정**으로 두고, 부록 A-1도 claim 패턴을 **제안 설계**로 명시한다. 팀 확정 전에는 구현에 착수하지 않는다(AGENTS). 아래는 그 제안 설계의 요지다.
**범위(3단계 claim, SA 부록 A-1 제안 설계 기준):**
1. **Claim:** `SET claim:{hash(token)} 1 NX PX <짧은 TTL 10~30초>`로 원자 선점. 실패 시 기존과 같은 `INVALID_OR_EXPIRED_TOKEN` — 동시 재사용은 여기서 차단.
2. **DB 처리:** 성공한 요청만 토큰(memberId) GET(아직 DEL 안 함) → 회원 조회 → 상태 변경 → 커밋.
3. **확정:** 성공 시 실제 토큰 키와 claim 키를 함께 삭제, 실패 시 토큰 키는 유지한 채 claim 키만 해제(또는 TTL 만료)해 재시도 허용.
`MemberTokenRepository.consumeEmailVerificationToken()`/`consumePasswordResetToken()`을 "claim 획득 → (호출부 DB 처리) → 커밋 결과에 따라 확정/롤백"의 2~3단계 API로 변경. 비밀번호 재설정 단일 활성 토큰(`pwd-reset-active:{memberId}`)과의 상호작용도 함께 설계. Level 3(실제 Redis) 동시 요청·DB 실패 시나리오 테스트 필요.
**미해결 설계 이슈(구현 전 확정 필요):** 위 3단계는 DB 커밋(2) 직후 실제 토큰 삭제(3) 전에 프로세스가 죽으면 claim TTL 만료 후 **원래 토큰이 다시 사용 가능**해진다. 이메일 인증은 결과적으로 멱등에 가깝지만, **비밀번호 재설정은 한 번 성공한 뒤 또 비밀번호를 바꿀 수 있어 "1회용 토큰" 계약을 위반**한다. 대안(토큰을 claim보다 먼저·원자적으로 무효화, 또는 재설정 토큰에 "소비됨" 영속 마커 추가 등)을 확정해야 한다 — 현재 claim 설계는 이 창을 아직 닫지 못한 제안 상태다.
**관련:** SA 부록 A-1, SA 부록 A.

## 4. 탈퇴 시 Redis 부수효과 순서 — 정책결정필요
**근거:** `MemberWithdrawalApplicationService.withdraw()`가 `@Transactional` 안에서 DB 변경 직후 같은 트랜잭션 내에 Redis 부수효과(`deleteByMemberId`·`blacklistMember`)를 실행한다. Redis는 커밋과 무관하게 즉시 반영되므로, Redis 성공 후 DB 커밋이 실패하면 DB상 활성 회원인데 세션만 삭제·블랙리스트된 fail-closed 불일치가 생긴다.
**범위(택1):**
- **현재 유지(fail-closed):** DB 커밋 실패라는 드문 케이스에서만, 결과가 "세션만 손해"라 보안 방향 안전. 구현 0.
- **`AFTER_COMMIT` 전환:** 커밋 확정 후에만 Redis 실행(§6-4 이메일 발송 흡수와 같은 패턴). 위 불일치는 사라지나, 커밋~Redis 반영 사이 짧은 창에 탈퇴 회원의 기존 Access Token이 여전히 인증 통과 가능.
둘 다 완전 해결이 아니라 "어느 실패 모드를 감수할지" 선택 → 팀 합의 필요.
**관련:** SA §6-3, SA 부록 A.

## 검증
- 3(claim)은 Level 3 실제 Redis로 동시 요청·DB 실패 시나리오를 검증. 1(정리 배치)·4(탈퇴 순서)는 스케줄러·트랜잭션 경계라 STRICT.
- 나머지는 정책 확정 후 구현한다. 판정은 PASS/FAIL/PARTIAL/BLOCKED, 완료 근거는 PASS만.
