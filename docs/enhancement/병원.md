## 공통 구현 원칙
- 회원·병원 스태프는 인증 주체로 식별(요청 body의 memberId·hospitalId 신뢰 금지). 스태프는 자병원 정보만, 회원은 본인 리뷰·찜만 수정·삭제.
- 공공데이터는 매일 03:00(`Asia/Seoul`)에 병원명·주소·전화번호·좌표·영업 상태(`business_status`) 등 원천 기본정보만 갱신한다. 진료역량을 제공하거나 추론하지 않으며, 제휴 상세·진료역량·운영 스케줄·임시 휴무는 변경하지 않는다. 단, 이번 갱신에서 `OPEN → CLOSED_TEMP/CLOSED`로 전환되면 `slot.startAt > now`인 진료 시작 전 `CONFIRMED` 예약만 `HOSPITAL_CANCELED`로 자동 취소한다.
- AI 추천은 실제 저장된 병원·진료역량·리뷰만 사용하고, 없는 리뷰·평점·진료역량을 생성하지 않도록 입출력을 검증한다.
- 리뷰·찜·통계 없는 병원이 검색·추천에서 부당하게 완전 제외되지 않게 한다. 스키마·인덱스 변경은 실제 MySQL Level 3 검증.

## 3.1 병원 찜하기 — #113 (develop 완료, 이 문서 작업 대상 아님)
**PR #128로 merge·develop 반영 완료.** 이 문서를 쓸 당시엔 미착수였으나 그사이 구현이 끝났다 — 아래는 실제 정본(코드)이 확정한 내용이고, 더 이상 "선행 정책 결정"이 아니다.
- **API:** `PUT`/`DELETE /api/hospitals/{hospitalId}/favorite`(등록/해제), `GET /api/members/me/favorite-hospitals`(내 목록). GUARDIAN 전용(`SecurityConfig`에서 `hasRole("GUARDIAN")`, 비인증 401·스태프 403).
- **중복·멱등:** `(member_id, hospital_id)` UNIQUE + 네이티브 `INSERT ... ON DUPLICATE KEY UPDATE`로 동시 중복 등록도 1건만 성립(8스레드 동시 요청 통합 테스트로 검증됨). 해제는 대상이 없어도 무조건 204.
- **응답 필드명은 `favorite`**(이 문서가 가정했던 `isFavorite`이 아니다) — 검색(`HospitalSearchResponse`)·상세(`HospitalDetailResponse`) **둘 다**에 `boolean favorite` 반영됨. 비인증·병원 스태프는 항상 `favorite=false`(정책 확정).
- **캐시 분리:** 공유 Redis 검색 캐시에는 회원별 `favorite`이 들어가지 않는다. 캐시 HIT/MISS 어느 쪽이든 응답 직전에 병원 ID 배치 조회 1회로 결합(N+1 없음, 다른 회원 간 찜 상태 섞임 없음 — 테스트로 확인).
- **내 찜 목록 정렬:** `createdAt DESC, id DESC`(안정 정렬). **폐업 병원도 영업상태와 함께 그대로 노출**(정책 확정).
- **회원 탈퇴:** 탈퇴 회원의 찜만 cascade 삭제, 다른 회원 찜은 보존.
**남은 것:** 찜 수의 검색 정렬·AI 추천 반영, 인기 순위, 찜 기반 알림, 병원 비교 화면 — 이 문서 범위 밖으로 계속 제외.

## 3.2 병원 리뷰 CRUD 및 평점 집계 — #114 (develop 완료, 이 문서 작업 대상 아님)
**PR #129로 merge·develop 반영 완료.** 이 문서를 쓸 당시엔 미착수였으나 그사이 구현이 끝났다 — 아래는 실제 정본(코드)이 확정한 내용이고, 더 이상 "선행 정책 결정"이 아니다.
- **작성 자격:** 본인 예약의 결제 상태가 `PAID`/`OFFLINE_PAID`일 때만. **예약 1건당 최초 1회**(`Reservation.reviewedAt` 조건부 UPDATE로 원자적 선점, 동시 작성 테스트로 검증됨).
- **평점 범위:** 1.0~5.0, 0.5 단위(앱 검증 + DB `CHECK` 제약 둘 다).
- **삭제 방식:** **Hard Delete**(Soft Delete 아님). 사용자 직접 삭제는 `reviewedAt`을 유지해 재작성을 차단하고, **환불 시에는** 리뷰를 Hard Delete하면서 `reviewedAt`도 초기화해 재작성을 허용한다(환불·리뷰 CRUD 경합은 결제 행/리뷰 행 `PESSIMISTIC_WRITE` 락으로 직렬화).
- **신고·숨김:** 포함 안 함(제외 확정).
- 병원 **상세** 응답에 `averageRating`(리뷰 없으면 null)·`reviewCount`(0) 반영됨. **검색 목록 응답에는 반영되지 않음**(상세 전용) — §5 참고.
- 별도 리뷰 상세 조회 API는 없음(목록 응답이 공개 정보를 전부 제공).
**후속 제외 범위:** 리뷰 기반 검색 랭킹, 찜·응답률 종합 점수, 대규모 신고·제재, 작성 보상, 이미지·동영상 리뷰. 리뷰의 AI 추천 반영은 PR #153에서 구현 완료됐다.

## 3.3 병원 스태프 진료시간 관리 — #115 — **구현 완료 (PR #144)**
**확정 정책:** 요일별 휴게·점심 표현, 변경 적용일, 미래 슬롯 재생성 범위, 예약 포함 슬롯 보존 방식, 정기/임시 휴무 구분, 공휴일 예외.
**범위:** 자병원 진료시간 조회·수정, 요일별 시작·종료·휴게시간 관리, 잘못된/중첩 시간 검증, 자병원·역할 권한 검증, 예약 없는 미래 슬롯 안전 재생성, 예약 있는 슬롯 보호, 기존 close-day·임시 휴무 연동.
**흐름:** 변경 요청 → 입력값·권한 검증 → 기존 예약 슬롯 보호 → 예약 없는 미래 슬롯 정리 → 변경 시간 기준 재생성.
**근거:** `SlotGenerationService`가 `HospitalDetail.openHours`로 슬롯을 만들지만 수정 API가 없다. 점심·공휴일·계절 변경 미반영 시 실제 운영시간과 슬롯 불일치, close-day만으로는 부분 변경 불가, 기존 예약 보호하며 미래만 재생성해야 유실 없음.
**제외:** 진료 항목별 가변 슬롯, 수의사별 일정·동시 수용, 슬롯당 복수 예약, 30분 정책 변경, 시작 시각 엄격 실시간 보장.

## 3.4 병원 스태프 진료역량 관리 — #116 — **구현 완료 (PR #150)**
**확정 정책:** 공공데이터에는 진료역량이 없고 서버도 공공데이터에서 진료역량을 추론하지 않는다. `partner-hospitals.json`의 역량은 최초 제휴 데이터 구축을 위한 초기값일 뿐이며, 이후에는 담당 병원 스태프가 저장한 `hospital_capabilities` 현재값을 최종값으로 사용한다. 팀 합의에 따라 현 단계에서는 `source`/`precedence` 컬럼과 전용 수정 이력 테이블·관리자 승인 절차를 두지 않는다. 대신 스태프의 진료역량 변경이 성공하면 병원 식별자, 변경 주체 식별자, 변경 전·후 항목 수를 구조화 로그로 남긴다. 향후 외부 진료역량 연동이나 감사 요구가 생기면 출처 우선순위와 영속 이력 정책을 별도로 확정해 확장한다.

**범위:**
- 인증된 `HOSPITAL_STAFF`가 `@AuthenticationPrincipal`의 `memberId`로 확인된 자병원의 진료역량을 조회하고 전체 교체한다. 요청 body·query·path의 `memberId`·`hospitalId`는 식별 근거로 사용하지 않는다.
- 기존 `CapabilityValue` 19개 화이트리스트만 허용하고, 값이 가진 `CapabilityType`을 그대로 사용한다. 허용되지 않은 값과 요청 내 중복 값은 400으로 거부한다.
- 수정 요청은 추가·삭제 명령이 아니라 전달받은 전체 목록으로 현재 진료역량을 교체한다. 결과는 승인 대기 없이 즉시 병원 상세와 QueryDSL 검색 필터에 동일하게 반영한다.
- 공공데이터에서 `business_status=CLOSED`로 확인된 병원은 진료역량을 수정할 수 없다. 폐업해도 제휴 상태, 상세정보, 진료역량과 과거 예약·결제·리뷰 이력은 삭제하지 않는다.

**제휴 시드·매일 갱신:**
- 최초 데이터 구축에서는 공공데이터 병원 적재 후 `partner-hospitals.json`을 한 번 적용해 제휴 상태·상세정보·초기 진료역량을 생성한다.
- 공공데이터 제공처의 변경이 일 단위로 반영되는 반면 서버가 주 1회만 동기화하면 실제 휴업·폐업 병원이 서버에서 최대 약 1주일 동안 `OPEN`으로 남아 신규 예약을 받을 수 있다. 이 불일치 기간을 줄이기 위해 서버의 전국 공공데이터 갱신 주기를 기존 매주 월요일 03:00에서 매일 03:00(`Asia/Seoul`)으로 변경하기로 팀 합의했다.
- 매일 03:00 공공데이터 갱신은 공공 원천 기본정보와 `business_status`만 갱신하고 검색 캐시를 무효화한다. 제휴 JSON을 재적용하지 않으며 `partnership_status`, `hospital_details`, `hospital_capabilities`, 운영 스케줄, 임시 휴무와 예약 데이터는 변경하지 않는다.
- 폐업은 제휴 계약 종료와 다른 개념이므로 `business_status=CLOSED`만으로 `partnership_status`를 자동 변경하지 않는다. 일반 검색은 `OPEN` 병원만 노출하며 휴업·폐업 병원은 캐시 HIT/MISS 모두에서 제외한다. 휴업·폐업 병원은 신규 예약·신규 슬롯 생성에서도 제외한다. 이번 공공데이터 갱신에서 `OPEN → CLOSED_TEMP/CLOSED`로 전환된 경우에만 `slot.startAt > now`인 `CONFIRMED` 예약을 `HOSPITAL_CANCELED`로 자동 취소하고 슬롯을 반환하며, 대상 조회와 조건부 UPDATE에 같은 시간 조건을 사용한다. `startAt == now`와 과거 예약은 자동 취소하지 않는다. 취소 사유·시각과 시스템 이력(`processed_by=null`)을 보존하고 보호자에게 알림을 저장한다. `REQUESTED`와 `CHECKED_IN` 이후 예약은 이 자동 취소 대상에 포함하지 않는다. 신규 예약 요청과 승인은 공공데이터 갱신과 동일한 병원 행 `FOR UPDATE` 잠금 아래 `OPEN`을 확인한다. 신규 요청은 이 잠금을 슬롯 점유·예약 저장까지 유지하므로 갱신이 먼저 확정되면 요청과 승인이 모두 실패한다.
- 일 배치, 진료시간 변경에 따른 슬롯 교체, 임시 휴무 취소 후 슬롯 복구는 모두 병원 행 잠금 안에서 `business_status=OPEN`일 때만 신규 슬롯을 만든다.

**흐름:** 최초 제휴 시드로 초기 역량 생성 → 담당 병원 스태프가 전체 목록 조회·교체 → `hospital_capabilities` 현재값을 상세·검색에서 즉시 사용. 매일 공공데이터 갱신은 이 흐름과 분리한다.

**근거:** 진료역량은 공공데이터 원천 필드가 아니며 실제 지원 동물·검사·전문 진료·장비는 담당 병원이 가장 정확하게 관리할 수 있다. 정기 갱신이 제휴 JSON을 재적용하는 구조는 운영자가 수정한 값을 초기 시드로 되돌릴 수 있으므로, 최초 구축과 주기 갱신의 책임을 분리한다. 진료역량 변경 로그는 정식 감사 이력이나 복원 수단이 아니라 현 단계의 최소 운영 추적 수단이며, 합의한 식별자와 변경 전·후 항목 수만 기록한다.

**제외:** 출처 구분·우선순위 컬럼, 진료역량 전용 이력 테이블과 이력 조회·복원 기능, 관리자 승인 시스템, 자격증 증빙, 수의사 개인별 진료역량, 항목별 가격, 진료역량별 슬롯 길이 변경.

## 3.5 AI 상담과 회원 펫 프로필 연동 — #117 — **미구현 종료·범위 제외**
이 기능은 구현하지 않기로 결정해 이슈 #117을 종료했다. 현재 AI 상담은 회원의 저장된 펫을 선택하거나 조회하지 않고 요청에 직접 포함된 `species`를 사용한다. 회원 펫 소유권 검증, 펫 프로필 연관·스냅샷 저장, 프로필 정보를 AI 문맥에 자동 결합하는 기능은 현재 범위에 포함하지 않는다.

## 3.6 진료역량과 리뷰를 반영한 AI 병원 추천 — #118 — **구현 완료 (PR #153)**
**선행 이슈:** #114·#116. #117의 펫 프로필 연동은 선행 조건으로 두지 않고, 상담 요청에 명시된 `species`를 병원 지원 동물 비교에 사용한다.
**범위:** AI가 파악한 증상↔병원 진료역량 연결, 요청 축종↔병원 지원 동물 비교, 거리·영업상태를 기본 후보 조건으로 유지, 리뷰 통계·선별 리뷰를 보조 근거로 반영, 최대 3개 병원에 추천 적합도·추천 이유·객관적 근거 제공, 리뷰/진료역량 부족 병원 fallback, 실제 저장 데이터만 사용 검증, AI 실패 시 기존 안전 응답·검색 fallback 유지.
**리뷰 근거:** 리뷰 작성·수정 시 본문은 최대 300자로 제한한다. 병원별 평균 평점·전체 리뷰 수와 긍정(4.0~5.0)·보통(3.0~3.5)·부정(1.0~2.5) 구간별 리뷰 수를 주된 판단 근거로 제공한다. 리뷰 본문은 별도로 자르지 않고 각 구간의 최신 리뷰를 최대 1개씩, 병원당 최대 3개까지 선별한다. AI 평가 후보는 최대 20개 병원으로 유지하되, 한 요청에 포함되는 리뷰 본문은 전체 최대 60개·총 18,000자로 제한한다. 제한 도입 전에 저장된 300자 초과 리뷰는 전체 통계에는 포함하되 AI 본문 표본에서는 제외한다. 리뷰 본문은 신뢰할 수 없는 사용자 데이터로 취급해 내부의 요청·명령을 모델 지시로 따르지 않는다. 선별 리뷰는 개별 사례를 보여 주는 보조 근거로만 사용하며 일부 표본을 전체 리뷰의 의견처럼 표현하지 않는다. 리뷰가 없거나 적다는 이유만으로 병원을 제외하거나 추천 적합도를 낮추지 않는다.
**추천 응답:** 조건에 맞는 후보가 3개 이상이면 3개, 3개 미만이면 실제 후보 수만큼 반환한다. 각 병원에는 사용자 리뷰 평균인 `averageRating`과 구분되는 AI 추천 적합도 `recommendationScore`(1~5 정수), 실제 데이터에 근거한 정보를 제공한다. 모델은 자유 형식 추천 이유를 생성하지 않고 객관적 근거만 선택하며, 서버가 검증을 통과한 근거 유형을 안전한 한국어 문구로 조합해 `recommendationReason`을 생성한다. `recommendationScore` 내림차순으로 정렬하고 동점이면 거리가 가까운 병원을 먼저 배치한다.
**판단 우선순위:** 진료역량·축종 일치를 리뷰보다 우선하고, 거리·영업상태와 리뷰를 추가 판단 근거로 사용한다.
**흐름:** 증상 + 요청 축종 → 필요한 진료역량 도출 → 거리·영업상태로 후보 제한 → 지원 동물·진료역량 일치 확인 → 리뷰 통계·구간별 선별 리뷰로 보완 → 최대 3개 추천 병원 + 추천 적합도 + 이유 + 근거.
**근거:** 거리·영업상태만으로는 진료 가능성·경험 설명 부족, 병원 직접 확인 진료역량이 실제 제공 역량을 반영, 요청 축종↔지원 동물 비교로 부적합 병원 감소, 평균 평점·전체 리뷰 수·평점 분포를 함께 사용해 소수 고평점이나 일부 리뷰의 과대대표를 완화, 근거 동반 제공으로 AI의 근거 없는 설명 방지.
**제외:** 전체 검색 종합 랭킹, 찜 수·응답률 자동 반영, 광고·제휴 순위, AI 자동 예약, 의료 진단·처방.

## 3.7 병원 예약 응답률 및 평균 승인 시간 — #119 — **구현 완료 (PR #165)**
**확정 정책:** 조회 시각을 끝으로 최근 90일간 `requestedAt`이 포함되는 예약을 실시간 집계한다. 응답률 분모는 승인, 병원 직접 거절, 승인 타임아웃 자동 거절이며 분자는 승인과 병원 직접 거절이다. 병원 응답 전 보호자 취소와 아직 `REQUESTED`인 예약은 제외한다. 타임아웃 마감이 지났더라도 실제 상태 전이와 `TIMEOUT_REJECTED` 이벤트 기록이 완료되지 않았다면 집계하지 않는다. 승인 후 보호자·병원 취소, 진료 완료, 노쇼로 바뀐 예약도 최초 승인 이력이 있으면 승인으로 집계한다.
**노출 정책:** 응답률 표본이 10건 이상일 때 `reservationResponseRate`를 반올림한 정수 백분율로 제공한다. 승인 표본이 10건 이상일 때 각 예약의 `confirmedAt-requestedAt`을 먼저 구한 뒤 평균하여 `averageApprovalMinutes`를 반올림한 정수 분으로 제공한다. 각 기준 미달 값은 독립적으로 `null`이며 내부 표본 수와 집계 기간은 API에 노출하지 않는다. 비제휴 병원은 두 값을 모두 `null`로 반환한다.
**구현:** 병원 상세 API 조회 시에만 MySQL 원본을 실시간 집계한다. 병원 이름 등 기본 정보만 사용하는 채팅·예약 상세 내부 경로에서는 집계하지 않는다. 이번 범위는 집계 결과의 기능·정합성 검증까지이며, `(hospital_id, requested_at)` 조회 인덱스, 캐시·사전 집계, 운영 데이터 규모의 실행계획·P95 측정은 제외한다. 운영 데이터 증가로 상세 조회 성능 문제가 확인되면 후속 성능 고도화 이슈에서 실행계획과 P95를 먼저 측정한 뒤 조회 인덱스 또는 일일 사전 집계를 선택한다.
**흐름:** 병원별 예약 이력 → 완료된 응답 사건·최근 90일·최소 표본 정책 적용 → 응답률 + 평균 승인 시간 → 병원 상세.
**근거:** 승인형 예약이라 응답 여부·속도를 보호자가 알 필요, 필요한 데이터가 이미 존재, 리뷰·평점만으론 운영 품질 판단 어려움, 표본 적은 수치 노출은 오해 유발 → 최소 표본 정책 필요.
**제외:** 응답률의 검색 정렬·AI 추천 반영, 스태프별 응답률, 실시간 순위, 성과 평가·제재, 운영 대시보드 전면 구축.

## 5. 기존 검색 성능 개선(#69)과의 관계
#69(검색 후처리 조회 범위 개선: 전체 메모리 적재 회피, 무좌표 병원 거리 정렬 경계, 영업중 후처리 배치화, 페이지 계약 유지)는 본 고도화와 별도로 완료했다. 리뷰(#114)의 `averageRating`·`reviewCount`는 **병원 상세 응답에만** 추가됐고 검색 목록 응답에는 없어 #69의 검색 페이지네이션과 무관하다(코드 확인). 찜(#113, PR #128, develop 완료)은 검색 목록에도 `favorite` 필드를 추가했지만 **재검증 결과 문제없음** — `HospitalService`의 찜 결합(`withFavorites`)은 캐시·페이지네이션·배치조회로 이미 결정된 결과 목록에 대해 병원 ID 배치 조회 1회를 얹는 순수 후처리 단계라, #69가 확정한 오프셋/배치 크기/페이지 계약 자체는 건드리지 않는다(코드 확인, `HospitalSearchServiceTest`의 캐시 HIT/MISS 테스트로도 검증됨). 응답률(#119, PR #165)은 병원 상세 응답에만 추가됐고 검색 목록에는 포함하지 않았으므로 검색 페이지네이션 계약은 그대로다. #70은 재검토 후 종료, 범위에서 제외.

## 6. 검증
- 완료된 #113~#116·#118·#119는 각 구현 PR에서 기능·권한·정합성 및 변경 범위에 필요한 실제 MySQL 통합 검증을 수행했다. #119는 실시간 집계의 기능·정합성까지 검증했고 운영 데이터 규모의 실행계획·P95 및 인덱스·캐시는 후속 성능 고도화 범위로 남겼다.
- #117은 구현하지 않으므로 관련 소유권·프로필 결합 검증도 완료 조건에 포함하지 않는다. 기존 AI 상담 요청의 `species` 사용 계약은 #118 검증 범위에서 확인했다.
