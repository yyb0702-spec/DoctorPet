# 고도화 — 결제 (담당: @maschemy)

> 이 문서는 동결된 MVP 정본에 대한 **델타(변경분)**다. 아래 `전제` 절에 적힌 SA·PRD 절만 함께 읽으면 되고, 그 밖의 MVP 문서는 읽지 않는다.
> 충돌 시: 이 문서가 `override 범위`에 선언한 것 안에서는 이 문서 > 동결 SA. 범위 밖은 동결 SA가 정본. (레이어 규칙: [README](README.md))

## 메타

- **상태:** 구현중 (3.1·3.2·3.4 구현 완료, 3.3·3.5-a는 정책 정본화 완료·구현 대기)
- **담당:** @maschemy
- **관련 이슈:** #
- **전제(동결 baseline — 이 절만 함께 읽는다):** SA §9-4(멱등·실패 분기·항목·영수증·셀프 복구·정정 재청구), SA §5-2(결제 상태), SA §8-7(결제 API), SA §4 payments·payment_methods·payment_items, PRD §6-7
- **override 범위(이 문서가 바꾸는 계약):** ① 청구 금액 항목화(payment_items 신설), ② 영수증 발급, ③ 결제수단 기본값·예약 결제수단 재지정, ④ 정정 재청구(payments의 예약당 활성 결제 UNIQUE로 대체) + 부분 환불(계약 미확정, 3.5 참고), ⑤ 결제 실패 셀프 복구, ⑥ 결제 알림 내용(금액·PENDING 안내)
- **건드리지 않는 것:** 청구·환불·정산·오프라인·웹훅의 **발행 지점·중복 차단(`applied`)** 구조 유지. 실패 분기·재시도·정산 스케줄러 유지. 알림 **전달 인프라**는 [알림.md](알림.md) 소유. 현장 수납분 환불은 제외(확정).

## 정본과의 관계 (정책 정본화 완료)

- 항목화·영수증·셀프 복구·정정 재청구의 **확정 정책 정본은 `AGENTS.md` 확정 결정 목록·PRD §6-7·SA §4·§5-2·§9-4**다. 이 문서는 그 계약을 요약·상세화하는 델타이며, **정본의 확정 결정을 단독으로 덮어쓰는 표현을 두지 않는다**(레이어 규칙 4의 override 대상은 동결 SA이지 AGENTS 확정 결정이 아니다).
- 정정 재청구(3.5-a)는 더 이상 "제안"이 아니다 — 기존 **"환불한 예약은 재청구할 수 없다"** 결정을 대체하는 갱신이 AGENTS·PRD·SA에 반영됐다. 남은 것은 구현(제약 교체·선기록 검사 교체)뿐이다.
- 부분 환불(3.5-b)은 재청구와 별개 계약이며 **여전히 미확정·제외**다(아래 "부분 환불 계약"). 계약이 PRD·SA에 확정 반영되기 전에는 착수하지 않는다.

## 3.1 청구 금액 항목화 — **구현 완료 (PR #158)** (STRICT: 스키마)
**범위:** `Payment.amount` 단일 총액 → `payment_items`(명칭·수량·단가·금액) 리스트. 총액 = 항목 합계 정합. 청구 시점 스냅샷으로 고정. 청구/환불/영수증/정정 근거로 재사용.
**근거:** 총액 하나라 "왜 8만원인지" 알 수 없고, 환불은 이미 있는데 분쟁 근거 데이터가 없다. **3.4·3.5의 데이터 전제**라 결제 계열 선두.
**제외:** 세율·부가세 분리, 진료 항목 마스터 코드 표준화.

**확정 계약 (정본: PRD §6-7·SA §4 payment_items·§9-4):**
- **작성·수정 창:** 병원 스태프만, **진료 완료 후 ~ 청구 선기록 전**까지. 선기록(Payment `PENDING` 생성) 이후에는 항목을 절대 수정·삭제하지 않는다.
- **경계의 성격:** 이 금지는 스냅샷 정합성뿐 아니라 **정정 재청구(3.5-a)를 우회 구현하지 못하게 하는 경계**다. 기존 결제의 금액 정정은 항목 수정이 아니라 3.5-a 절차만 쓴다.
- **초안 모델:** 청구 전 항목은 예약에 매달린 초안(`payment_items.reservation_id` + `payment_id IS NULL`)이다. 선기록 전에는 `payments` 행이 없어 결제에 매달 수 없기 때문이다. 선기록은 한 트랜잭션에서 **예약 행 락 → 초안 재조회·합계 산출 → `payments`(PENDING) INSERT → 채번된 id로 초안 스탬프** 순서다(SA §9-4). `payments.id`가 IDENTITY라 INSERT가 스탬프보다 먼저여야 하며, 스탬프 건수가 재조회한 초안 수와 다르면 전체를 롤백한다.
- **직렬화(STRICT):** 항목 수정과 청구 선기록은 **같은 예약 행을 `PESSIMISTIC_WRITE`로 잠근다**(`findByIdForUpdate` — 청구가 이미 쓰는 락, 3.2의 재지정과 같은 락). 청구는 잠금 뒤 초안을 재조회해 **총액을 서버가 산출**하고, 항목 수정은 `WHERE payment_id IS NULL` 조건부 UPDATE로만 반영해 0건이면 `PAYMENT_ITEM_ALREADY_CHARGED`(409)로 거부한다. 락 없이 "PENDING 없음"만 확인하면 check-then-act이라 **영수증 항목 합계와 `payments.amount`가 갈라진다**.
- **할인·조정:** 별도 할인 필드 없이 **음수 금액 항목**으로 기록한다. `unit_price`·`amount`는 음수를 허용하는 signed 정수 컬럼이다 — **DDL에서 이 두 컬럼을 `UNSIGNED`로 만들면 안 된다**(음수 조정 저장이 막힌다). `quantity > 0`은 요청 DTO `@Positive`로 강제하고, `amount`는 요청에서 받지 않고 서버가 `quantity * unit_price`로 계산한다.
- **합계:** 스탬프된 항목에 한해 `payments.amount == sum(payment_items.amount)`이고 합계는 **0 초과**·절대 상한 이하다.
- **기존 결제:** 항목화 이전 결제는 항목이 없고 **백필하지 않는다**(총액으로 합성 항목을 만들면 증빙에 없던 내역이 생긴다). 불변식은 항목이 있는 결제에만 적용한다. 항목화 이후의 일반 신규 청구와 정정 재청구는 항목 1건 이상이 필수지만, 항목 없는 레거시 `OFFLINE_REQUIRED` 결제의 셀프 재청구는 원 내역을 꾸며내지 않기 위해 새 복구 결제도 항목 0건을 허용하고 원 총액만 승계한다.

## 3.4 영수증·증빙 발급 — **구현 완료 (PR #158)** (JSON)
**범위:** 결제 완료 건 영수증 데이터(항목·총액·병원·일시·결제수단 brand·last4), 펫보험 청구용 최소 증빙 필드. **형식은 구조화 JSON까지**, PDF/전자문서는 후속.
**근거:** 지금 내려줄 게 `PaymentHistoryResponse`뿐. 펫보험 청구에 영수증이 필요.
**제외:** 세금계산서·현금영수증 국세청 연동, 진료확인서(수의사 서명), PDF·전자문서.

**확정 계약 (정본: PRD §6-7·SA §9-4):**
- **대상:** `PAID`·`OFFLINE_PAID`·`REFUNDED`. `PENDING`·`OFFLINE_REQUIRED`는 확정된 수납 사실이 없어 발급하지 않는다.
- **인가:** 보호자는 본인 예약 결제만, 병원 스태프는 자기 병원 결제만. 식별은 `@AuthenticationPrincipal`만 신뢰한다.
- **내용과 기준 시점:** 결제 항목·총액·결제 일시·결제수단 brand·last4는 결제 시점 스냅샷을 쓴다. 병원·보호자는 변경 가능한 표시명 대신 안정 식별자만 제공하고, 펫은 `pet_id`와 예약 시점의 이름·종 스냅샷을 제공한다. 현재 병원명·회원명·연락처는 영수증에 넣지 않는다. `REFUNDED`는 환불 상태·환불 일시를 추가한다.
- **항목이 없는 결제:** 항목화 이전 결제는 항목을 **빈 배열로 반환하고 총액만 제공**한다. 합성 항목으로 채우지 않고, 발급 자체를 막지도 않는다(실제 수납된 건이다).
- **환불 사유 비노출(기존 결정 승계):** `payment_refunds.reason`은 SA §4대로 감사용이며 보호자 알림·보호자 응답·영수증에 넣지 않는다.

## 3.2 결제수단 기본값·예약 결제수단 재지정 — **구현 완료 (PR #152)**
**범위:** 기본 결제수단 지정·변경 API, **예약의 결제수단 재지정**(진료 전 카드 교체 반영), DELETED 결제수단이 예약에 물린 경우 처리.
**근거:** `Reservation.paymentMethodId`가 요청 시점 고정 → 카드 교체 시 기존 카드 DELETED → 진료 후 청구가 전부 `OFFLINE_REQUIRED`로 떨어진다. 재지정 수단이 없다.
**제외:** 우선순위 자동 폴백 체인, 분할 결제.

**상태:** 구현·병합 완료(PR #152, develop). 정본 반영도 완료 — `payment_methods.is_default`·생성 컬럼·UNIQUE·조회 인덱스는 SA §4 payment_methods, 두 API와 직렬화 계약은 SA §8-7, 제품 정책은 PRD §6-7에 있다. 아래는 그 계약의 상세 사본이다.

**확정 계약 (PR #152):**
- **스키마·기존 데이터:** `payment_methods.is_default boolean not null default false`를 추가한다. MySQL 부분 UNIQUE 부재를 보완하기 위해 `status='ACTIVE' and is_default=true`일 때만 `member_id`를 내보내는 stored 생성 컬럼 `active_default_member_id`와 `UNIQUE uk_payment_methods_active_default_member_id(active_default_member_id)`로 회원별 활성 기본 결제수단을 최대 한 건으로 제한한다. 기존 비활성 수단의 기본값은 `false`로 정리하고, 기존 활성 수단은 자동으로 기본값을 부여하지 않는다. 기본값 변경 때 활성 수단을 잠그는 조회는 `idx_payment_methods_member_id_status(member_id, status)`를 사용한다.
- **기본값 API:** 보호자만 `PATCH /api/payment-methods/{paymentMethodId}/default`를 호출한다. 성공은 `200 ApiResponse<PaymentMethodResponse>`이며 응답의 `isDefault`가 `true`인 대상이 해당 회원의 유일한 ACTIVE 기본값이다. 본인 소유가 아니거나 없으면 `PAYMENT_METHOD_003`, 비활성 수단이면 `PAYMENT_METHOD_004`를 반환한다. 동시 최초 등록은 DB UNIQUE 충돌을 비기본 저장으로 재시도해, 저장된 수단은 모두 보존하면서 기본값은 한 건만 남긴다.
- **예약 재지정 API:** 보호자만 `PATCH /api/reservations/{reservationId}/payment-method`에 `{ "paymentMethodId": number }`를 보낸다. 성공은 `200 ApiResponse<Void>`이다. 인증 보호자의 소유인 ACTIVE 결제수단만 지정할 수 있으며, 예약은 `REQUESTED` 또는 `CONFIRMED`에서만 변경한다. 결제 선기록이 이미 있으면 상태와 관계없이 `RESERVATION_019(PAYMENT_ALREADY_STARTED)`으로 거부하고, 진료가 시작된 뒤의 상태는 `RESERVATION_018(PAYMENT_METHOD_CHANGE_NOT_ALLOWED)`으로 거부한다.
- **청구와의 직렬화:** 재지정과 청구 선기록은 같은 예약 행을 `PESSIMISTIC_WRITE`로 잠근다. 청구가 먼저 예약 잠금·결제 선기록을 커밋하면 이후 재지정은 결제를 발견해 거부된다. 재지정이 먼저 커밋되면 이후 청구는 예약에 저장된 교체 결제수단의 brand·last4 스냅샷을 사용한다. 상태 전이상 정상 청구는 `TREATMENT_COMPLETED`, 재지정은 진료 전 상태에서만 가능하므로 두 성공 경로가 같은 상태에서 동시에 성립하지는 않는다.

## 3.3 결제 실패 셀프 복구 + 3.5 정정 재청구·부분 환불 — **STRICT 클라이맥스**
**범위:**
- 3.3: `OFFLINE_REQUIRED`에서 보호자가 카드 교체 후 **재청구 트리거**하는 셀프 경로.
- 3.5-a **금액 정정 재청구**(예: 8만→6만 오타 정정): 기존 PAID를 전액 REFUNDED로 돌리고 **새 payment row 생성 + `correction_of`(이전 payment_id) 체인**. 최종 결제는 새 row 하나로 표현되므로 기존 `REFUNDED`(전액 종착 상태, SA §5-2) 그대로 재사용해도 의미가 맞는다 — 이건 "취소 후 재시도"다.
- 3.5-b **부분 환불**(예: 8만 결제 중 2만만 환불, 6만은 유지): **아래 "부분 환불 계약"이 비어 있었다(리뷰 지적) — 계약 확정 전 구현하지 않는다.**
- 3.3·3.5-a는 **같은 "새 시도 = 새 row + 체인" 메커니즘 공유**. 3.5-b는 기존 row를 대체하지 않는 별개 메커니즘이다(아래 참고).

**확정 계약 — 3.3 셀프 복구 (정본: PRD §6-7·SA §5-2·§9-4):**
- **전제 상태는 `Payment.status == OFFLINE_REQUIRED`뿐**이다. 보호자가 `ACTIVE` 결제수단을 새로 지정한 뒤 **명시적으로 재청구를 요청**해야 하며, 서버가 요청 없이 자동 재시도하지 않는다.
- **`PENDING`에서는 어떤 셀프 재청구도 허용하지 않는다.** 승인 여부가 불확정이라 이중 결제 위험이 있어, 기존 정산 스케줄러(SA §9-7)의 단건 조회 결과를 기다린다.
- `AMOUNT_MISMATCH`·`INVALID_PG_RESULT`처럼 자동 확정하지 않는 `PENDING`은 **기존 운영 확인 한계**이며, 이번 범위에서 자동 복구 정책을 새로 추가하지 않는다.
- **항목·금액·체인 승계:** 새 결제는 `recovery_of`로 원 `OFFLINE_REQUIRED` 결제를 가리킨다(`correction_of`와 동시에 쓰지 않으며 DB `CHECK`로도 막는다). 원 결제에 스탬프 항목이 있으면 원 행 대체, 새 `PENDING` 생성, 원 항목을 보존한 새 `payment_items` 행 전체 복제를 같은 선기록 트랜잭션에서 수행한다. 복제 항목 합계와 원 `amount`가 다르면 대체를 롤백하고 PG 승인 요청 없이 운영자 확인 대상으로 남기며, 일치할 때만 같은 금액을 승인 요청한다. PG 요청은 선기록 트랜잭션 밖에서 한다. 클라이언트는 항목·총액을 보내거나 바꿀 수 없다. 원 결제가 항목화 이전 결제라면 가짜 항목을 만들지 않고 원 총액만 승계하며, 새 영수증도 항목 빈 배열 규칙을 따른다. 새 시도마다 `merchant_payment_id`를 새로 발급한다.
- **현장 수납과의 경합(STRICT — 이중 수납 방지):** 셀프 재청구의 대체는 `WHERE id=? AND status='OFFLINE_REQUIRED' AND superseded_at IS NULL` 조건부 UPDATE가 1건 성립한 트랜잭션에서만 새 `PENDING` 행을 만들고, **오프라인 정산도 전제조건에 `superseded_at IS NULL`(활성)을 포함**한다. 먼저 커밋한 쪽이 이기고 늦은 쪽은 409다 — 이 조건이 없으면 상태만 보는 정산이 대체된 행을 `OFFLINE_PAID`로 만들고 새 행이 `PAID`가 되어 한 예약에서 **자동결제와 현장 수납이 동시에 성립**한다. 다중 스레드 + 실 MySQL(Level 3)로 "둘 중 하나만 성립"을 검증한다.

**확정 계약 — 3.5-a 정정 재청구 (정본: AGENTS 확정 결정·PRD §6-7·SA §4·§9-4):**
- 전액 환불된 기존 `PAID` 결제 뒤에 **새 `payments` 행 + `correction_of` 체인**. 예약당 **활성 결제 1건**만 허용하고, 환불·대체된 과거 결제는 이력으로 남긴다.
- 기존 `payments.UNIQUE(reservation_id)`가 이 흐름을 막으므로 **"활성 결제 UNIQUE"로 대체**한다(다음 절). 같은 PR에서 **`exists(reservation_id)`로 판단하는 게이트 두 곳(청구 선기록, 항목 초안 쓰기)도 함께 바꾼다.**
- **초안 게이트의 술어(중요):** 단순히 "활성 결제가 있으면 거부"로 바꾸면 정정 재청구도 막힌다 — 전액 환불은 `superseded_at`을 세우지 않아 `REFUNDED` 결제가 그대로 활성이기 때문이다. 활성 결제가 **`REFUNDED`일 때만 초안 작성을 허용**하고, `PENDING`·`PAID`·`OFFLINE_PAID`·`OFFLINE_REQUIRED`는 거부한다(`OFFLINE_REQUIRED`는 셀프 복구가 원 항목을 복제하므로 초안이 필요 없다). 순서는 환불 → 정정 초안 작성 → 재청구 트랜잭션(선점·새 결제·스탬프)이다(SA §9-4 "전체 순서(고정)"). 교체 순서는 expand/contract를 지킨다 — 새 UNIQUE를 먼저 만들고 검증한 뒤 구 UNIQUE를 제거하며, 재청구 경로는 그 다음 배포에서 활성화한다(SA §4 "제약 교체 순서"). 순서를 뒤집으면 두 제약이 모두 없는 창에서 활성 결제가 2건 생긴다. 청구 선기록의 `exists(reservation_id)` 검사도 같은 PR에서 활성 결제 기준으로 바꾼다.
- **새 결제의 항목·멱등키:** 새 결제는 자기 초안 항목을 새로 작성해 스탬프받고(3.1), `merchant_payment_id`도 새로 발급한다 — 이전 키를 재사용하면 공급자 멱등 캐시가 이전 승인을 돌려줘 정정 금액이 승인되지 않는다.
- **리뷰 부수효과:** 정정은 전액 환불을 반드시 거치므로 기존 계약대로 **그 예약의 리뷰가 Hard Delete되고 작성권이 초기화**된다(SA §9-4·§9-10). 새 결제가 `PAID`가 되면 작성권은 복구되지만 리뷰 본문은 돌아오지 않는다. 보호자 안내 포함 여부는 구현 PR에서 결정한다.
- 부분 환불(3.5-b)과는 무관한 별개 계약이고, 현장 수납(`OFFLINE_PAID`) 환불은 계속 제외다.

**부분 환불 계약 (선행 정책 결정, 미정 — 확정 전 구현하지 않는다):**
- **상태 표현:** `REFUNDED`(SA §5-2)는 전액 환불의 종착 상태라 부분 환불에 그대로 쓰면 전액 환불과 구분이 안 된다. 새 상태값(예: `PARTIALLY_REFUNDED`, SA 개정 필요) vs `status=PAID` 유지 + 누적액 컬럼만으로 구분, 둘 중 확정 필요.
- **금액 필드:** 원 결제액(`amount`)과 별도로 이 결제에서 **누적 환불된 금액**을 저장해야 한다(이번 요청액이 아니라 지금까지의 합계). 잔여액 = `amount - 누적 환불액`.
- **누적 상한(DB로 보장):** 동시에 두 부분 환불 요청이 들어와도 누적 환불액이 `amount`를 못 넘게 조건부 UPDATE(`WHERE 누적 + :요청액 <= amount`) 또는 DB `CHECK` 제약으로 막는다 — 애플리케이션 검증만으론 동시 요청에서 뚫린다(SA §9-4 멱등과 같은 이유). 다중 스레드 "합계가 원금을 못 넘음" 테스트 필수.
- **멱등키:** 3.5-a의 `merchant_refund_id` 재사용 방식을 그대로 쓸지, 부분 환불마다 별도 키가 필요한지 — PortOne 부분 환불 API 자체 지원 여부부터 먼저 확인해야 한다.
- **`payment_refunds` 이력 스키마 영향:** 현재 이력 테이블이 "환불 1건 = payment 1건"을 가정하는지, 한 payment에 여러 부분 환불 이력이 쌓이는 구조로 바뀌어야 하는지 확인 필요.

**활성 결제 유일성(확정 방식, 3.3·3.5-a 대상 — 3.5-b는 기존 row를 대체하지 않으므로 이 제약과 무관):** MySQL은 부분 유니크 인덱스가 없으므로, `payments`에 nullable **생성 컬럼 `active_reservation_id`**(활성일 때만 `reservation_id`, 아니면 NULL) + `UNIQUE(active_reservation_id)`. NULL은 UNIQUE에서 중복이 아니므로 "예약당 활성 결제 1건"이 DB 제약으로 못박힌다.
**동시성(STRICT):** 활성 결제가 있으면 새 청구를 막는 조건부 처리 → 이중결제 방지. 다중 스레드 "1건만 성립" 테스트 필수(SA §9-4 멱등).
**활성의 술어(확정):** 활성은 상태가 아니라 `superseded_at IS NULL`이다. 대체는 `OFFLINE_REQUIRED`(3.3)·`REFUNDED`(3.5-a)에서만 허용하고 `PAID`·`OFFLINE_PAID`는 대체하지 않는다 — 이미 수납된 결제를 대체하면 받은 돈의 근거가 사라진다(SA §5-2).
**근거:** 전액 환불만 가능해 정정하려면 전액 환불 후 신규 청구인데, `reservation_id` UNIQUE가 같은 예약 재청구를 막아 금액 오타 하나가 오프라인 수납으로 강제 전환된다.
**제외(확정):** 현장 수납분 환불, 자동 재시도 스케줄.

## 3.6 결제 알림 내용 보강 — 홀 메꾸기
**범위:** P2 결제 알림에 금액 포함(현재 문구만, 금액 없음). P1 `PENDING`/`RECONCILE_STUCK` 무음 해소 — "결제 확인 중" 안내 1회(상태는 안 바꾸고 안내만, 이중수납 금지 유지).
**근거:** 푸시/배지에 금액이 있어야 쓸모, PENDING 영구 무음은 CS 직행. 실시간은 이미 SSE로 도달하므로(develop) 여기서는 **content(금액)·PENDING 안내만** 보강하면 된다.
**의존:** 저장 신뢰성(아웃박스)은 [알림.md](알림.md) 3.11과 공유.
**리뷰 반영(PR #139):** "안내 1회"는 존재조회만으로는 배치·락 밖 웹훅 동시 경합에서 깨질 수 있어, 멱등 발행 전용 `notifications.dedup_key` UNIQUE 제약(`uk_notifications_dedup_key`)으로 보장한다(스키마 변경 — SA §4 v1.53). enum 값 추가는 마이그레이션이 없지만 이 컬럼은 DDL 변경이다. STUCK 안내는 "완료 뒤 뒤늦은 확인중" 순서를 막기 위해 발행 결정·저장을 결제 행 락(`findByIdForUpdate`) 아래 한 트랜잭션으로 원자화해 확정 조건부 UPDATE와 직렬화한다(실 MySQL 동시성 테스트로 검증). 유니크 충돌 흡수는 JPA가 유니크 위반도 `DataIntegrityViolationException`으로 번역하므로 제약 이름으로 dedup_key 위반만 골라 삼키고 나머지는 전파한다.
