## 3.1 예약 대기열 등록 및 자동 승급

### 구현 범위
- 슬롯이 이미 찬 경우 대기열 등록, 동일 사용자·동일 슬롯 중복 등록 차단.
- 대기열 본인 조회·취소.
- 예약 취소·거절·타임아웃으로 슬롯이 반환되면 FIFO 순서로 승급 제안. **제안이 나간 슬롯은 응답 대기 중에도 다른 사용자가 가로챌 수 없다**(아래 "승급 제안 중 슬롯 점유" 참고).
- 승급 제안 수락 시 `REQUESTED` 예약 생성, 제한 시간 내 미응답/거절 시 다음 대기자 승급.
- 승급 상태·이력·알림 저장, 승급 재처리·중복 승급 방지.

### 확정 정책 — 승급 제안 중 슬롯 점유 (STRICT)
- 승급 제안 유효 시간은 최대 **10분**이며, 슬롯 시작 `4시간 전`보다 늦게 만료될 수 없다. 남은 리드타임이 10분보다 짧으면 그 시각까지만 제안하고, 수락 가능한 시간이 전혀 없으면 제안을 만들지 않는다.
- 보호자가 제안을 수락하면 신규 예약을 `REQUESTED` 상태로 생성한다.
- `OFFERED` 대기열이 존재하는 동안 슬롯은 `RESERVED`를 유지한다. 따라서 일반 예약 생성 경로는 해당 슬롯을 점유할 수 없다.
- 제안 거절·만료 시 같은 트랜잭션에서 FIFO 다음 대기자에게 즉시 제안한다.
- 더 이상 `WAITING` 대기자가 없을 때만 슬롯을 `OPEN`으로 반환한다.
- 대기열 **등록·승급 제안·수락은 모두 슬롯 시작 시각 4시간 전까지** 허용한다. 기준 시각은 기존 예약 리드타임과 같이 `slot.startAt >= now + 4시간`이며, 4시간 이내에는 새 `OFFERED`를 만들지 않는다.
- 보호자 예약 취소는 기존처럼 슬롯 시작 2시간 전까지 허용한다. 승급 마감(시작 4시간 전) 이후 2시간 전까지 취소되어 기존 `WAITING`이 남아 있으면, 새 제안을 만들지 않고 해당 `WAITING`을 시스템 `CANCELED`로 종료한 뒤 슬롯을 `OPEN`으로 반환한다. 이 규칙은 대기열 때문에 기존 보호자 취소 가능 시간이 줄어드는 것을 막는다.
- 휴업·폐업 등 병원 운영 상태 변경으로 예약을 자동 취소할 때는 병원이 새 예약을 받을 수 없으므로 FIFO 승급을 만들지 않는다. `CONFIRMED` 예약에 연결된 슬롯뿐 아니라, 확정 예약 없이 이미 `OFFERED` 또는 `WAITING`만 남은 병원 소속 슬롯까지 조회해 활성 대기열을 시스템 `CANCELED`로 종료한 뒤 슬롯을 `OPEN`으로 반환한다.
- 회원 탈퇴 시 해당 회원의 `WAITING`·`OFFERED` 대기열은 모두 `CANCELED`로 종료한다. `OFFERED` 종료는 같은 트랜잭션에서 다음 FIFO 대기자 승급 또는 슬롯 `OPEN` 반환까지 처리한다. 승급 중 탈퇴·비활성 회원을 만나도 `CANCELED`로 건너뛰고 다음 활성 보호자를 찾는다.

슬롯 상태는 SA §5-3의 `OPEN`/`RESERVED` 둘만 유지한다. 별도 `HELD` 상태나 `reservation_slots.offered_to_waitlist_id` 컬럼을 추가하지 않는다. 승급 제안 생성·만료·수락은 슬롯의 기존 `@Version` 낙관적 락과 대기열의 `@Version`을 같은 트랜잭션에서 사용해 한 번만 성립시킨다.

### 1단계 데이터 모델
`reservation_waitlists`는 `member_id`, `slot_id`, `status`, `offered_at`, `offer_expires_at`, `responded_at`, `canceled_at`, 감사 시각, `version`을 저장한다.

- `UNIQUE(member_id, slot_id)`으로 동일 보호자·동일 슬롯 중복 등록을 DB에서도 차단한다.
- `(slot_id, status, created_at, id)` 인덱스로 FIFO 후보를 안정적으로 조회한다. 동률은 `id` 오름차순으로 결정한다.
- 테이블 DDL은 `ReservationWaitlistSchemaMigrationRunner`가 Hibernate 초기화 전에 생성·검증하며, `schema_migrations` 마커와 MySQL named lock으로 재실행·다중 인스턴스 실행을 막는다.

### API·만료 처리
- `POST /api/reservation-waitlists`: 마감(`RESERVED`) 슬롯의 대기열 등록. 슬롯 시작 4시간 이내에는 등록을 거부한다.
- `GET /api/reservation-waitlists`, `GET /api/reservation-waitlists/{waitlistId}`: 인증된 보호자는 자신의 대기열 목록·상세만 조회한다. 응답에는 상태와 제안·응답·취소 시각을 포함한다.
- `DELETE /api/reservation-waitlists/{waitlistId}`: 본인 대기열을 `WAITING → CANCELED`로 취소한다. `OFFERED` 이후에는 제안의 수락·거절 흐름을 보존하기 위해 취소를 허용하지 않는다.
- `POST /api/reservation-waitlists/{waitlistId}/accept`: 제안 수락. 요청 body의 `petId`, `paymentMethodId`는 수락 시점에 보호자 소유·활성 상태를 다시 검증하고, 병원의 현재 예약 가능 상태도 일반 예약과 동일하게 재검증한다. `OFFERED AND offer_expires_at > now AND slot.startAt >= now + 4시간` 조건을 만족하는 행만 조건부 UPDATE로 원자적으로 `ACCEPTED`로 전이한 뒤 새 `REQUESTED` 예약을 생성한다.
- `PATCH /api/reservation-waitlists/{waitlistId}/reject`: 제안 거절. `REJECTED` 전이 후 즉시 FIFO 다음 대기자에게 제안하고, 다음 대기자가 없을 때만 슬롯을 `OPEN`으로 반환한다.
- `ReservationWaitlistExpirationScheduler`는 기본 1분 주기로 만료된 `OFFERED`를 DB `LIMIT`으로 배치 조회한다. 다중 인스턴스 제어는 스케줄러가 호출하는 `ReservationWaitlistExpirationBatchService`의 MySQL named lock 경계에서 수행하므로, 잠금을 얻지 못한 인스턴스는 조회·상태 전이 없이 다음 주기에 재시도한다. 만료 건은 `EXPIRED` 전이 후 같은 슬롯의 다음 FIFO 대기자에게 즉시 제안한다.

제안·거절·만료는 대기열의 `@Version`을 flush해 상태 전이 충돌을 즉시 감지한 뒤에만 후속 슬롯 반환 처리를 진행한다. 수락 조건부 UPDATE는 `OFFERED AND offer_expires_at > now`와 함께 `version = version + 1`을 원자적으로 수행한다. 따라서 이미 `OFFERED`를 읽은 만료 배치·거절 요청은 flush에서 낙관적 락 충돌로 롤백되고, 수락 후 슬롯 반환이 뒤늦게 실행되지 않는다.

대기열 등록 INSERT는 `reservation_slots.status = RESERVED`를 조건으로 둔다. 같은 보호자가 종료(`CANCELED`·`REJECTED`·`EXPIRED`)한 대기열을 다시 등록하면 기존 행을 `WAITING`으로 되살리고 `created_at`을 새로 기록해 FIFO 맨 뒤로 보낸다. 슬롯 반환은 활성 대기열(`WAITING`·`OFFERED`)이 없을 때만 `RESERVED → OPEN` 조건부 UPDATE를 실행하고, 그 UPDATE가 0건이면 FIFO 승급을 한 번 더 시도한다. 등록과 반환이 경합해도 `OPEN` 슬롯에 활성 대기열이 남는 상태를 만들지 않는다. 실제 MySQL 다중 스레드 검증은 §5의 STRICT 테스트로 보장한다.

예약 취소·거절·만료는 슬롯의 `OPEN` 반환 또는 `OFFERED` 승급 중 하나가 실제로 성립한 경우에만 성공한다. 단, 승급 마감 뒤 보호자 취소는 기존 `WAITING`을 시스템 `CANCELED`로 종료한 뒤 `OPEN` 반환이 성립하면 성공한다. 최종 재시도 뒤에도 해당 결과가 성립하지 않으면 예외를 전파해 앞선 예약 상태 변경도 같은 트랜잭션에서 롤백한다.

### 상태 흐름
`ACCEPTED`·`EXPIRED`·`REJECTED`는 모두 `OFFERED`에서만 갈라지는 서로 다른 결과이며, 한쪽으로 전이한 뒤 다른 쪽으로 역전이하지 않는다.
```text
WAITING ──(본인 취소)──────────────→ CANCELED
   │
   │ (슬롯 반환 시 FIFO 승급 제안)
   ▼
OFFERED ──(수락)───────────────────→ ACCEPTED
   │
   ├──(제한 시간 내 미응답)────────→ EXPIRED
   └──(거절)───────────────────────→ REJECTED
```
`CANCELED`는 `WAITING`의 본인 취소, 회원 탈퇴, 승급 마감 뒤 보호자 취소에 따른 시스템 정리에서 도달한다. 휴업·폐업 같은 병원 운영 상태 변경에서는 `WAITING`과 `OFFERED` 모두 시스템 취소한다. 회원 탈퇴에서도 이미 `OFFERED`인 항목을 종료해 보호자 부재로 슬롯이 점유되지 않게 한다. `OFFERED` 상태의 일반 본인 취소는 이번 MVP에서 허용하지 않는다.

### 구현 근거
- 슬롯이 마감돼도 보호자가 예약 기회를 가질 수 있게 보완한다.
- 취소·거절·타임아웃으로 빈 슬롯을 방치하지 않고 다음 사용자에게 연결한다.
- 동시에 여러 사용자가 승급되는 상황을 슬롯의 기존 `@Version` 낙관적 락(SA §9-3, AGENTS 확정 결정)과 위 "승급 제안 중 슬롯 점유" 기본안으로 함께 방지한다 — `@Version`만으로는 일반 예약 생성이 제안 대기 중인 슬롯을 가로채는 것까지 막지 못한다.

### 남은 정책 결정
- 대기열 우선순위는 FIFO로 확정하며, 유료 우선권 등 다른 정책은 제외한다.
- 본인 취소(`CANCELED`)는 `WAITING`만 지원한다. `OFFERED` 상태의 본인 취소는 이번 MVP에서 제외한다.

### 제외 범위
- 대기열 우선순위 고도화, SSE·WebSocket 실시간 전송, 결제·환불, 병원 통계·관리자 화면, AI 예약 Tool Calling, 복잡한 보상·재예약 정책.

## 3.2 병원 측 확정 예약 취소

### 구현 범위
- 병원 본인 소유 예약 검증 후 `CONFIRMED` 예약의 병원 취소 API 제공, 취소 사유 필수.
- 병원 취소 전용 상태·이력 저장, 취소된 예약의 체크인·진료 시작·완료 차단.
- 보호자 대상 `RESERVATION_HOSPITAL_CANCELED` 알림 발행.
- 병원 취소 시 슬롯을 `OPEN`으로 반환. 대기열 승급 트리거 연결은 3.1 구현 범위로 분리한다.

병원 취소 상태·컬럼·이벤트·알림·API의 최종 계약은 SA v1.57 §4·§5-1·§5-3·§8-6을 따른다. 기존 `HOSPITAL_CANCELLED` 데이터는 Hibernate `ddl-auto=update`보다 먼저 실행되는 선행 마이그레이션에서 `HOSPITAL_CANCELED`로 변환하고, 애플리케이션 기동 후 사후 검증을 다시 수행한다.

### 상태 흐름
```text
CONFIRMED → HOSPITAL_CANCELED
```
`REQUESTED`·`REJECTED`·`CHECKED_IN`·`IN_TREATMENT`·`TREATMENT_COMPLETED`(실제 `ReservationStatus` enum 이름 — `IN_PROGRESS`·`COMPLETED`는 존재하지 않는다)는 이번 병원 취소 대상에서 제외한다.

### 구현 근거
- 병원 API에 승인·거절·체크인·진료 시작/완료가 있어도, 수의사 질병·응급수술 등으로 확정 예약을 중단하는 전이가 없으면 운영상 예약을 해소할 수 없다.
- 병원 취소와 보호자 취소를 구분해야 취소 주체·알림·통계·후속 대기열 처리를 정확히 구분한다.
- 상태 머신에 허용 전이를 추가하는 범위이며 결제·환불 정책을 새로 정의하지 않는다.

### 제외 범위
- 보호자 취소 정책 변경, 결제 취소·환불·보상·위약금, 취소 사유별 보상 정책, 확정 외 상태의 병원 취소, 대기열 승급 우선순위 정책.

## 4. 구현 의존성·순서

```text
(승인·거절 알림 = develop 완료)
병원 확정 예약 취소 → 슬롯 반환 이벤트
        ↓
대기열 자동 승급 → 승급 알림 + REQUESTED 예약 생성
```

권장 순서: 병원 확정 취소 → 대기열 등록·자동 승급. 대기열은 취소·거절·타임아웃을 트리거로 쓰므로 상태 변경·슬롯 반환 흐름을 먼저 안정화한다.

## 5. 검증 (STRICT: 상태 전이·슬롯 점유·낙관적 락)
- 기능: `CONFIRMED→HOSPITAL_CANCELED` 정상 전이, 타 병원·잘못된 상태 취소 차단, 취소·거절·타임아웃 후 FIFO 승급, 승급 수락 시 `REQUESTED` 생성, 승급 거절·만료 시 다음 대기자.
- 정합성: 승인·거절·취소 중복 요청 방지, 동일 이벤트 재처리 시 예약·이력·알림 중복 생성 방지, 동시 승급에도 1명만 승급, **수락 조건부 UPDATE가 version 증가까지 포함해 한 건만 성공하고 그 성공 트랜잭션만 `REQUESTED`를 생성함**, **수락과 만료·거절 경합에서 한 전이와 한 후속 처리만 성립함**, **등록과 슬롯 반환 경합에서도 `OPEN` 슬롯에 활성 대기열이 남지 않음**, **승급 제안 응답 대기 중인 슬롯을 일반 예약 생성이 가로채지 못함**, **승급 마감 뒤 2시간 취소에서도 `WAITING`이 시스템 종료되고 슬롯이 `OPEN`으로 반환됨**, **휴업·폐업 자동 취소가 `CONFIRMED` 예약 유무와 무관하게 활성 대기열을 종료한 뒤 슬롯을 반환함**, 병원 취소 이후 체크인·진료 차단.
- 실행: 대기열 동시성은 실제 MySQL Level 3, 로컬 기동 Level 5, 실제 HTTP Level 6. 판정 PASS만 완료 근거.

## 6. 완료 기준
- 대기열 등록·자동 승급, 병원 확정 취소의 포함 범위가 구현된다.
- 확정 정책(10분 제안, 수락 시 `REQUESTED`, `OFFERED` 중 `RESERVED` 유지)이 이 델타 문서에 반영된다.
- 상태 전이·권한·멱등성·동시성 테스트 통과, 새 상태/전이가 SA §5 상태 머신에 반영된다.
- 병원취소·대기열 알림의 NotificationType·발행 방식이 알림 도메인과 합의돼 반영된다.
- 제외 범위가 섞이지 않는다. PR 리뷰 완료.
