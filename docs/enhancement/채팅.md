# 고도화 — 채팅·실시간 (담당: @maschemy)

> 이 문서는 동결된 MVP 정본에 대한 **델타(변경분)**다. 아래 `전제` 절에 적힌 문서만 함께 읽는다. 채팅 설계 정본은 구현 PR #151에서 승격한 SA §8-9·§9-12이며, 이 문서는 구현 범위·완료 기준을 유지한다.

- **담당:** @maschemy
- **관련 이슈:** #147

## 전송 방식 (확정)

- **알림 = SSE**: 기존 `NotificationPusher`·`SseNotificationPusher` 및 커밋 후 전송 계약을 유지한다.
- **채팅 = native WebSocket + STOMP**: SockJS fallback은 포함하지 않는다. 메시지는 저장 커밋 뒤에만 WebSocket으로 전달하고 롤백 메시지는 전달하지 않는다.
- **CONNECT 인증과 세션 무효화**: 전용 `/ws/chat` HTTP Upgrade 경로만 CONNECT까지 도달하도록 허용한다. JWT는 URL 쿼리 파라미터가 아니라 STOMP CONNECT `Authorization: Bearer <accessToken>` 헤더로 전달한다. `ChannelInterceptor`가 검증·인증 주체 등록을 수행하며 미인증 CONNECT는 거부한다. CONNECT 뒤에도 세션별 principal·Access Token `jti`·만료 시각(원문 JWT는 보관하지 않음)을 기준으로 `SEND`·`SUBSCRIBE`·heartbeat 및 채팅 `MESSAGE` 전달 직전에 재검증한다. 로그아웃 토큰 블랙리스트, 탈퇴 회원 블랙리스트 또는 만료가 확인되면 기존 연결은 이후 송신·신규 구독·기존 구독 수신이 모두 차단된다.
- **구독 인가**: 서버가 인증 주체와 예약 관계를 확인한다. 클라이언트가 전달한 `memberId`·`hospitalId`나 구독 경로만으로 권한을 부여하지 않는다.
- **broker 범위**: 단일 애플리케이션 인스턴스 Spring SimpleBroker를 기준으로 한다. 다중 인스턴스 Redis pub/sub·외부 STOMP broker fan-out은 후속 고도화다. 재연결 누락분은 아래 인증된 채팅 조회 API로 복구하며, 이 계약은 SA §8-9·§9-12에 반영됐다.

## 3.1 병원↔회원 채팅 — 신규 (예약당 스레드)

**범위:**

- 예약 1건당 1스레드이며, 상시 병원-회원 1:1 채팅은 제공하지 않는다.
- 회원은 본인이 보호자인 예약 스레드만, 병원 스태프는 자신이 소속된 병원의 예약 스레드만 접근한다. 병원 측 접근·읽음은 병원 단위로 공유한다.
- 발신자 정보는 인증 주체에서 결정한다. 회원 메시지는 회원 `memberId`, 병원 메시지는 실제 발신 스태프 `memberId`를 감사용으로 저장한다. 화면 표시명은 서버가 해석한다. 보호자 발신은 보호자 nickname, 병원 발신은 병원명으로 표시하며 스태프 개인 nickname은 기본 노출하지 않는다.
- 메시지는 텍스트만 허용하며 최대 1,000자다. 전송 요청은 UUID `clientMessageId`를 함께 보내며 서버는 `(reservation_id, member_id, client_message_id)` UNIQUE로 같은 재시도를 한 건으로 처리하고 개인 ACK로 `messageId`를 돌려준다. 이미지·파일 첨부, 메시지 수정·삭제, 신고·차단, 자동응답·봇, 타이핑 인디케이터는 제외한다.
- `REQUESTED`, `CONFIRMED`, `NO_SHOW_PENDING`, `CHECKED_IN`, `IN_TREATMENT`에서만 신규 메시지 송수신을 허용한다. `REJECTED`, `CANCELED`, `HOSPITAL_CANCELED`, `TREATMENT_COMPLETED`, `NO_SHOW`는 기존 메시지 조회만 가능한 읽기 전용 상태다.
- 메시지는 생성일부터 1년 보존하고, 이후 하드 삭제 배치로 제거한다. 법적 보존 의무가 확인되면 보존 기간과 삭제 방식은 별도 정책 변경 대상으로 둔다.
- 재연결 복구용 조회는 아래 `GET /api/reservations/{reservationId}/chat/messages` 계약을 따르며, 예약 참여자만 `afterMessageId` 커서로 누락분을 조회한다.

### 재연결 조회 API 계약

`GET /api/reservations/{reservationId}/chat/messages?afterMessageId={messageId}&size={n}`

- 접근자는 예약 보호자 또는 서버가 해석한 해당 병원 스태프여야 한다. 요청의 `memberId`, `hospitalId` 값은 받거나 신뢰하지 않는다.
- `afterMessageId`는 선택값이다. 제공되면 서버는 해당 메시지가 같은 `reservationId` 스레드의 메시지인지 먼저 검증하고, 그 뒤 메시지를 `createdAt ASC, id ASC` 순서로 조회한다.
- `size`는 1~100이다. 응답은 `{ messages, nextAfterMessageId, hasNext }`이며, `hasNext`는 이번 페이지 뒤에 메시지가 더 있는지를 뜻한다. `hasNext=true`일 때만 `nextAfterMessageId`는 이번 페이지의 마지막 메시지 ID이고, 그 외에는 `null`이다.
- 각 `messages` 항목은 `messageId`, `senderType`, `content`, `createdAt`, 화면 표시용 `senderName`, 발신자가 자신의 재전송 결과를 식별하는 `clientMessageId`를 제공한다. 보호자 발신의 `senderName`은 서버가 해석한 보호자 nickname이고, 병원 발신의 `senderName`은 병원명만 사용하며 스태프 nickname이나 실제 staff `memberId`를 노출하지 않는다. `clientMessageId`는 UUID 재전송 키일 뿐 회원·병원 식별자는 아니다. 보존 기간 중 보호자가 탈퇴해 nickname을 더 이상 조회할 수 있으면 과거 메시지는 삭제하지 않고 `탈퇴한 보호자`로 표시한다.

**제외:** 이 문서는 구현 범위와 계약만 다루며, 채팅 Java 코드·WebSocket 설정·STOMP Controller·`chat_messages` 테이블·Redis pub/sub·테스트 구현은 포함하지 않는다.

## 3.2 WebSocket 실시간 전송 — 신규 (채팅 전용)

- STOMP over native WebSocket으로 예약 스레드 구독자에게 메시지를 전달한다.
- 채팅 저장 트랜잭션 커밋 후 스레드 구독자에게 전달한다(**AFTER_COMMIT**). 롤백된 메시지는 전송하지 않는다.
- 알림 전송에는 관여하지 않는다. 예약·결제 알림은 SSE를 그대로 사용한다.
- heartbeat와 재연결 동작의 세부값은 구현 PR에서 정하되, 유실 메시지 복구는 위에서 정의한 채팅 조회 API를 사용한다.
- Spring SimpleBroker는 SUBSCRIBE receipt를 발급하지 않으므로, 클라이언트는 topic 구독 직후 `/subscription-ready` 제어 요청을 보내고 topic으로 되돌아온 `SUBSCRIPTION_READY` 프레임을 실제 수신 증거로 삼아 커서 조회를 한 번 더 수행한다.
- **읽음 처리는 그 최종 커서 복구가 성공한 뒤에만 보낸다.** `SUBSCRIBE` 호출 자체는 broker 구독 활성화를 보장하지 않으므로, 그 전에 읽음을 보내면 최초 조회와 구독 사이에 저장된 메시지가 화면에 병합되기 전에 읽음이 된다. 최종 복구가 실패하면 읽음을 보류하고 다음 재연결에서 다시 복구한다 — 못 본 메시지를 읽음 처리하는 것보다 미읽음으로 남는 편이 안전하다.
