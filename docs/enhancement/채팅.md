## 전송 방식 결정 (확정: 2번 안)
- **알림 = SSE**(이미 구축, 단방향 확정), **채팅 = WebSocket**(양방향 신규). 근거는 각 도구의 적합성 — 채팅은 낮은 지연·양방향이 필요.
- 이미 있는 SSE를 버리지 않는다. `NotificationPusher` 추상화가 있어, 훗날 하나로 합치고 싶으면 `WebSocketNotificationPusher` 교체로 가능(지금은 안 합침).

## 3.1 병원↔회원 채팅 — 신규 (예약당 스레드)
**범위:**
- `chat_messages` **별도 테이블**(sender_type, hospital_id, member_id, reservation_id, body, created_at, read_at). 알림 테이블에 본문을 섞지 않는다.
- **예약당 1스레드** — 예약 맥락 안에서만 대화, 진료 종료 후 읽기전용.
- 스레드 조회(페이지네이션), 메시지 전송, 읽음 처리, 안읽은 메시지 수.
- 새 메시지 도착 → (a) WebSocket으로 스레드에 실시간 전달(3.2), (b) 상대에게 **알림은 기존 경로**(`create()` → SSE/이메일)로 발행.

**결정(확정):**
- 범위 = **예약당 스레드**(상시 1:1 아님) — 권한·보존 범위가 명확.
- 병원 측 수신·읽음 = **병원 단위 공유**(스태프 누구나 열람, 개인 fan-out 없음).

**근거:** 알림 content(500자)·읽음모델·보존정책과 채팅 요구가 달라 분리한다. 예약 스코프라 "누가 누구와 왜" 대화하는지 컨텍스트가 자명하다.
**제외:** 이미지·파일 첨부, 메시지 편집/삭제, 신고·차단, 자동응답/봇, 타이핑 인디케이터, 상시 1:1 스레드.

## 3.2 WebSocket 실시간 전송 — 신규 (채팅 전용)
**범위:**
- STOMP over WebSocket. **JWT 핸드셰이크 인증**, 구독 인가(본인이 속한 예약 스레드만 — 회원은 자기 예약, 병원 스태프는 자병원 예약).
- 채팅 저장 커밋 후 스레드 구독자에게 전달(**AFTER_COMMIT** — 롤백 시 유령 메시지 금지).
- heartbeat, 재연결 시 스레드 조회 API로 유실분 복구.
- **알림 전송에는 관여하지 않는다** — 알림은 SSE 그대로.

**근거:** 채팅은 양방향·저지연이 사실상 필수. SA 부록 A의 "양방향 채널은 채팅 도입 시 재논의"를 WebSocket으로 확정(구현 시 SA·AGENTS에 반영).
**제외:** 다중 인스턴스 팬아웃(Redis pub/sub 브로커) — **SSE·WebSocket 공통 숙제**라 수평 확장 시 함께 도입. 모바일 푸시(FCM/APNs), 읽음 실시간 동기.

## 5. 검증 (STRICT: 스키마·동시성)
- 채팅: 예약 소유자/자병원 외 구독·전송 차단, 병원 단위 읽음 공유, 안읽은 수 정합성. Level 3 MySQL.
- WebSocket: 미인증 핸드셰이크 차단, AFTER_COMMIT 전송(롤백 시 미전송)·재연결 유실 복구를 통합 테스트로 확인. 판정 PASS만 완료 근거.

## 6. 완료 기준
- chat_messages·WebSocket(채팅) 전송이 구현되고, SA 부록 A의 양방향 채널 확정(WebSocket)이 정본에 반영된다.
- JWT 핸드셰이크·구독 인가가 적용되고 유령 메시지가 없음이 검증된다. **알림은 SSE 유지**(중복 전송 없음).
- 폴링 병행(유실 복구)이 유지된다. 제외 범위 미혼입, PR 리뷰 완료.
