# 고도화 — 채팅·실시간 (담당: @maschemy)

> 이 문서는 동결된 MVP 정본에 대한 **델타(변경분)**다. 아래 `전제` 절에 적힌 문서만 함께 읽으며, 이 문서의 채팅 정책은 구현 PR의 기준으로 사용한다. SA 채팅 절 승격은 실제 채팅 구현 PR에서 수행한다.

## 메타

- **상태:** 설계중
- **담당:** @maschemy
- **관련 이슈:** #147
- **전제(동결 baseline — 이 절만 함께 읽는다):** SA §9-8(알림=SSE), SA §6(인증·인가), SA §4 reservations, 코드컨벤션
- **override 범위:** 병원↔회원 예약당 채팅, native WebSocket + STOMP 전송, CONNECT 인증·구독 인가, 상태별 송수신·읽기, 보존, AFTER_COMMIT, 재연결 복구 계약. 이 범위의 설계 정본은 이 델타이며, 구현 PR에서 SA 채팅 절로 승격한다.
- **구현 범위 델타:** 병원↔회원 예약당 채팅과 native WebSocket + STOMP 전송. 알림 SSE 계약은 동결 SA §9-8을 따른다.
- **건드리지 않는 것:** 예약·결제 알림의 저장·SSE 전송·AFTER_COMMIT 구조는 변경하지 않는다. WebSocket은 채팅 전용이며 알림을 WebSocket으로 이전하지 않는다.

## 전송 방식 (확정)

- **알림 = SSE**: 기존 `NotificationPusher`·`SseNotificationPusher` 및 커밋 후 전송 계약을 유지한다.
- **채팅 = native WebSocket + STOMP**: SockJS fallback은 포함하지 않는다. 메시지는 저장 커밋 뒤에만 WebSocket으로 전달하고 롤백 메시지는 전달하지 않는다.
- **CONNECT 인증**: 전용 `/ws/chat` HTTP Upgrade 경로만 CONNECT까지 도달하도록 허용한다. JWT는 URL 쿼리 파라미터가 아니라 STOMP CONNECT `Authorization: Bearer <accessToken>` 헤더로 전달한다. `ChannelInterceptor`가 검증·인증 주체 등록을 수행하며 미인증 CONNECT는 거부한다.
- **구독 인가**: 서버가 인증 주체와 예약 관계를 확인한다. 클라이언트가 전달한 `memberId`·`hospitalId`나 구독 경로만으로 권한을 부여하지 않는다.
- **broker 범위**: 단일 애플리케이션 인스턴스 Spring SimpleBroker를 기준으로 한다. 다중 인스턴스 Redis pub/sub·외부 STOMP broker fan-out은 후속 고도화다. 재연결 누락분은 구현 PR에서 승격할 인증된 채팅 조회 API로 복구한다.

## 3.1 병원↔회원 채팅 — 신규 (예약당 스레드)

**범위:**

- 예약 1건당 1스레드이며, 상시 병원-회원 1:1 채팅은 제공하지 않는다.
- 회원은 본인이 보호자인 예약 스레드만, 병원 스태프는 자신이 소속된 병원의 예약 스레드만 접근한다. 병원 측 접근·읽음은 병원 단위로 공유한다.
- 발신자 정보는 인증 주체에서 결정한다. 회원 메시지는 회원 `memberId`, 병원 메시지는 실제 발신 스태프 `memberId`를 감사용으로 저장한다. 보호자 화면에는 병원 발신자를 병원명으로 표시하고 스태프 개인 nickname은 기본 노출하지 않는다.
- 메시지는 텍스트만 허용하며 최대 1,000자다. 이미지·파일 첨부, 메시지 수정·삭제, 신고·차단, 자동응답·봇, 타이핑 인디케이터는 제외한다.
- `REQUESTED`, `CONFIRMED`, `NO_SHOW_PENDING`, `CHECKED_IN`, `IN_TREATMENT`에서만 신규 메시지 송수신을 허용한다. `REJECTED`, `CANCELED`, `TREATMENT_COMPLETED`, `NO_SHOW`는 기존 메시지 조회만 가능한 읽기 전용 상태다.
- 메시지는 생성일부터 1년 보존하고, 이후 하드 삭제 배치로 제거한다. 법적 보존 의무가 확인되면 보존 기간과 삭제 방식은 별도 정책 변경 대상으로 둔다.
- 재연결 복구용 조회는 구현 PR에서 SA 채팅 절로 승격할 `GET /api/reservations/{reservationId}/chat/messages` 계약을 따르며, 예약 참여자만 `afterMessageId` 커서로 누락분을 조회한다.

**제외:** 이 문서는 구현 범위와 계약만 다루며, 채팅 Java 코드·WebSocket 설정·STOMP Controller·`chat_messages` 테이블·Redis pub/sub·테스트 구현은 포함하지 않는다.

## 3.2 WebSocket 실시간 전송 — 신규 (채팅 전용)

- STOMP over native WebSocket으로 예약 스레드 구독자에게 메시지를 전달한다.
- 채팅 저장 트랜잭션 커밋 후 스레드 구독자에게 전달한다(**AFTER_COMMIT**). 롤백된 메시지는 전송하지 않는다.
- 알림 전송에는 관여하지 않는다. 예약·결제 알림은 SSE를 그대로 사용한다.
- heartbeat와 재연결 동작의 세부값은 구현 PR에서 정하되, 유실 메시지 복구는 위에서 정의한 채팅 조회 API를 사용한다.

## 5. 검증 (STRICT: 스키마·동시성)

- 채팅 구현 PR은 예약 소유자·자병원 외 구독·전송 차단, 병원 단위 접근·읽음 공유, 메시지 가능 상태와 1,000자 제한을 Level 3 MySQL로 검증한다.
- WebSocket 구현 PR은 미인증 CONNECT 차단, 서버 구독 인가, AFTER_COMMIT 전송(롤백 시 미전송), 재연결 유실 복구를 통합 테스트로 확인한다. 판정 PASS만 완료 근거다.
