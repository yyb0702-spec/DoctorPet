## 3.10 수신자 모델 확장 — 병원 단위 공유 (홀 + 채팅 전제)
**범위:** `notifications`에 수신자 타입 도입(MEMBER | HOSPITAL). 병원향 알림은 `recipient_type=HOSPITAL, recipient_id=hospitalId`로 저장, **읽음도 병원 단위 1건**. SSE 레지스트리(`SseEmitterRegistry`)도 `memberId` 키라 병원 실시간 수신 경로가 없으므로, 이 확장이 병원 SSE 수신도 함께 연다.
**결정(확정):** 병원 수신·읽음 = **병원 단위 공유**(스태프 누구나 열람, 개인 fan-out·읽음 복제 없음). 스태프 계정 관리가 범위 밖(AGENTS)인 것과 정합.
**근거:** 현재 수신자는 항상 보호자(`member_id`)라 병원 수신 경로가 0. **채팅(양방향)의 스키마 전제.**
**구현(#141, SA §4·§8-8 승격 반영):**
- `recipient_type`(MEMBER|HOSPITAL)+`recipient_id`를 정본으로 추가. 설계 판단 = **member_id 유지+일반화 병행** — `member_id`는 nullable로 완화해 기존 행 백필·하위호환용으로만 남기고(HOSPITAL 행은 NULL), 신규 로직·인덱스는 recipient_*를 쓴다(ddl-auto=update로 컬럼 drop이 위험하고 #134 데이터·경로 회귀를 피하기 위함).
- 마이그레이션은 이 저장소 관례(Flyway 없이 `schema_migrations` 마커 + `get_lock`)를 따른다 — 기존 행을 (MEMBER, member_id)로 백필 → recipient_* NOT NULL → member_id nullable 완화 → 인덱스를 `idx_notifications_recipient_created/read`로 교체. `NotificationRecipientMigrationRunner`.
- 발행부 무변경: `NotificationService.create(memberId,...)`는 `(MEMBER, memberId)` 위임 오버로드로 유지. 병원향은 `create(HOSPITAL, hospitalId,...)`.
- 조회·읽음·미읽음 수·모두 읽음(#134)을 호출자 recipient 기준으로 확장. 스태프→hospitalId는 기존 수단 `MemberService.getMyInfo`로 해석(`NotificationRecipientResolver`). 회원↔병원 격리.
- **범위 판단(사용자 확인) = SSE 병원 라우팅은 후속 PR로 분리.** #141은 저장·조회·인가 모델까지 포함하고, HOSPITAL 알림의 SSE 오배달만 방지했다(`SseNotificationPusher`가 MEMBER만 전송, HOSPITAL은 no-op).
- **후속 PR ① = 병원 수신 SSE 전달 경로(transport, 구현 완료).** `SseNotificationPusher.push(HOSPITAL, hospitalId, ...)`가 발송 시점의 현재 소속 스태프 memberId를 `MemberService.findActiveHospitalStaffMemberIds`로 받아 각 스태프의 모든 연결로 같은 payload를 전달한다. 저장은 병원 단위 1건·읽음 공유 그대로이고 fan-out은 전달 계층일 뿐이다 — 스태프별 알림 행·개별 읽음은 만들지 않는다. `SseEmitterRegistry` 키와 티켓 발급은 계속 개별 memberId이며(병원을 연결 키로 쓰지 않는다) 회원당 연결 상한 5도 그대로다. 탈퇴·소속 해제 스태프의 잔존 연결에는 보내지 않는다. 수신자 유형 해석은 exhaustive `switch` 식이라 `NotificationRecipientType`에 상수가 추가되면 컴파일 에러로 잡힌다(새 유형이 무전송으로 조용히 빠지는 것을 막는다). 대상별 전송은 개별 격리(`try/catch`)라 한 스태프의 전송 실패가 나머지 스태프의 전달을 삼키지 않는다. 프론트는 `StaffLayout`이 기존 `NotificationBell`을 그대로 재사용하고, 리소스 이동 경로는 벨이 로그인 회원 `role`로 직접 고른다(레이아웃 주입 없음 — 스태프가 보호자 `AppLayout` 화면에 서는 조합에서도 보호자 경로로 떨어지지 않는다).
- **후속 PR ② = 병원향 알림 발행 지점(구현 완료, #166).** ①이 전달 경로만 열어 병원 수신 알림 행이 실제 시나리오에서 생성되지 않던 갭을 메웠다. ⓐ 발행 지점은 `ReservationApplicationService`의 **`request()`·`requestFromWaitlist()` 두 곳 모두**다 — 둘 다 병원이 확인해야 할 새 `REQUESTED` 예약을 만들므로, 대기열 출신만 조용하면 병원 관점의 일관성 구멍이 된다. 알림 도메인이 정의한 병원향 유형 **`RESERVATION_REQUESTED`**(문구 "새로운 예약 요청이 접수되었습니다." — 병원 시점 평서문, 동적 PII 미포함, 상세는 `resourceId`로 연결)를 쓰고, 예약 도메인 포트 `ReservationNotificationPublisher.publishReservationRequested(hospitalId, reservationId)` → 어댑터 `StoringReservationNotificationPublisher`가 `create(HOSPITAL, hospitalId, ...)`로 저장한다. 저장은 **예약 생성과 같은 트랜잭션**이라 전이가 롤백되면 알림도 남지 않고(기존 `publishConfirmed`와 동일 계약), 실시간 전송은 AFTER_COMMIT 리스너가 자동으로 잇는다. ⓑ `members(hospital_id, role)` 조회 인덱스를 엔티티 `@Index`(`idx_members_hospital_role`) + `schema_migrations` 마커 러너(`MemberHospitalStaffIndexMigrationRunner`)로 넣었다 — fan-out 대상 조회가 members 풀스캔(`EXPLAIN type=ALL`)이었고 알림 1건마다 커밋한 요청 스레드에서 돌기 때문이다(적용 후 실측 `type=ref`, `key=idx_members_hospital_role`). MySQL `notifications.type`이 ENUM이던 동안에는 새 값마다 확장 러너가 필요했고 실행 순서까지 강제해야 했다(`@DependsOn`) — 순서가 뒤집히면 앞선 러너가 컬럼을 자기 목표 ENUM으로 되돌려 방금 추가한 값이 사라졌다. **이 관례는 #176에서 원인을 없애 폐기했다**(아래 3.12). ⓒ Level 6 E2E PASS — 실제 HTTP 예약 요청 1건으로 같은 병원 스태프 A·B가 SSE 수신, 타 병원 스태프 C는 미수신. **정본 승격 완료** — 새 유형·members 인덱스·두 마커 키를 SA §4(v1.60)와 DB설계 경량본에 반영했다(구현 PR에서 승격하는 관례, v1.53·v1.56 선례). **스태프 벨 클릭 이동은 목록 `/staff/reservations`**(병원 예약 단건 조회 API 부재, 아래 "스태프 알림 이동 경로" 참조).
- **알려진 한계(①의 범위 밖, 후속):** ⓐ 인메모리 레지스트리라 전달은 이 인스턴스에 연결된 스태프까지만 도달한다(단일 인스턴스 기준) — 다중 인스턴스 fan-out(Redis pub/sub)은 후속이고, 미도달분은 목록 폴링으로 복구된다. ⓑ 로그아웃·강제 세션 폐기 시 그 회원의 SSE 연결을 끊는 장치가 없어(티켓은 접속 시 1회만 검증) 최대 emitter 타임아웃 30분까지 연결이 살아 있다 — MEMBER 경로부터 있던 성질이지만 병원 수신이 열리면서 노출 범위가 병원 단위 알림으로 넓어졌다. ⓒ 전달은 커밋한 요청 스레드에서 동기 수행하므로 스태프 수 × 탭 수만큼 blocking write가 응답 시간에 올라탄다(`SseEmitterRegistry` heartbeat 주석의 한계와 같은 성질). ①까지는 프로덕션 호출자가 없어 이 비용을 실제로 내는 경로가 없었으나, ②(#166)부터는 **보호자의 예약 요청 API(`POST /api/reservations`)가 그 비용을 낸다** — 대상 조회는 `idx_members_hospital_role`로 완화했지만 스태프 연결별 write는 남는다. 병원당 스태프·탭 수가 많아지면 리스너를 `@Async` 전용 실행기로 옮기는 것이 다중 인스턴스 fan-out과 함께 해소할 후속 범위다(전송 실패는 이미 리스너에서 삼켜 저장·응답에 전파하지 않는다). ⓑ·ⓒ는 다중 인스턴스 확장 때 함께 해소한다.
- **스태프 알림 이동 경로:** 예약 리소스 알림도 병원 스태프는 **목록(`/staff/reservations`)**으로 보낸다. `StaffReservationDetailPage`가 목록에서 넘겨준 `location.state` 없이는 열리지 않기 때문(병원 예약 단건 조회 API가 SA §8-6에 없다) — 상세 URL로 보내면 즉시 목록으로 리다이렉트되는 죽은 링크가 된다. 단건 조회 API가 생기면 `NotificationBell`의 역할별 경로 표에 상세 함수를 채운다. 역할이 아직 확정되지 않은 동안(내 정보 조회 로딩·실패)에는 **어느 쪽 경로도 고르지 않고 이동을 보류**한다 — 보호자를 기본값으로 두면 그 창에 스태프가 알림을 눌렀을 때 보호자 경로로 샌다. `/staff/*` 안쪽은 `StaffRoute`가 역할 확인 전 레이아웃을 렌더하지 않아 안전하지만, 공개·보호자 라우트의 `AppLayout`은 인증만으로 벨을 렌더하므로 실제로 도달 가능한 경합이다(PR #162 리뷰 P2). 읽음 처리는 역할과 무관하므로 보류하지 않는다.
- 검증: Level 3 실제 MySQL — 백필·DDL·인덱스(`NotificationRecipientMigrationIntegrationTest`), 병원 단위 읽음 공유·회원↔병원 격리(`NotificationRecipientIntegrationTest`), 다중 스태프 동시 읽음 멱등(`NotificationMarkReadConcurrencyIntegrationTest`), #134 회원 회귀 없음. 후속 ① 전달 경로는 `NotificationHospitalFanOutIntegrationTest`(현재 소속만 수신·**연결별 payload 실제 도달**·커밋 후 전송·전송 실패 대상별 격리)와 `SseNotificationPusherTest`. 후속 ② 발행 지점은 `ReservationRequestHospitalNotificationIntegrationTest`(두 요청 경로의 병원 수신 저장·예약 롤백 시 알림 미생성), `MemberHospitalStaffIndexMigrationIntegrationTest`(인덱스 생성·`EXPLAIN` 적용 가능성·드리프트 교체·멱등), `NotificationReservationRequestedTypeMigrationIntegrationTest`(ENUM 확장 멱등·오타 값 정정 선행 강제). 연결별 도달 검증은 emitter 미전송 버퍼를 읽어 확인한다 — 호출 횟수만 세면 "회원의 첫 연결에만 보내는" 구현도 통과하기 때문이다.

## 3.9 채널 확장(이메일) + 수신 설정 (고도화 / 정책, 구현 완료)
**범위:** `NotificationChannel` 추상화(인앱 저장 · SSE(존재) · **이메일** 추가). 기존 `mail` 게이트웨이 재사용해 예약 승인·결제 결과 이메일 발송. 유형별 수신 on/off **스키마 선반영**.
**결정(기본):** 이메일은 예약승인·결제결과만, 수신설정은 스키마만 선반영(소급이 어려움). **WebSocket은 여기 아님**(채팅 전용).
**근거:** SSE는 앱이 연결돼 있을 때만 도달 → 앱을 닫으면 못 본다. 이메일이 그 공백을 메운다.

**구현(SA §9-8·§4 승격 반영):**
- `NotificationChannel`(+`NotificationChannelType`) 추상화를 두고 커밋 후 리스너(`NotificationPushListener`)가 등록된 모든 채널에 넘긴다. **인앱 저장은 채널이 아니다** — 저장이 알림의 원본이라 끌 수 있는 대상이 아니고(끄면 알림 자체가 없다), 채널은 저장 커밋 이후 추가로 나가는 전달 수단만 열거한다(REALTIME·EMAIL). 문서의 "인앱 저장 · SSE · 이메일" 열거와 다른 지점이라 근거를 남긴다.
- **SSE 인프라는 건드리지 않았다.** `RealtimeNotificationChannel`이 기존 `NotificationPusher`에 그대로 위임하는 어댑터다(`SseNotificationPusher`·`SseEmitterRegistry`·티켓 인증·heartbeat·연결 상한 무변경) — 알림 실시간=SSE는 재논의 금지 결정이므로(AGENTS) 추상화를 넣으면서 그 계약을 손대지 않기 위한 선택이다. 그래서 `NotificationPusher.push`와 `NotificationChannel.deliver`의 시그니처가 겹치는데, 의도된 중복이다(새 채널이 SSE 인프라 인터페이스를 구현하도록 강요하지 않는다).
- 전달 실패 격리 단위를 리스너 전체 → **채널 단위**로 좁혔다. 이메일(SMTP 장애)이 SSE 전달을 막거나 그 반대가 되면, 저장은 됐는데 도달 가능한 채널까지 함께 잃는다.
- `NotificationCreatedEvent`에 알림 유형(enum)을 실었다 — payload의 `type`은 문자열이라 채널이 대상 여부를 판단하려면 다시 파싱해야 하고, 그러면 알 수 없는 값에서 조용히 깨진다.
- `EmailNotificationChannel` — **회원(MEMBER) 수신의 `RESERVATION_CONFIRMED`·`PAYMENT_RESULT`만** 보낸다. `PAYMENT_PENDING`은 결과가 아니라 중간 안내라 제외했다. 병원(HOSPITAL) 수신은 대표 메일·스태프 개인 메일 중 무엇으로 보낼지가 정해지지 않아 범위 밖이며 조용히 no-op한다. 주소는 **인증된(`email_verified`) 활성 회원의 이메일만** 쓴다(`MemberService.findActiveVerifiedEmail` 신설 — 다른 도메인은 Member Repository를 직접 참조하지 않는 가드레일). 미인증 주소로 보내면 그 주소의 실제 소유자에게 진료·결제 정보가 새어 나간다. 본문은 저장된 `content` 스냅샷을 그대로 쓴다(문구의 동적 PII 미포함 원칙을 채널이 깨지 않게).
- 운영 스위치 `notification.email.enabled`(기본 true) — false면 채널 빈 자체가 등록되지 않아 이메일만 빠지고 인앱 저장·SSE는 그대로다.
- **중복 발송 대책 = 저장 멱등 승계.** 채널은 저장된 알림 1행당 1회 호출되므로, 멱등 발행(`uk_notifications_dedup_key`)은 행이 1건이라 메일도 1통이고, 일반 발행에서 행이 2건이면 서로 다른 사건이라(결제 완료 뒤 환불된 `PAYMENT_RESULT`) 2통이 맞다. 그래서 채널에 별도 중복 방지 장치를 두지 않는다 — 이 판단이 기존 `dedup_key` 계약과의 관계다.
- **트랜잭션 안에서 외부 호출을 하지 않는다.** 발송은 SSE와 같은 AFTER_COMMIT 리스너 경로다(SA §9-8 불변식). 롤백된 알림 생성은 저장도 메일도 없다.
- **수신 설정 `notification_preferences`** — (회원 · 유형 · 채널)당 1행 + `UNIQUE`. **행이 없으면 수신이 기본**이라 소급 생성 없이 도입된다. 테이블·UNIQUE는 `ddl-auto=update`가 만든다(신규·기존 DB 실측 확인). 두 enum 컬럼은 이슈 #176의 교훈대로 처음부터 `@JdbcTypeCode(SqlTypes.VARCHAR)`로 못박았다.
- **CHECK 제약(CI가 잡아낸 후속).** 애너테이션만으로는 부족했다 — Hibernate는 VARCHAR enum 컬럼에 값 열거 CHECK 제약을 함께 만든다. `notifications`는 오래된 테이블이라 그 제약이 없지만(`ddl-auto=update`는 기존 테이블에 CHECK를 추가하지 않는다) **이 테이블은 신규라 모든 DB에서 새로 생성돼 예외 없이 붙는다** — 남겨두면 `NotificationType`에 값 하나를 추가할 때마다 이 테이블에도 DDL이 필요해져 #176이 없앤 부채가 새 테이블로 되살아난다. `NotificationPreferenceCheckConstraintMigrationRunner`(마커 `notification_preference_check_drop_v1`)가 부팅 시 드롭하고 남아 있으면 부팅을 중단시킨다. **선행(pre-JPA)이 아니라 JPA 초기화 이후에 도는 `ApplicationRunner`**인 것이 중요하다 — 제약을 만드는 주체가 Hibernate의 테이블 생성이라 그보다 먼저 돌면 드롭할 대상이 없다. 드롭 SQL은 `NotificationEnumCheckConstraints`로 #176 러너와 공유한다.
- **범위 판단(문서와의 차이) = 이메일 채널이 이 설정을 읽는다.** 문서 결정은 "스키마만 선반영"이지만, 읽는 곳이 없으면 엔티티·리포지토리가 죽은 코드가 되고 나중에 설정 API를 붙일 때 채널 동작이 처음 검증된다. 지금 읽게 하면 표가 비어 있어 **관측 가능한 동작 변화는 0**이고(기본 수신), 나중의 API는 순수 추가가 된다. 설정을 바꾸는 **API·화면은 만들지 않았다** — 그 부분은 문서 결정 그대로다. 담당자가 이 해석에 반대하면 채널의 `isEnabled` 호출만 되돌리면 된다.
- **검증:** Level 1 `EmailNotificationChannelTest`(대상/비대상 유형·병원 수신·미인증 주소·설정 off/기본 on·게이트웨이 예외 전파), `NotificationPushListenerTest`(모든 채널 전달·채널 실패 격리). Level 3 `NotificationEmailChannelIntegrationTest`(커밋 후 1통·롤백 시 미발송·비대상 유형·미인증 회원·설정 off/on, 실 리스너 배선), `NotificationPreferenceDdlIntegrationTest`(UNIQUE 강제·채널별 분리·varchar 컬럼·이름·CHECK 부재), `NotificationPreferenceCheckConstraintMigrationIntegrationTest`(CHECK 드롭·드롭 후 열거 밖 값 저장·멱등). Level 5 실기동으로 빈 DB에서 테이블·UNIQUE 생성 실측. **통합 스위트는 빈 DB로도 돌린다** — 오래된 개발 DB로만 돌리면 CHECK 제약 관련 결함이 드러나지 않는다.
- **알려진 한계(후속):** ⓐ 커밋 직후 프로세스가 죽으면 그 메일은 재시도 없이 유실된다(인앱 저장은 남는다) — 전달 보장은 3.11 아웃박스 범위다. ⓑ 발송이 커밋한 요청 스레드에서 동기 수행되므로 SMTP 지연이 응답 시간에 올라탄다(3.10 알려진 한계 ⓒ와 같은 성질이고 같은 `@Async` 전용 실행기 이관으로 함께 해소한다). 로컬·CI는 fake provider라 이 비용이 드러나지 않는다. ⓒ 수신 설정을 바꾸는 API·화면이 없어 실제로 끄려면 DB에 행을 넣어야 한다.

## 3.12 유형 컬럼 ENUM → VARCHAR (부채 해소, #176 구현 완료)
**범위:** `notifications.type`·`resource_type`의 물리 타입을 MySQL native ENUM에서 `VARCHAR(40)`으로 전환한다. 엔티티(`Notification`)의 세 유형 컬럼에 `@JdbcTypeCode(SqlTypes.VARCHAR)`를 못박아 **신규 DB도 varchar로 생성**되게 하고, 기존 DB는 `NotificationTypeVarcharMigrationRunner`(마커 `notification_type_varchar_v1`, 선행 pre-JPA 실행)가 한 번 전환한다.
**CI가 잡아낸 후속(중요):** 애너테이션만으로는 목적이 달성되지 않는다 — Hibernate는 VARCHAR enum 컬럼에 허용 값을 열거하는 **CHECK 제약**을 함께 만든다(`check (type in ('NO_SHOW',…))`). 남겨두면 값 추가 시 기존 DB에서 그 값의 INSERT만 실패하는 증상이 MySQL 1265(ENUM) 대신 3819(CHECK)로 **이름만 바뀐 채 그대로 재현**된다. `@Column(columnDefinition = …)`으로도 억제되지 않음을 실측했으므로, 같은 러너가 `type`·`resource_type`·`recipient_type`을 참조하는 CHECK 제약을 드롭하고 남아 있으면 부팅을 중단시킨다. 제약 이름은 MySQL이 `notifications_chk_N`으로 자동 부여해 순서에 따라 달라지므로 이름을 하드코딩하지 않고 CHECK 절이 참조하는 컬럼으로 대상을 고른다. 이 CHECK는 **새로 생성되는 테이블에만** 붙는다(`ddl-auto=update`는 기존 테이블에 CHECK를 추가하지 않는다) — 그래서 오래된 개발 DB로 통합 테스트를 돌리면 통과하고 **CI의 빈 DB에서만 깨졌다**.
**근거:** 이 컬럼이 ENUM이었던 것은 마이그레이션의 선택이 아니라 Hibernate 기본 동작이었다 — `@Enumerated(EnumType.STRING)`을 native ENUM으로 만들고 `@Column(length)`를 무시한다. `ddl-auto=update`는 기존 ENUM 정의를 넓혀주지 않으므로 enum에 값만 추가하면 컴파일·단위 테스트는 통과하는데 **기존 DB에서 그 값의 INSERT만 실패**했다(MySQL 1265). 그래서 값마다 확장 러너가 생겼고, 그 러너들은 목표 목록을 하드코딩해 컬럼 정의를 통째로 교체하므로 상위집합·실행 순서 관례를 사람이 기억해야 남의 값이 사라지지 않았다. 정본(SA §4)은 이미 VARCHAR로 규정하고 있었으므로 이 전환은 새 설계가 아니라 **정본대로 되돌리는 것**이다.
**함께 제거한 것:** 값 확장 전용 러너 두 개(`NotificationWaitlistOfferedType*`·`NotificationReservationRequestedType*`, 각 Configuration·통합 테스트 포함)와, `ReservationHospitalCanceledStatusMigrationRunner`의 `notifications.type` 취급. 마지막 것이 가장 위험한 지뢰였다 — 예약 도메인 러너인데 알림 컬럼을 자기 하드코딩 ENUM으로 교체하면서 그 목록에 `RESERVATION_REQUESTED`가 없어, 조건이 맞는 DB에서는 뒤에 추가된 값을 지우거나(행이 없을 때) 부팅을 깨뜨렸다(행이 있을 때). 알림 도메인 러너들의 `@DependsOn` 체인은 다른 도메인이라 이 러너를 덮지 못했다. 이미 적용된 DB의 옛 마커는 지우지 않고 남긴다 — 마커는 실행 이력이고 아무도 참조하지 않는다.
**안전성 판단(DB가 값을 막지 않게 된 대가):** 저장 경로는 모두 `NotificationService.create()`를 지나 자바 enum을 인자로 받으므로 **잘못된 문자열이 들어오는 코드 경로는 없다** — 유효성 검증은 enum 파싱이 전담한다. 남는 위험은 ⓐ 수동 DB 편집, ⓑ 구/신 버전 혼재(신버전이 쓴 값을 구버전이 읽음)뿐이다. 과거 오타 값(`RESERVATION_HOSPITAL_CANCELLED`) 정정은 제거한 러너 대신 전환 러너가 같은 잠금 안에서 승계하고, enum이 모르는 그 밖의 값은 **부팅을 막지 않고 경고로만** 드러낸다 — 구버전 롤백 직후를 부팅 실패로 만들지 않기 위한 선택이며, VARCHAR 전환이 사준 전방 호환을 스스로 버리지 않기 위함이다(해당 행의 조회만 깨진다).
**검증:** 스키마를 바꿨으면 **빈 DB로도 통합 테스트를 돌린다**(CI는 매 실행 빈 DB — 오래된 개발 DB로만 돌리면 위 CHECK 결함이 드러나지 않는다). CHECK 드롭 테스트는 신규 DB 상태를 기존 DB에서 재현하려고 제약을 직접 만들어 놓고 러너가 드롭하는지 본다. Level 3 `NotificationTypeVarcharMigrationIntegrationTest`(ENUM→varchar 전환·재실행 멱등·기존 행 값 보존·마커가 있어도 수동 ENUM 드리프트 복구·전환 후 정의에 없던 새 값 INSERT 성공·오타 값 정정·**CHECK 제약 드롭**·recipient_type CHECK 드롭), `NotificationEnumColumnSchemaIntegrationTest`(ENUM 분기를 제거하고 **varchar가 아니면 실패**하도록 계약 전환 + **CHECK 제약 부재 단정** — 엔티티의 `@JdbcTypeCode` 유실과 CHECK 재도입 회귀를 잡는다). Level 5 실기동 — 빈 DB 부팅에서 두 컬럼이 `varchar(40)`으로 생성되고(대조 실험: 애너테이션을 떼면 같은 조건에서 native ENUM으로 생성됨을 실측), ENUM 상태 DB 부팅에서 pre-JPA 러너가 전환한 뒤 재기동이 무동작이다.

## 3.11 알림 저장 신뢰성 / 아웃박스 (홀, 낮음)
**범위:** 결제·예약 커밋과 같은 신뢰도로 저장 보장(같은 트랜잭션에 outbox row → 별도 발행자).
**근거:** SSE 실시간 유실은 **이미 폴링 fallback으로 커버**된다(저장이 원본). 남는 구멍은 `create()` **저장 자체가 실패**하면 보호자가 결과를 영영 못 받는 것뿐. 결제 [결제.md](결제.md) 3.6과 공유.
