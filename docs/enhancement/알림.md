> 이 문서는 동결된 MVP 정본에 대한 **델타(변경분)**다. 아래 `전제` 절에 적힌 SA 절만 함께 읽으면 되고, 그 밖의 MVP 문서는 읽지 않는다.
> 충돌 시: 이 문서가 `override 범위`에 선언한 것 안에서는 이 문서 > 동결 SA. 범위 밖은 동결 SA가 정본. (레이어 규칙: [README](README.md))

## 메타

- **상태:** 초안
- **담당:** @maschemy
- **관련 이슈:** #
- **전제(동결 baseline — 이 절만 함께 읽는다):** SA §9-8(폴링 + MVP2 단방향 **SSE 확정**·NotificationPusher 추상화·티켓 인증·커밋 후 전송), SA §8-8(알림 API), SA §4 notifications
- **override 범위(이 문서가 바꾸는 계약):** ① 수신자 모델(MEMBER 전용 → MEMBER/HOSPITAL), ② 미읽음 수·모두 읽음 API, ③ 채널 확장(인앱·SSE에 **이메일** 추가) + 수신 설정, ④ 저장 신뢰성(아웃박스)
- **건드리지 않는 것:** **예약 승인/거절 알림 발행은 develop에 이미 구현됨**(작업 아님). **SSE 실시간 인프라**(`NotificationPusher`·`SseNotificationPusher`·`NotificationPushListener` AFTER_COMMIT·티켓 인증·heartbeat)는 **유지·재사용**한다(버리지 않음). 결제 발행 지점·읽음 멱등 유지. **WebSocket은 채팅 전용**([채팅.md](채팅.md)) — 알림을 WebSocket으로 옮기지 않는다(전송 2계층: 알림=SSE, 채팅=WebSocket).

## develop 현황 — 이미 된 것(작업 아님)
- **예약 승인/거절/자동거절/노쇼 알림 발행: DONE.** `HospitalReservationApplicationService`가 `publishConfirmed`(L84)·`publishRejected`(L119)·`publishNoShow`(L263) 호출, `publishAutoRejected`까지 분리.
- **단방향 실시간 push: SSE로 DONE(#40).** `NotificationService.create()`가 `NotificationCreatedEvent` 발행 → `NotificationPushListener`(AFTER_COMMIT)가 `SseNotificationPusher`로 전송. 티켓 인증(`NotificationSubscriptionController`)·heartbeat·연결상한까지. → 이 채널을 **유지**한다.

## 도메인 경계 조율

## 3.8 미읽음 개수 + 모두 읽음 (고도화) — 웨이브 0, 지금 바로
**범위:** `GET /api/notifications/unread-count`(count 쿼리 신설), `PATCH /api/notifications/read-all`(조건부 bulk UPDATE, 멱등).
**근거:** 현재 컨트롤러는 GET 목록 + PATCH `/{id}/read`뿐. 배지 숫자에 목록 전체 폴링, 30개면 읽음 PATCH 30번.
**독립성:** 스키마 변경 없음, 순수 추가. 다른 결정·작업과 무관 → 착수 1순위.

## 3.10 수신자 모델 확장 — 병원 단위 공유 (홀 + 채팅 전제)
**범위:** `notifications`에 수신자 타입 도입(MEMBER | HOSPITAL). 병원향 알림은 `recipient_type=HOSPITAL, recipient_id=hospitalId`로 저장, **읽음도 병원 단위 1건**. SSE 레지스트리(`SseEmitterRegistry`)도 `memberId` 키라 병원 실시간 수신 경로가 없으므로, 이 확장이 병원 SSE 수신도 함께 연다.
**결정(확정):** 병원 수신·읽음 = **병원 단위 공유**(스태프 누구나 열람, 개인 fan-out·읽음 복제 없음). 스태프 계정 관리가 범위 밖(AGENTS)인 것과 정합.
**근거:** 현재 수신자는 항상 보호자(`member_id`)라 병원 수신 경로가 0. **채팅(양방향)의 스키마 전제.**

## 3.9 채널 확장(이메일) + 수신 설정 (고도화 / 정책)
**범위:** `NotificationChannel` 추상화(인앱 저장 · SSE(존재) · **이메일** 추가). 기존 `mail` 게이트웨이 재사용해 예약 승인·결제 결과 이메일 발송. 유형별 수신 on/off **스키마 선반영**.
**결정(기본):** 이메일은 예약승인·결제결과만, 수신설정은 스키마만 선반영(소급이 어려움). **WebSocket은 여기 아님**(채팅 전용).
**근거:** SSE는 앱이 연결돼 있을 때만 도달 → 앱을 닫으면 못 본다. 이메일이 그 공백을 메운다.

## 3.11 알림 저장 신뢰성 / 아웃박스 (홀, 낮음)
**범위:** 결제·예약 커밋과 같은 신뢰도로 저장 보장(같은 트랜잭션에 outbox row → 별도 발행자).
**근거:** SSE 실시간 유실은 **이미 폴링 fallback으로 커버**된다(저장이 원본). 남는 구멍은 `create()` **저장 자체가 실패**하면 보호자가 결과를 영영 못 받는 것뿐. 결제 [결제.md](결제.md) 3.6과 공유.
