# 병원 검색 인덱스 성능 검증

## 1. 검증 목적

MVP의 병원 공공데이터 범위는 마포구 지자체 코드 `3130000` 한 곳이었다. 이 규모에서는 검색용 인덱스를 미리 추가하지 않고 QueryDSL 검색의 정확성과 페이징 계약을 우선 검증했다.

이후 병원 데이터를 전국 범위로 확장하면서 검색 대상 데이터가 121건에서 10,671건으로 증가했다. 동일한 검색 코드와 부하 조건에서 데이터 규모만 바꿔 응답시간과 처리량을 비교하고, 전국 데이터에서 검색 인덱스가 필요한지 판단한다.

이 문서는 인덱스 적용 전 기준값을 먼저 기록한다. 인덱스 종류는 실행 계획을 확인한 뒤 결정하며, 적용 후에는 같은 데이터와 부하 조건으로 다시 측정한다.

## 2. 성능 목표

PRD §9와 SA의 검색 성능 목표를 기준으로 판단한다.

| 항목 | 목표 |
| --- | ---: |
| P95 응답시간 | 300ms 이하 |
| 처리량 | 100 RPS 이상 |
| 오류율 | 1% 이하 |

## 3. 측정 대상

캐시 효과와 DB 검색 성능을 분리하기 위해 Redis 캐시 대상이 아닌 요청을 사용했다.

```text
검색 조건 없음
partnerOnly=false
openNow=false
page=1
size=50
sort=name
```

기본 캐시 대상은 `size=20`이므로 `size=50`을 사용해 모든 요청이 MySQL의 count 쿼리와 페이지 조회 쿼리를 실행하도록 했다.

## 4. 측정 방법

- 측정일: 2026-08-05
- 환경: 로컬 MySQL 8.4.8, Spring Data JPA, QueryDSL
- 대상: `HospitalService.hospitalSearch()`
- 비교 데이터:
  - 확장 전: 마포구 지자체 코드 `3130000`의 병원 121건
  - 확장 후: 전국 병원 10,671건
- 워밍업: 각 데이터 규모에서 20회
- 부하: 32개 스레드에서 동일 조건 500요청을 동시 실행
- 응답시간: `System.nanoTime()` 기준 평균·P50·P95
- 처리량: 전체 요청 수를 부하 구간의 총 경과시간으로 나눈 RPS
- 오류: 완료되지 못한 요청 또는 실행 중 예외 기준
- DB 조회: Hibernate Statistics의 `queryExecutionCount`, `preparedStatementCount`
- 격리: 원본 `smartcare` DB를 변경하지 않고 별도 `doctorpet_performance` DB에 비교 대상 데이터를 복사
- 정리: 측정 후 임시 DB와 임시 측정 테스트 제거

측정에 사용한 임시 테스트 명령은 다음과 같다.

```powershell
.\gradlew.bat test --tests "com.doctorpet.domain.hospital.service.HospitalSearchDataScaleBenchmarkTest" --info
```

임시 측정 클래스는 현재 기능 코드에 포함할 필요가 없어 결과 기록 후 제거했으며 커밋하지 않았다. 인덱스 적용 후 비교에서는 같은 조건의 재현 가능한 성능 테스트를 인덱스 작업 범위에서 구성한다.

검증 판정: **PASS**

- 마포구 121건에서는 P95 272.633ms와 처리량 505.745 RPS로 두 성능 목표를 충족했다.
- 전국 10,671건에서는 P95 713.072ms와 처리량 74.408 RPS로 두 성능 목표를 모두 충족하지 못했다.
- 두 측정 모두 요청당 count 쿼리 1회와 페이지 조회 쿼리 1회가 실행됐다.
- 쿼리 횟수는 변하지 않았으므로, 전국 데이터 확장에 따른 검색·정렬 대상 증가가 실행 비용 상승의 원인 후보다.
- 오류는 발생하지 않아 기능 정확성과 가용성 문제보다 응답시간과 처리량 저하가 우선 확인됐다.

## 6. 인덱스 도입 결정

MVP의 단일 지자체 데이터에서는 인덱스 없이도 목표 성능을 충족했기 때문에 검색 인덱스를 선반영하지 않았다. 전국 데이터로 확장한 뒤 동일 조건에서 P95와 처리량이 모두 목표를 벗어났으므로, 측정 결과에 근거해 검색 인덱스를 도입한다.

인덱스는 예상만으로 추가하지 않고 다음 순서로 결정한다.

```text
전국 데이터에서 검색 쿼리별 EXPLAIN ANALYZE 확인
→ 전체 스캔·정렬·조인 비용 확인
→ 선택도와 실제 where/order by/join 조건에 맞는 후보 인덱스 선정
→ 인덱스 적용
→ 동일한 전국 데이터와 부하로 재측정
→ 쓰기 비용과 실행 계획을 함께 비교해 최종 채택
```

우선 검토 대상은 SA에 기록된 다음 검색 경로다.

- 기본 검색의 `business_status` 조건과 제휴 우선·이름 정렬
- 좌표 바운딩박스의 `coord_x`, `coord_y` 조건
- 역량 검색의 `capability_type`, `capability_value`, `hospital_id` 조인

## 7. 인덱스 적용 후 기록

현재 판정: **PARTIAL**

적용한 인덱스 후보는 다음과 같다.

| 검색 경로 | 적용 인덱스 | 근거 |
| --- | --- | --- |
| 기본 이름순 목록 | `hospitals(name, id, business_status)` | 이름순 페이지 조회와 스캔 중 폐업 상태 확인 지원 |
| 좌표 바운딩박스 | `hospitals(coord_x, coord_y)` | 설계된 경도·위도 복합 범위 검색 지원 |
| 역량 AND 매칭 | 적용하지 않음 | 후보의 전체 쿼리 개선이 1ms 미만이라 유지 비용 대비 효과가 부족함 |

인덱스 적용 전 데이터 규모 비교와 도입 결정은 완료했다. 아래 항목을 모두 기록해야 전체 검증을 완료할 수 있다.

- 검색 조건별 `EXPLAIN ANALYZE` 결과
- 인덱스 적용 전후 평균·P50·P95·처리량·오류율
- count 쿼리와 페이지 조회 쿼리의 실행 계획 변화
- 인덱스가 공공데이터 적재·갱신 쓰기 비용에 미치는 영향
- 적용하지 않은 후보 인덱스와 제외 근거

## 8. 인덱스 적용 후 재측정

- 측정일: 2026-08-06
- 데이터: 로컬 MySQL 8.4.8 `smartcare`, 병원 10,691건
- 조건: 인덱스 적용 전과 동일하게 32개 스레드, 500요청, `size=50`, Redis 캐시 우회
- SQL DEBUG 출력은 측정 구간에서 비활성화하고 Hibernate Statistics로 쿼리 수를 확인했다.

| 항목 | 기존 검증 결과 10,671건 | 인덱스 적용 후 검증 결과 10,691건(2회) | 관찰 결과 |
| --- | ---: | ---: | --- |
| 평균 응답시간 | 415.944ms | 634.859~688.582ms | 이번 측정값 증가 |
| P50 응답시간 | 399.232ms | 594.607~635.503ms | 이번 측정값 증가 |
| P95 응답시간 | 713.072ms | 1,199.222~1,508.822ms | 이번 측정값 증가 |
| 처리량 | 74.408 RPS | 43.769~48.909 RPS | 이번 측정값 감소 |
| 오류 | 0건 | 0건 | 동일 |
| 요청당 DB 쿼리 | 2개 | 2개 | 동일 |

기존 검증에서는 전국 병원 10,671건에서 평균 415.944ms, P50 399.232ms, P95 713.072ms, 처리량 74.408 RPS가 측정됐다. 이후 후보 인덱스를 적용하고 병원 10,691건에서 두 번 다시 측정한 결과 평균 634.859~688.582ms, P50 594.607~635.503ms, P95 1,199.222~1,508.822ms, 처리량 43.769~48.909 RPS가 측정됐다. 두 검증 모두 오류는 0건이고 요청당 DB 쿼리는 2개였다.

인덱스 적용 후 이번 측정값도 성능 목표(P95 300ms 이하, 100 RPS 이상)를 충족하지 못했으며, 수치만 비교하면 기존 검증보다 응답시간은 길고 처리량은 낮았다. 다만 두 결과는 같은 JVM 실행 안에서 인덱스만 활성·비활성화해 비교한 통제 실험이 아니다. DB 버퍼 상태, JVM 워밍업, 커넥션 대기, 직전 테스트 부하 등 측정 조건 차이가 있으므로 이 차이를 인덱스 적용에 따른 성능 악화로 단정하지 않는다.

### 실행 계획

- count 쿼리는 `idx_hospitals_business_status` covering index를 사용했다. 단일 실행에서 약 13.1ms가 걸렸고, 10,691개 인덱스 행을 읽어 `CLOSED`를 제외한 5,585건을 처리했다.
- 페이지 쿼리는 새 인덱스를 사용하지 않았다. `hospitals` 10,691건을 table scan한 뒤 `name, id`로 정렬하고 50건을 제한했으며 단일 실행에서 약 22ms가 걸렸다.
- `business_status <> 'CLOSED'`는 선택도가 낮고 `order by name, id`를 지원하지 않아 현재 단일 컬럼 인덱스만으로 기본 목록 병목을 제거하지 못했다.
- 로컬 DB에는 기존 `idx_hospitals_coord_y_x(coord_y, coord_x)`가 있어 신규 `idx_hospitals_coord_x_y(coord_x, coord_y)`와 목적이 겹친다. 좌표 검색 실행 계획을 비교하기 전에는 둘을 함께 유지하지 않는다.

### 결론

현재 측정만으로 후보 인덱스 3개의 최종 효과를 판정하지 않는다. 기본 목록 쿼리에서 `business_status` 인덱스는 count에만 사용되고 페이지 조회에는 사용되지 않았다는 실행 계획을 근거로, 같은 실행 환경에서 인덱스를 비활성·활성화해 반복 측정해야 한다. 기본 목록의 필터·정렬을 함께 지원하는 후보와 기존 좌표 인덱스도 같은 방식으로 비교한 후 마이그레이션 정의를 확정한다.

## 9. 현재 고정 데이터 인덱스 OFF/ON 통제 비교

- 측정일: 2026-08-06
- 데이터: 병원 10,591건, 제휴 병원 100건, 상세 100건, 진료역량 696건
- 비교 대상: `idx_hospitals_business_status`
- 조건: 동일 JVM·동일 데이터·동일 커넥션 풀에서 인덱스 OFF/ON 교차 실행
- 순서: `OFF → ON → ON → OFF`를 5회 반복해 조건별 10회 측정
- 회차별 요청: 워밍업 100건 후 32개 스레드에서 500건
- SQL DEBUG 출력 비활성화, 각 회차 오류 0건

전체 테스트 중 중단된 캐시 성능 테스트가 남긴 `LOCAL-GOV`·`CACHE-PERF-*` 임시 병원 100건을 측정 전에 제거했다. 제거 후 전국 제휴 데이터는 100건이며, 이후 비교에서는 같은 데이터를 유지했다.

| 항목 중앙값 | 인덱스 OFF | 인덱스 ON | ON 기준 변화 |
| --- | ---: | ---: | ---: |
| 평균 응답시간 | 402.706ms | 428.199ms | 6.3% 증가 |
| P50 응답시간 | 397.714ms | 392.330ms | 1.4% 감소 |
| P95 응답시간 | 691.620ms | 832.374ms | 20.4% 증가 |
| 처리량 | 76.883 RPS | 72.667 RPS | 5.5% 감소 |

두 조건 모두 성능 목표(P95 300ms 이하, 100 RPS 이상)를 충족하지 못했다. `business_status` 단일 인덱스를 켰을 때 P50은 소폭 낮았지만 평균·P95는 높고 처리량은 낮았다. 기존 실행 계획에서도 이 인덱스는 count 쿼리에만 사용되고 `order by name, id`가 있는 페이지 쿼리에는 사용되지 않았다.

따라서 현재 기본 목록 시나리오에서는 `hospitals(business_status)` 단일 인덱스의 도입 효과가 확인되지 않았으며 최종 후보에서 제외하거나 필터·정렬을 함께 지원하는 복합 인덱스와 다시 비교해야 한다. 좌표 및 진료역량 인덱스는 각각 해당 검색 조건으로 별도 OFF/ON 통제 비교가 필요하다.

현재 판정은 **PARTIAL**이다. 기본 영업상태 인덱스는 통제 비교를 완료했지만 좌표·진료역량 인덱스의 효과와 공공데이터 적재 쓰기 비용은 아직 검증하지 않았다.

## 10. 이름순 인덱스 OFF/ON 통제 비교

- 측정일: 2026-08-06
- 데이터: 병원 10,591건, 제휴 병원 100건
- 비교 대상: `idx_hospitals_name_id(name, id)`
- 조건: 동일 JVM·동일 데이터·동일 커넥션 풀에서 인덱스 OFF/ON 교차 실행
- 순서: `OFF → ON → ON → OFF`를 5회 반복해 조건별 10회 측정
- 회차별 요청: 워밍업 100건 후 32개 스레드에서 500건
- 검색 조건: `partnerOnly=false`, `page=1`, `size=50`, `sort=name`, Redis 캐시 우회
- 각 회차 오류: 0건

| 항목 중앙값 | 인덱스 OFF | 인덱스 ON | ON 기준 변화 |
| --- | ---: | ---: | ---: |
| 평균 응답시간 | 383.437ms | 178.583ms | 53.4% 감소 |
| P50 응답시간 | 385.593ms | 179.503ms | 53.5% 감소 |
| P95 응답시간 | 644.481ms | 319.632ms | 50.4% 감소 |
| 처리량 | 80.906 RPS | 172.459 RPS | 113.2% 증가 |

`EXPLAIN ANALYZE`에서 페이지 쿼리는 `idx_hospitals_name_id`를 순서대로 스캔했다. 폐업 병원을 건너뛰며 111개 인덱스 행을 확인한 뒤 50건을 채우고 종료했으며, 별도 정렬은 수행하지 않았다. 페이지 쿼리 단일 실행은 약 0.55ms였다.

### 설계 변경 이유

최초 설계에서는 폐업 병원 제외 조건을 지원하기 위해 `hospitals(business_status)`를 적용했다. 그러나 고정 데이터 OFF/ON 비교와 실행 계획을 확인한 결과, 이 인덱스는 선택도가 낮은 count 쿼리에만 제한적으로 사용되고 실제 페이지 쿼리의 전체 스캔과 `name, id` 정렬을 제거하지 못했다.

따라서 기본 목록 인덱스의 적용 범위를 영업상태 필터 지원에서 이름순 페이지 조회 지원으로 변경했다. 먼저 `hospitals(name, id)`로 전체 스캔과 정렬을 제거했고, 후속 비교에서 인덱스 스캔 중 영업상태도 확인할 수 있는 `hospitals(name, id, business_status)`가 추가 개선을 보여 최종 후보를 교체했다.

기존 `business_status` 단일 인덱스는 count 쿼리만 제한적으로 지원하고 페이지 쿼리의 전체 스캔·정렬을 바꾸지 못했다. 반면 `(name, id)`는 실제 병목이었던 페이지 조회의 정렬 순서를 직접 제공해 읽는 행 수를 줄였다. 이 실행 계획 변화와 10회 교차 측정에서 일관되게 재현된 개선을 근거로 기본 이름순 목록 인덱스로 채택한다.

처리량 목표 100 RPS 이상은 충족했지만 P95는 319.632ms로 목표 300ms 이하를 19.632ms 초과했다. 따라서 이름순 인덱스 효과 검증은 **PASS**, 기본 목록 성능 목표의 종합 판정은 **PARTIAL**이다. 좌표·진료역량 인덱스와 공공데이터 적재 쓰기 비용도 아직 검증하지 않았다.

측정 중 예약 승인 타임아웃 스케줄러가 두 번 실행됐지만 두 번 모두 `scanned=0`, `processed=0`이었다. 데이터 변경은 없었으나 스케줄러 스레드 실행 자체를 완전히 배제한 측정은 아니다.

## 13. count 쿼리 불필요 조인 제거 검증

- 측정일: 2026-08-06
- 데이터: 로컬 MySQL 8.4.8 `smartcare`, 병원 10,591건, 제휴 병원 100건
- 대상: 시설 조건이 없는 기본 검색의 count 쿼리
- 비교: 기존 `hospital_details LEFT JOIN` 유지 쿼리와 조인 제거 쿼리
- 조건: 동일 연결에서 측정 순서를 교차하며 조건별 10회, 회차별 워밍업 30건 후 100건

시설 조건이 없는 검색은 `hospital_details` 컬럼을 필터에 사용하지 않는다. 병원과 병원 상세는 `hospital_id` UNIQUE인 1:1 관계이므로, 이 경우 count 쿼리에서 조인을 제거해도 전체 건수는 변하지 않는다. 수술·입원·야간·응급 조건 중 하나라도 `true`이면 기존처럼 병원 상세를 조인한다.

| count 단독 중앙값 | 기존 LEFT JOIN | 조인 제거 | 변화 |
| --- | ---: | ---: | ---: |
| 평균 실행시간 | 13.157ms | 3.512ms | 73.3% 감소 |
| P95 실행시간 | 17.489ms | 4.288ms | 75.5% 감소 |

`EXPLAIN ANALYZE`에서 기존 쿼리는 영업 중인 5,485건마다 `uk_hospital_details_hospital_id`를 단건 조회했다. 조인 제거 후 이 5,485회의 상세 인덱스 조회가 사라졌고, 두 쿼리의 count 결과는 동일했다.

조인을 제거한 상태에서 `hospitals(business_status)` 단일 인덱스도 별도로 비교했다. 현재 `(name, id, business_status)` 인덱스 사용 시 중앙값 3.964ms·P95 4.893ms, 단일 인덱스 강제 사용 시 중앙값 3.643ms·P95 5.991ms였다. 두 실행 계획 모두 10,591행을 읽었고 P95 개선이 재현되지 않았으므로, count 전용 단일 인덱스는 추가하지 않는다.

변경 후 기본 이름순 검색을 SQL 출력 없이 32개 스레드·500요청으로 10회 측정한 중앙값은 다음과 같다. Redis 캐시는 우회했고, 각 회차 전에 100건을 워밍업했다.

| --- | ---: |

이번 절대 측정값은 성능 목표인 P95 300ms 이하와 처리량 100 RPS 이상을 모두 충족한다. 다만 직전 전체 검색 측정과 구·신 코드를 같은 JVM에서 교차한 비교는 아니므로 전체 응답 개선 폭을 조인 제거의 효과로만 단정하지 않는다. 조인 제거의 직접 효과 판정은 위 count 단독 통제 비교를 근거로 **PASS**, 현재 기본 목록 성능 목표 판정도 **PASS**로 갱신한다.

## 14. 제휴 병원 이름순 검색 인덱스 검증

- 측정일: 2026-08-06
- 데이터: 로컬 MySQL 8.4.8 `smartcare`, 병원 10,591건, 제휴 병원 100건
- 검색 조건: `partnerOnly=true`, `page=1`, `size=50`, `sort=name`
- 최종 후보: `hospitals(partnership_status, name, id, business_status)`

처음에는 count 조건만 보고 `(partnership_status, business_status)`를 후보로 비교했다. 깨끗한 스키마와 같은 조건에서 count 중앙값은 4.034ms에서 0.293ms, P95는 5.211ms에서 0.591ms로 감소했다. 그러나 이 후보는 `ORDER BY name, id`를 지원하지 않으므로 count 전용 인덱스를 추가하는 대신 제휴 필터·이름순 정렬·영업상태 확인을 함께 지원하는 최종 후보로 확장했다.

이 후보는 모든 이름순 검색을 대체하는 공통 인덱스가 아니다. `partnerOnly=false`인 기본 검색에는 `partnership_status` 등호 조건이 없으므로 선두 컬럼을 고정할 수 없고, 뒤의 `name, id` 정렬을 온전히 활용하기 어렵다. 반대로 `partnerOnly=true`에서는 `partnership_status='PARTNER'`가 선두 컬럼을 하나의 범위로 고정하므로 이어지는 `name, id`가 정렬 순서를 제공한다. 따라서 기본 검색은 `(name, id, business_status)`, 제휴 병원 전용 검색은 `(partnership_status, name, id, business_status)`를 각각 사용한다.

로컬 DB에는 저장소 코드와 전체 Git 이력에 정의가 없는 `idx_hospitals_partnership_name_id(partnership_status, name, id)`가 남아 있었다. 신규 환경에는 존재하지 않는 과거 로컬 후보이므로 측정 중에만 `INVISIBLE`로 전환하고, 현재 v3 스키마와 같은 조건에서 비교했다. 최종 v4 마이그레이션은 중복되는 이 구 인덱스가 업그레이드 DB에 남아 있으면 제거한다.

| 쿼리 단독 중앙값 | 현재 인덱스 | 최종 후보 | 변화 |
| --- | ---: | ---: | ---: |
| count 평균 실행시간 | 4.006ms | 0.297ms | 92.6% 감소 |
| count P95 실행시간 | 5.134ms | 0.519ms | 89.9% 감소 |
| 페이지 평균 실행시간 | 0.864ms | 0.282ms | 67.4% 감소 |
| 페이지 P95 실행시간 | 1.236ms | 0.568ms | 54.0% 감소 |

현재 count 실행 계획은 병원 10,591건을 전체 스캔하지만, 후보는 `partnership_status='PARTNER'`로 제휴 병원 100건만 covering index에서 확인했다. 현재 페이지 쿼리는 기본 이름순 인덱스에서 338행을 확인한 뒤 50건을 채웠고, 후보는 제휴 병원 인덱스에서 50행만 확인했다. 두 조건의 count 결과와 페이지 ID 순서는 동일했다.

최종 후보를 적용한 제품 코드 경로를 SQL 출력 없이 32개 스레드·500요청으로 10회 측정했다. 각 회차 전 100건을 워밍업했고 Redis 캐시는 사용하지 않았다.

| 항목 | 제휴 병원 검색 결과 |
| --- | ---: |
| 평균 응답시간 | 19.381ms |
| P50 응답시간 | 7.121ms |
| P95 응답시간 | 86.275ms |
| 처리량 | 1,484.903 RPS |
| 오류 | 0건 |

count와 페이지 쿼리의 통제 비교에서 모두 개선됐고 전체 검색도 P95 300ms 이하와 처리량 100 RPS 이상을 충족했다. 따라서 제휴 병원 이름순 인덱스 효과와 해당 검색 경로의 성능 목표 판정은 **PASS**다. 좌표·진료역량 인덱스 효과와 공공데이터 적재 쓰기 비용은 아직 별도 검증이 필요하므로 전체 인덱스 작업 판정은 **PARTIAL**로 유지한다.

## 15. 좌표 바운딩박스 인덱스 검증

- 측정일: 2026-08-06
- 데이터: 로컬 MySQL 8.4.8 `smartcare`, 병원 10,591건
- 검색 조건: 서울 중심 반경 5km에 해당하는 경도·위도 바운딩박스
- 비교 대상: 좌표 인덱스 OFF, `(coord_x, coord_y)`, `(coord_y, coord_x)`
- 통제 방법: 동일 DB 연결과 데이터에서 두 좌표 인덱스의 가시성만 바꾸고, 각 조건을 워밍업한 뒤 반복 측정
- 정확성 통제: 세 조건 모두 같은 병원 ID 159건을 반환하는지 검증

비교 SQL의 핵심 조건은 다음과 같다. 제품 검색과 동일하게 경도와 위도에 각각 `BETWEEN` 범위 조건을 적용했다.

```sql
select h.id
from hospitals h
where h.coord_x between :minLongitude and :maxLongitude
  and h.coord_y between :minLatitude and :maxLatitude;
```

| 후보 | 확인한 인덱스 행 | 중앙값 | P95 |
| --- | ---: | ---: | ---: |
| 인덱스 OFF | 10,591행 테이블 스캔 | 11.192ms | 12.297ms |
| `(coord_x, coord_y)` | 296행 범위 스캔 | 1.923ms | 2.390ms |
| `(coord_y, coord_x)` | 296행 범위 스캔 | 1.900ms | 2.402ms |

인덱스 OFF에서는 병원 10,591건을 모두 확인했다. 두 후보는 선두 좌표의 범위로 296행까지 줄인 뒤 나머지 좌표 조건을 검사했다. `(coord_x, coord_y)`의 중앙값은 OFF보다 82.8%, P95는 80.6% 감소했다. 역순 후보와의 차이는 중앙값 0.023ms, P95 0.012ms로 측정 오차 범위에 가깝다.

두 컬럼 모두 범위 조건이라 선두 컬럼 이후 조건으로 탐색 범위를 더 좁히는 데에는 한계가 있다. 어느 순서를 사용해도 결과와 접근 행 수가 같고 성능도 사실상 동률이므로, 기존 SA 설계와 검색 요청의 경도·위도 순서를 따르는 `(coord_x, coord_y)`를 유지한다. 같은 검색을 위한 `idx_hospitals_coord_y_x`를 함께 두면 조회 이득 없이 적재·갱신 때 두 인덱스를 모두 관리해야 하므로 v5 마이그레이션에서 제거한다.

스캔 행 수와 중앙값·P95가 모두 큰 폭으로 감소했고 결과 집합도 동일하므로 좌표 인덱스 효과 판정은 **PASS**다.

- 비교: 관련 보조 인덱스 OFF, 기존 `(capability_type, capability_value, hospital_id)`, 후보 `(capability_value, hospital_id)`
- 통제 방법: 동일 DB 연결과 데이터에서 비교 대상 인덱스의 가시성만 전환
- 반복 방법: 조건별 워밍업 30회 후 100회 실행한 평균을 한 표본으로 삼아 총 10표본 측정
- 정확성 통제: 세 조건 모두 같은 병원 ID 100건을 반환하는지 검증

비교한 제품 SQL 형태는 다음과 같다. `HospitalRepositoryCustomImpl.capabilityMatches()`와 같이 `capability_type` 조건 없이 값으로 필터링하고, 요청한 두 값을 모두 보유한 병원만 `HAVING`으로 남긴다.

```sql
select h.id, h.name, h.business_status, hd.open_hours
from hospitals h
left join hospital_details hd on hd.hospital_id = h.id
where h.business_status <> 'CLOSED'
  and h.id in (
      select hc.hospital_id
      from hospital_capabilities hc
      where hc.capability_value in ('DOG', 'XRAY')
      group by hc.hospital_id
      having count(distinct hc.capability_value) = 2
  );
```

첫 측정은 로컬 DB에 과거 실험에서 생성된 `idx_hospital_capabilities_value_hospital`이 남아 있어 OFF 조건에서도 후보 인덱스를 사용하는 오염을 발견했다. 이 결과는 판정에서 제외했다. 잔존 후보와 기존 검색 인덱스를 모두 `INVISIBLE`로 통제한 뒤 아래 결과를 다시 측정했고, 테스트 종료 시 원래 가시성을 복구했다.

| 후보 | 진료 역량 접근 방식 | 중앙값 | P95 |
| --- | --- | ---: | ---: |
| 인덱스 OFF | UNIQUE 인덱스 696행 전체 스캔 | 14.996ms | 15.695ms |
| 기존 설계 | UNIQUE 인덱스 696행 전체 스캔 | 14.385ms | 15.306ms |
| `(capability_value, hospital_id)` | 조건 일치 200행 범위 스캔 | 14.221ms | 15.034ms |

OFF 실행 계획은 UNIQUE 인덱스 `uk_hospital_capabilities_hospital_type_value`의 696행을 covering scan했다. 기존 검색용 인덱스는 선두 `capability_type`을 쿼리에서 고정하지 않아 선택되지 않았고 실행 계획도 OFF와 같았다. 후보만 `capability_value='DOG' OR 'XRAY'` 범위에서 200행을 읽었다.

후보의 실행 계획은 의도대로 바뀌었지만 전체 쿼리 중앙값은 0.775ms, P95는 0.661ms만 감소했다. 비율로는 각각 5.2%, 4.2%지만 절대 개선 폭은 모두 1ms보다 작다. 역량 서브쿼리 밖에서 `hospitals` 10,591행을 검사하는 비용이 전체 시간을 지배하고, 현재 역량 데이터 696건은 기존 covering scan으로도 처리 비용이 작기 때문이다.

검색 전용 인덱스를 추가하면 모든 역량 INSERT·UPDATE·DELETE에서 인덱스를 함께 관리하고 저장 공간과 마이그레이션 대상을 늘려야 한다. 현재 측정에서는 그 비용을 감수할 만큼 제품 쿼리가 개선되지 않았다. 따라서 신규 `(capability_value, hospital_id)` 후보를 **기각**하고, 실제 쿼리에서 사용되지 않은 기존 `(capability_type, capability_value, hospital_id)` 검색 인덱스도 최종 적용 대상에서 제외한다. 무결성 보장을 위한 `uk_hospital_capabilities_hospital_type_value`는 유지한다.

재검토 시점은 진료 역량 행 수나 역량 검색 트래픽이 현재보다 유의미하게 증가했을 때다. 그때도 동일한 검색 조건으로 결과 동일성, 실행 계획, 전체 쿼리 절대 지연시간, 공공데이터 적재 비용을 함께 비교한다. 진료 역량 후보 검증 자체는 **PASS**, 도입 결정은 **기각**이다. 좌표 후보까지 판정을 마쳤지만 공공데이터 적재·갱신 쓰기 비용이 남아 있으므로 전체 인덱스 작업은 **PARTIAL**이다.

## 17. 복합 인덱스 키 길이 확인

- 확인일: 2026-08-07
- 환경: 로컬 MySQL 8.4.8, `utf8mb4_0900_ai_ci`
- 확인 명령: `SHOW CREATE TABLE hospitals`, `information_schema.columns` 조회

실제 DDL에서 `name`은 `varchar(255)`, `business_status`는 `enum('CLOSED','CLOSED_TEMP','OPEN')`, `partnership_status`는 `enum('NON_PARTNER','PARTNER')`로 생성됐다. 두 enum은 값이 255개 이하이므로 MySQL에서 각각 1바이트로 저장된다.

가장 큰 `idx_hospitals_partnership_name_id_business_status(partnership_status, name, id, business_status)`의 최대 키 길이는 `name` 1,020바이트(`255 × utf8mb4 최대 4바이트`) + enum 2바이트 + `BIGINT` 8바이트로 약 1,030바이트다. InnoDB 인덱스 키 한도 3,072바이트보다 약 2,042바이트 작다. 현재 정의는 키 길이 여유가 충분하므로 enum 컬럼에 별도 길이 제한을 추가하지 않는다. 인덱스에 문자열 컬럼을 추가하거나 문자셋·컬럼 타입을 변경할 때 다시 계산한다.
