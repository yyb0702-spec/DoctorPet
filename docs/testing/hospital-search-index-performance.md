# 병원 검색 인덱스 성능 검증

## 1. 검증 목적

MVP의 병원 공공데이터 범위는 마포구 지자체 코드 `3130000` 한 곳이었다. 이 규모에서는 검색용 인덱스를 미리 추가하지 않고 QueryDSL 검색의 정확성과 페이징 계약을 우선 검증했다.

이후 병원 데이터를 전국 범위로 확장하면서 검색 대상 데이터가 121건에서 10,671건으로 증가했다. 동일한 검색 코드와 부하 조건에서 데이터 규모만 바꿔 응답시간과 처리량을 비교하고, 전국 데이터에서 검색 인덱스가 필요한지 판단한다.

이 문서는 인덱스 적용 전 기준값을 먼저 기록한다. 인덱스 종류는 실행 계획을 확인한 뒤 결정하며, 적용 후에는 같은 데이터와 부하 조건으로 다시 측정한다.

## 2. 성능 목표

PRD §9와 SA의 검색 성능 목표를 기준으로 판단한다.

| 항목 | 목표 |
| --- | ---: |
| P95 응답시간 | 300ms 이하 |
| 처리량 | 100 RPS 이상 |
| 오류율 | 1% 이하 |

## 3. 측정 대상

캐시 효과와 DB 검색 성능을 분리하기 위해 Redis 캐시 대상이 아닌 요청을 사용했다.

```text
검색 조건 없음
partnerOnly=false
openNow=false
page=1
size=50
sort=name
```

기본 캐시 대상은 `size=20`이므로 `size=50`을 사용해 모든 요청이 MySQL의 count 쿼리와 페이지 조회 쿼리를 실행하도록 했다.

## 4. 측정 방법

- 측정일: 2026-08-05
- 환경: 로컬 MySQL 8.4.8, Spring Data JPA, QueryDSL
- 대상: `HospitalService.hospitalSearch()`
- 비교 데이터:
  - 확장 전: 마포구 지자체 코드 `3130000`의 병원 121건
  - 확장 후: 전국 병원 10,671건
- 워밍업: 각 데이터 규모에서 20회
- 부하: 32개 스레드에서 동일 조건 500요청을 동시 실행
- 응답시간: `System.nanoTime()` 기준 평균·P50·P95
- 처리량: 전체 요청 수를 부하 구간의 총 경과시간으로 나눈 RPS
- 오류: 완료되지 못한 요청 또는 실행 중 예외 기준
- DB 조회: Hibernate Statistics의 `queryExecutionCount`, `preparedStatementCount`
- 격리: 원본 `smartcare` DB를 변경하지 않고 별도 `doctorpet_performance` DB에 비교 대상 데이터를 복사
- 정리: 측정 후 임시 DB와 임시 측정 테스트 제거

측정에 사용한 임시 테스트 명령은 다음과 같다.

```powershell
.\gradlew.bat test --tests "com.doctorpet.domain.hospital.service.HospitalSearchDataScaleBenchmarkTest" --info
```

임시 측정 클래스는 현재 기능 코드에 포함할 필요가 없어 결과 기록 후 제거했으며 커밋하지 않았다. 인덱스 적용 후 비교에서는 같은 조건의 재현 가능한 성능 테스트를 인덱스 작업 범위에서 구성한다.

## 5. 인덱스 적용 전 측정 결과

| 항목 | 마포구 121건 | 전국 10,671건 | 변화 |
| --- | ---: | ---: | ---: |
| 평균 응답시간 | 57.413ms | 415.944ms | 358.531ms 증가, 약 7.2배 |
| P50 응답시간 | 14.152ms | 399.232ms | 385.080ms 증가, 약 28.2배 |
| P95 응답시간 | 272.633ms | 713.072ms | 440.439ms 증가, 약 2.6배 |
| 처리량 | 505.745 RPS | 74.408 RPS | 431.337 RPS 감소, 약 85.3% |
| 오류 | 0건 | 0건 | 동일 |
| Query 실행 | 1,000회 | 1,000회 | 동일 |
| PreparedStatement 생성 | 1,000회 | 1,000회 | 동일 |
| 요청당 DB 쿼리 | 2회 | 2회 | 동일 |

검증 판정: **PASS**

- 마포구 121건에서는 P95 272.633ms와 처리량 505.745 RPS로 두 성능 목표를 충족했다.
- 전국 10,671건에서는 P95 713.072ms와 처리량 74.408 RPS로 두 성능 목표를 모두 충족하지 못했다.
- 두 측정 모두 요청당 count 쿼리 1회와 페이지 조회 쿼리 1회가 실행됐다.
- 쿼리 횟수는 변하지 않았으므로, 전국 데이터 확장에 따른 검색·정렬 대상 증가가 실행 비용 상승의 원인 후보다.
- 오류는 발생하지 않아 기능 정확성과 가용성 문제보다 응답시간과 처리량 저하가 우선 확인됐다.

## 6. 인덱스 도입 결정

MVP의 단일 지자체 데이터에서는 인덱스 없이도 목표 성능을 충족했기 때문에 검색 인덱스를 선반영하지 않았다. 전국 데이터로 확장한 뒤 동일 조건에서 P95와 처리량이 모두 목표를 벗어났으므로, 측정 결과에 근거해 검색 인덱스를 도입한다.

인덱스는 예상만으로 추가하지 않고 다음 순서로 결정한다.

```text
전국 데이터에서 검색 쿼리별 EXPLAIN ANALYZE 확인
→ 전체 스캔·정렬·조인 비용 확인
→ 선택도와 실제 where/order by/join 조건에 맞는 후보 인덱스 선정
→ 인덱스 적용
→ 동일한 전국 데이터와 부하로 재측정
→ 쓰기 비용과 실행 계획을 함께 비교해 최종 채택
```

우선 검토 대상은 SA에 기록된 다음 검색 경로다.

- 기본 검색의 `business_status` 조건과 제휴 우선·이름 정렬
- 좌표 바운딩박스의 `coord_x`, `coord_y` 조건
- 역량 검색의 `capability_type`, `capability_value`, `hospital_id` 조인

## 7. 인덱스 적용 후 기록

현재 판정: **PARTIAL**

인덱스 적용 전 데이터 규모 비교와 도입 결정은 완료했다. 다음 인덱스 브랜치에서 아래 항목을 기록해야 전체 검증을 완료할 수 있다.

- 검색 조건별 `EXPLAIN ANALYZE` 결과
- 실제 적용한 인덱스와 선택 근거
- 인덱스 적용 전후 평균·P50·P95·처리량·오류율
- count 쿼리와 페이지 조회 쿼리의 실행 계획 변화
- 인덱스가 공공데이터 적재·갱신 쓰기 비용에 미치는 영향
- 적용하지 않은 후보 인덱스와 제외 근거

## 8. 해석 시 주의사항

- 로컬 개발 환경의 절대 시간은 운영 환경 성능으로 일반화하지 않는다.
- 이번 측정은 HTTP·네트워크 구간을 제외한 서비스·DB 통합 측정이다.
- 고정 도착률이 아니라 32개 작업 스레드의 동시 실행 결과이므로 k6의 100 RPS 시나리오와 구분한다.
- 한 번의 측정값만으로 미세한 차이를 단정하지 않는다. 인덱스 적용 후에는 같은 환경에서 반복 측정한다.
- 이번 결과는 조건 없는 기본 목록의 캐시 우회 요청에 대한 기준값이다. 지역·좌표·축종·진료 역량 검색은 실행 계획과 성능을 별도로 확인해야 한다.
- 인덱스의 최종 채택은 조회 개선뿐 아니라 전국 공공데이터 주간 적재의 쓰기 비용까지 함께 고려한다.
