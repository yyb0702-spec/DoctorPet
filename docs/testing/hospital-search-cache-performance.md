# 병원 검색 최초 진입 페이지 캐시 성능 검증

## 1. 검증 목적

병원 검색 화면 최초 진입 시 모든 사용자가 공통으로 조회하는 기본 첫 페이지에 Redis 캐시를 적용한다. 캐시 도입 전후의 응답시간과 DB 조회 횟수를 동일한 로컬 환경에서 비교한다.

이 검증은 공통 진입 화면의 반복 조회에서 Redis 캐시가 정상적으로 재사용되는지를 확인하기 위한 것이다. 실제 운영 트래픽의 캐시 HIT율이나 운영 환경 성능을 입증하지 않는다.

## 2. 캐시 적용 범위

- 별도 검색 조건 없음
- `partnerOnly=true`
- `openNow=false`
- `page=1`
- `size=20`
- `sort=name`

위 조건과 일치하지 않는 위치·반경·거리순·현재 영업·조건 검색과 뒤쪽 페이지에는 캐시를 적용하지 않는다.

## 3. 측정 방법

- 환경: 로컬 MySQL, 로컬 Redis, Spring Data JPA, QueryDSL
- 대상: `HospitalService.hospitalSearch()` 최초 진입 기본 첫 페이지
- 데이터: 기존 로컬 데이터에 테스트 전용 제휴 병원 20건을 추가하고 측정 후 제거
- 워밍업: 20회
- 부하: 32개 스레드에서 동일 조건 500요청을 동시 실행
- 응답시간: `System.nanoTime()` 기준 평균·P50·P95
- 처리량: 전체 요청 수를 부하 구간의 총 경과시간으로 나눈 RPS
- 오류율: 완료되지 못한 요청 수 기준
- DB 조회: Hibernate Statistics의 `queryExecutionCount`, `preparedStatementCount`
- 시간값에는 테스트 통과 기준을 두지 않고 동일 환경 전후 비교값으로만 사용
- DB 조회 횟수는 캐시 도입 전 요청당 count 쿼리 1회와 페이지 조회 쿼리 1회를 기준으로 검증

실행 명령:

```powershell
.\gradlew.bat test --tests "com.doctorpet.domain.hospital.service.HospitalSearchCacheBaselineIntegrationTest" --info
.\gradlew.bat test --tests "com.doctorpet.domain.hospital.service.HospitalSearchCachePerformanceIntegrationTest" --info
```

## 4. 캐시 도입 전 기준값

측정일: 2026-07-29

| 항목 | 결과 |
| --- | ---: |
| 테스트 추가 제휴 병원 | 20건 |
| 동시 스레드 | 32개 |
| 측정 요청 | 500회 |
| 평균 응답시간 | 79.551ms |
| P50 응답시간 | 35.640ms |
| P95 응답시간 | 282.980ms |
| 처리량 | 388.869 RPS |
| 오류 | 0건 |
| Query 실행 | 1,000회 |
| PreparedStatement 생성 | 1,000회 |
| 요청당 DB 쿼리 | 2회 |

판정: **PASS**

- 동일한 최초 진입 기본 첫 페이지 요청마다 count 쿼리와 페이지 조회 쿼리가 각각 실행됨을 확인했다.
- 캐시 적용 후 동일 조건 반복 요청의 Redis HIT에서는 DB 쿼리 0회를 목표로 비교한다.

## 5. 캐시 적용 후 기록

측정일: 2026-07-29

| 항목 | 적용 전 | 적용 후 | 변화 |
| --- | ---: | ---: | ---: |
| 평균 응답시간 | 79.551ms | 72.282ms | 7.269ms 감소(9.1%) |
| P50 응답시간 | 35.640ms | 22.422ms | 13.218ms 감소(37.1%) |
| P95 응답시간 | 282.980ms | 290.064ms | 7.084ms 증가(2.5%) |
| 처리량 | 388.869 RPS | 431.970 RPS | 43.101 RPS 증가(11.1%) |
| 오류 | 0건 | 0건 | 동일 |
| Query 실행 | 1,000회 | 0회 | 1,000회 감소 |
| PreparedStatement 생성 | 1,000회 | 0회 | 1,000회 감소 |
| 캐시 HIT 시 요청당 DB 쿼리 | 2회 | 0회 | 2회 감소 |

판정: **PASS**

- 캐시를 한 번 예열한 뒤 500개 HIT 요청에서 MySQL 쿼리가 한 번도 실행되지 않았다.
- 평균과 P50 응답시간, 처리량은 개선됐지만 P95는 2.5% 증가했다. 현재의 작은 데이터와 로컬 측정만으로 꼬리 응답시간 개선까지 단정할 수 없다.
- 이번 구현에서 명확히 확인된 성과는 공통 첫 페이지 반복 요청의 DB 부하 제거다. 응답시간 수치는 로컬 환경에서 관찰한 비교값으로만 사용한다.

## 6. 해석 시 주의사항

- 로컬 개발 환경의 절대 시간은 운영 환경 성능으로 일반화하지 않는다.
- 동일 조건 반복 요청을 사용하므로 실제 사용자 검색 조건의 반복률을 의미하지 않는다.
- HTTP·네트워크 구간을 제외한 서비스·DB 통합 측정이므로 실제 API 종단 간 부하 결과와 구분한다.
- 고정 도착률이 아니라 32개 작업 스레드의 동시 실행 결과이므로 k6의 100 RPS 시나리오와 구분한다.
- 캐시 도입 근거는 모든 사용자가 공통으로 조회하는 최초 진입 기본 첫 페이지라는 제품 흐름이다.
- Redis 저장·조회와 TTL은 실제 Redis 통합 테스트로 확인했다.
- Redis 읽기·쓰기 예외가 요청으로 전파되지 않는 fallback은 단위 테스트로 확인했다. 실제 Redis 프로세스를 중단한 상태의 API 종단 간 검증은 포함하지 않았다.
- 전국 단위 데이터 확장 시에는 캐시와 별개로 실행 계획과 응답시간을 분석해 검색 인덱스를 적용한다.
