## 1. 오늘 작업 요약

직원 도착 확인 API와 자동 노쇼 기능에 대해 팀 리뷰에서 지적된 누락 사항을 확인하고 수정했다.

- 체크인 이력과 노쇼 정정 이력의 연결을 보완했다.
- 회원 탈퇴 때 `NO_SHOW_PENDING` 예약도 활성 예약으로 판단하도록 바꿨다.
- 추가 유예가 끝나는 순간 체크인과 최종 노쇼가 부딪히는 경계 테스트를 추가했다.
- API 경로와 상태 정책을 문서에 명확히 적었다.
- DB 마이그레이션과 경량 문서의 상태·버전 정보를 정본과 맞췄다.

## 2. 문제와 해결

### 2-1. 노쇼 정정 후 체크인 이력이 빠질 수 있던 문제

#### 문제

`NO_SHOW` 예약을 직원이 `CHECKED_IN`으로 정정한 뒤 같은 예약에 체크인 요청이 다시 들어오면, 상태는 이미 `CHECKED_IN`이었다. 이때 기존 코드가 체크인 이력을 새로 만들 수 있어 정정 시각과 실제 도착 시각이 섞이거나, 처리 직원 정보가 잘못 기록될 수 있었다.

#### 해결

- 노쇼 정정 시 `CHECKED_IN` 이력을 정정 시각·직원 ID와 함께 먼저 저장한다.
- 이미 `CHECKED_IN`인 예약을 다시 요청하면 기존 이력만 읽어 최초 시각을 반환한다.
- 오래된 데이터처럼 체크인 이력이 없는 경우에는 임의의 이력을 새로 만들지 않고 예약의 마지막 수정 시각을 응답한다.
- 체크인 성공 직후 이력이 정말 저장되지 않았다면 `CHECK_IN_HISTORY_NOT_FOUND` 도메인 오류를 반환한다.

쉽게 말하면, 이미 도착 처리된 사람의 도착 시간을 매번 새로 쓰지 않고 처음 기록한 시간을 계속 보여주도록 고쳤다.

### 2-2. 회원 탈퇴 중인 사용자의 예약이 운영 대상에서 빠지던 문제

#### 문제

회원 탈퇴 가능 여부를 확인할 때 `CONFIRMED`, `CHECKED_IN`만 검사하고 있었다. 하지만 `NO_SHOW_PENDING`도 직원이 아직 체크인할 수 있는 예약이다. 이 상태에서 탈퇴하면 병원 직원이 처리해야 할 예약과 회원 정보가 끊길 수 있다.

#### 해결

탈퇴를 막는 활성 예약 상태를 다음 세 가지로 통일했다.

```text
CONFIRMED
NO_SHOW_PENDING
CHECKED_IN
```

`ReservationServiceTest`에도 `NO_SHOW_PENDING`이 활성 상태 목록에 포함되는지 반영했다.

### 2-3. 추가 유예가 끝나는 순간의 경합 검증 부족

#### 문제

예약 시작 후 15분이 되는 경계에서 체크인과 자동 최종 노쇼가 동시에 요청될 수 있다. 이때 두 작업이 모두 성공하면 상태와 이력이 서로 맞지 않게 된다.

#### 해결

최종 경계 시각을 기준으로 두 조건부 UPDATE를 동시에 실행하는 통합 테스트를 추가했다.

- 체크인: 슬롯 시작 시각이 마감 시각 이상일 때만 성공
- 최종 노쇼: 슬롯 시작 시각이 마감 시각보다 이전일 때만 성공
- 같은 예약에서는 두 작업 중 정확히 하나만 성공
- 경계 시각에는 체크인이 우선되고 최종 노쇼는 0건 처리

이렇게 시간 조건에 겹치는 구간이나 빈 구간이 없다는 것을 실제 MySQL 테스트로 확인했다.

### 2-4. API 경로 표기가 서로 달랐던 문제

#### 문제

이슈 설명에 예전 경로인 `POST /api/v1/hospital/reservations/{reservationId}/check-in`이 남아 있었지만, 실제 컨트롤러와 SA는 다른 경로를 사용하고 있었다.

#### 해결

현재 구현과 문서의 정본을 다음 경로로 통일했다.

```text
PATCH /api/hospital/reservations/{reservationId}/check-in
```

HTTP 메서드는 상태를 변경하는 부분 수정 요청이므로 `PATCH`를 사용한다.

### 2-5. 경량 문서가 최신 상태를 설명하지 못하던 문제

경량본 일부가 아직 `CONFIRMED → NO_SHOW`만 설명하고 있거나 정책 버전이 v9로 표시되어 있었다. 다음 내용을 정본과 맞췄다.

- `CONFIRMED → NO_SHOW_PENDING → NO_SHOW` 상태 전이
- 기본 5분 추가 유예
- `no_show_pending_at` 컬럼
- `CHECKED_IN`, `AUTO_NO_SHOW_PENDING` 이력 타입
- 회원 탈퇴 시 `NO_SHOW_PENDING` 활성 예약 확인
- 정책 경량본 버전 v10

## 4. 배운 점

1. 상태 이름을 코드에 추가하는 것만으로 끝나지 않는다. 탈퇴, 조회, 응답, 문서처럼 그 상태를 사용하는 모든 경로를 함께 확인해야 한다.
2. 시간 기반 상태 전이는 정확히 같은 시각에 어떤 작업을 허용할지 먼저 정해야 한다.
3. 멱등 API는 두 번째 요청을 성공시키는 것보다 첫 번째 처리 시각과 이력을 보존하는 것이 중요하다.
4. PR 리뷰에서 지적된 경로·버전·상태 표기는 실제 코드만큼 중요한 계약이다.
