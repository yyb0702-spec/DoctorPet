# 예약 목록·상세 조회 구현 정리

## 구현 범위

- `GET /api/reservations`: 로그인한 보호자의 예약 목록을 QueryDSL로 조회한다.
- `GET /api/reservations/{reservationId}`: 본인 예약의 병원·반려동물 스냅샷·슬롯·상태를 조합한다.
- 상태, 예약일 시작/종료일, 페이지, 크기, `reservedAt` 정렬을 지원한다.
- 목록은 슬롯과 병원을 일괄 조회해 예약마다 병원 조회가 반복되지 않도록 했다.

## 서비스 흐름

1. `MemberService.assertActiveMember()`로 인증 주체의 활성 회원 여부를 확인한다.
2. 목록은 `memberId`를 QueryDSL 조건에 항상 포함하고, `from`은 포함·`to`는 다음 날 0시 미만으로 변환한다.
3. 상세는 예약을 먼저 조회한 뒤 소유 회원이 아니면 `COMMON_003`(403), 없으면 `RESERVATION_NOT_FOUND`(404)를 반환한다.
4. 반려동물 이름·종은 예약 생성 시 서버가 소유한 활성 `PetProfile`에서 스냅샷으로 저장한다.
5. 결제수단도 예약 생성 시 활성·소유 여부를 `PaymentMethodService`로 검증한다.
6. 진행 상태는 예약 상태와 결제 상태를 DTO에서 조합한다. 현재 결제 엔티티가 아직 없어 `paymentStatus`는 `null`이다.

## 보안·오류 처리

- 예약 GET/POST/cancel은 `GUARDIAN` 역할만 허용하도록 `SecurityConfig`에 명시했다.
- 날짜 형식, 페이지, 상태, 날짜 범위, 정렬 오류를 각각 Validation 또는 예약 도메인 오류로 변환한다.
- `HandlerMethodValidationException`, `MethodArgumentTypeMismatchException`도 공통 Validation 응답으로 처리한다.

## 명세와 현재 스키마의 차이

SA의 예약 스냅샷은 `petId`, 이름, 종만 정의한다. 따라서 API 예시에 있는 `age`, `weight`, `neutered`, `symptom`, `requestNote`는 스키마를 임의로 확장하지 않고 이번 구현에서 제외했다. 결제 도메인(#34)이 합쳐지면 목록·상세의 `paymentStatus` 조회만 결제 서비스 계약에 연결하면 된다.

또한 현재 공통 `ApiResponse` 정책에 따라 성공 메시지는 기본 문구를 사용하며, 엔티티의 `LocalDateTime` 정책상 응답은 오프셋이 없는 날짜시간으로 직렬화된다.
