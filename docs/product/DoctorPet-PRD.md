## 1. 개요

반려동물 증상을 입력받아 AI가 방문 필요성과 필요 진료역량을 안내하고, 근처 동물병원을 찾아 예약·진료·후불 결제까지 이어주는 서비스다.

흐름은 이렇다: 증상 입력 → AI가 방문 필요성 + 필요 진료역량(requiredCapabilities)을 구조화하고 검색 Tool을 직접 호출 → 제휴/비제휴 2계층으로 노출된 병원 중에서 선택 → 예약 요청(REQUESTED) → 병원 승인(CONFIRMED) 또는 거절(REJECTED) → 체크인 → 진료중 → 진료완료 → 등록 빌링키로 후불 청구.

기술적으로 어려운 지점은 세 곳이다.

- **슬롯 동시 예약 충돌** — 같은 시간대에 여러 요청이 몰릴 때 하나만 성립해야 한다.
- **노쇼 처리** — 그레이스타임 경과 후 자동/수동 판정이 섞인다.
- **후불 결제 정합성** — 진료 후에야 금액이 확정되므로 검증·실패 분기·이중 청구 방지가 핵심이다.

MVP 전제는 다음과 같다.

- 예약은 병원 승인형이다. 병원 기능은 프론트 화면 없이 운영 API로만 제공한다.
- 축종은 검색 필터(`supportedSpecies`)로 적용하며 개·고양이와 주요 특수동물을 지원한다.
- 병원 데이터는 공공데이터 시드 적재(MVP 1회) + 제휴/비제휴 2계층 노출로 구성한다. 실시간 API 프록시는 쓰지 않는다.
- 노쇼는 판정·기록만 한다. 수수료나 예약 제한은 두지 않고, 예약 이력을 병원 승인 판단 자료로 넘긴다.

## 2. 문제와 목표

보호자는 증상이 나타났을 때 병원 방문이 필요한지, 어떤 진료역량을 갖춘 병원에 가야 하는지 판단하기 어렵다. 근처 예약 가능한 병원을 찾아 방문·진료·결제까지 이어가는 과정도 분절돼 있다. 진료비는 진료 내용에 따라 사후 확정되므로 사전 결제가 성립하지 않고, 예약 후 오지 않는 노쇼가 병원 운영을 방해한다.

풀어야 할 문제:

- 증상만으로는 방문 필요성도, 필요 진료역량도 판단하기 어렵다 → AI가 역량 단위로 구조화해서 검색까지 연결한다.
- 근처에서 조건에 맞는 예약 가능 병원을 찾기 번거롭다 → QueryDSL 조건 검색 + AI 추천이 같은 API를 공유한다.
- 동일 슬롯에 예약이 중복 확정되면 병원 운영이 불가능하다 → 동시성 제어로 막는다.
- 노쇼로 슬롯이 낭비되고 병원이 예약자 신뢰도를 판단할 근거가 없다 → 판정·기록하고 이력을 병원에 제공한다.
- 진료비가 사후 확정되어 사전 결제가 안 된다 → 빌링키 후불 청구로 해결한다.
- 결제 실패 시 대금 회수 경로가 불명확하다 → 원인별 분기 + 오프라인 정산으로 처리한다.
- 예약부터 결제까지 상태가 흩어지면 추적이 안 된다 → 상태를 일관되게 관리한다.

수의사법 제10조·제12조는 수의사가 아닌 자의 진료 행위와 처방을 금지한다. 반려동물 AI 모니터링은 규제샌드박스 실증특례로 일부 허용되지만 재진 모니터링에 한정되고 처방전 발급은 안 된다. 이 서비스의 AI는 "진단"·"처방"을 명시적으로 배제한다. `requiredCapabilities`는 병명이 아니라 검색 필터값이라 이 리스크 영역에 해당하지 않는다.

## 3. 사용자와 요구사항

**보호자**는 반려동물 증상이 있을 때 방문 여부와 병원을 찾는다. 필요한 건: 방문 필요성·필요 진료역량 안내(진단·처방 없음), 조건(지역·역량) 기반 검색과 예약, 관심 병원 찜과 내 찜 목록 관리, 예약 취소(2시간 전까지), 후불 자동 결제와 결과 통지, 결제 완료 진료에 대한 병원 리뷰 작성·조회다. 예약은 요청 후 병원 승인을 거쳐야 확정되며, 승인 전에는 "예약 요청됨"으로만 보인다.

**병원 스태프**는 예약 요청을 검토·승인/거절하고, 체크인·진료 상태를 관리하고, 진료비를 청구한다. 결제가 최종 실패하면 오프라인으로 수납하고 시스템에 기록한다. 그레이스타임 전에도 노쇼를 수동 확정할 수 있고, 자동 판정을 정정할 수도 있다. 병원 기능은 프론트 화면 없이 운영 API로만 제공한다 — 요청 조회/승인/거절/체크인/진료 시작/완료/진료비 입력/오프라인 정산이 전부다.

**스케줄러**는 그레이스타임 경과 건과 병원 미응답 건을 자동으로 정리한다.

회원/인증: 가입은 이메일·휴대폰·비밀번호·닉네임을 모두 필수로 받는다(기능 구멍 점검 대응 — 병원이 예약 확인·노쇼 직전 연락할 수단이 이메일만으로는 없었다). 반려동물 정보는 가입 스키마에서 빼고 PetProfile로 분리해 선택 등록한다. Access Token은 30분~1시간, Refresh Token은 14일이며 서버 측에 저장·회전한다. 폐기된 Refresh Token이 재사용되면 해당 사용자 전체 세션을 로그아웃시킨다. 미인증은 401, 권한 없음은 403.

## 4. 핵심 가치와 차별점

증상을 병명이 아니라 "필요한 진료역량"으로 번역해서 방문 판단을 돕는다. AI 추천과 사용자 직접 검색이 같은 QueryDSL 검색 API를 공유하기 때문에, AI가 내놓은 결과를 그대로 받아도 되고 조건을 조정해 재검색해도 된다. 제휴 병원은 예약 가능, 비제휴 병원도 참고용으로 함께 보여줘서 "우리 동네엔 병원이 없다"는 공백을 없앤다.

거래 쪽에서는 동시성 제어로 슬롯 중복 확정을 막고, 병원이 예약자 이력을 보고 직접 승인/거절하는 실제 운영 구조를 갖는다. 진료비가 사후 확정되는 후불 구조를 빌링키로 처리하되, 실패 원인별로 분기하고 오프라인 정산으로 회수 경로를 남긴다. AI는 진단·처방을 배제하고 disclaimer·응급 라우팅으로 오정보 위험을 방어한다.

프로젝트 관점에서는 QueryDSL 동적 검색, 캐싱, 동시성, AI 안전, 결제 정합성이라는 백엔드 핵심 역량을 하나의 도메인에서 다룬다. 병원은 이력 기반으로 예약을 통제하고, 후불 결제로 현장 수납 부담을 던다.

## 5. 주요 이용 시나리오

### 5-1. 보호자 정상 흐름

```
증상 발생
  → 증상 입력 (프로필 없이 임시 정보로도 가능)
  → AI: 방문 필요성 + 필요 진료역량(requiredCapabilities) 구조화
  → AI: 검색 Tool 직접 호출 → QueryDSL로 제휴 병원 조회
  → AI: 실제 결과 근거로 자연어 안내 + 병원 목록
  → 병원 선택 (또는 검색 화면에서 조건 직접 조정 후 재검색)
  → 반려동물 프로필 + 빌링키 등록
  → 예약 요청(REQUESTED)
  → 병원이 예약자 이력 확인 후 승인 → 확정(CONFIRMED)
  → 병원 방문 → 체크인 → 진료중 → 진료완료
  → 병원이 최종 진료비 입력 → 등록 빌링키로 자동 결제
  → 결제완료 + 결과 알림
```

### 5-2. AI 진료역량 추천 (3단계)

```
"강아지가 어제부터 뒷다리를 절어요. 인천인데 갈 만한 병원 있어?"

1. 구조화 출력   증상 → { requiredCapabilities: ["엑스레이","정형외과 진료"], urgencyLevel: "MODERATE", ... }
2. Tool Calling  searchNearbyVets(requiredCapabilities=[...], region="인천") → QueryDSL 조회
3. 자연어 응답   "엑스레이·정형외과 진료가 가능한 병원이 인천 근처에 3곳 있어요. OO동물병원이 1.2km로 가장 가깝습니다."
```

AI 추천과 사용자 직접 검색은 같은 검색 API를 쓴다.

### 5-3. 응급 신호

증상 입력에 응급 키워드가 있으면 LLM 판단을 우회하고 고정 응답으로 "병원 즉시 방문"을 라우팅한다.

### 5-4. 예약 예외 상황

| 상황 | 처리 |
| --- | --- |
| 프로필 없이 예약 요청 | 요청 거부, 프로필 등록 화면으로 유도 |
| 빌링키 미등록 상태로 예약 요청 | 요청 거부, 카드 등록으로 유도 |
| 예약시각 4시간 이내 임박 슬롯 요청 | 요청 거부 (최소 리드타임 미충족) |
| 동일 슬롯 동시 예약 요청 | 1건만 성립, 나머지는 "다른 이용자가 방금 예약했습니다" |
| 병원이 예약 요청 거절 | REJECTED, 슬롯 반환 + 알림. 후불 구조라 환불 불필요 |
| 승인 데드라인까지 병원 미응답 | 타임아웃 자동 거절. 데드라인 = `min(요청+1시간, 예약시각−2시간)` |
| 비제휴 병원 | 참고용으로만 노출, 예약 버튼 없음 + "제휴 전 병원입니다" 배지 |
| 검색 Tool 호출 실패·타임아웃 | LLM을 재호출하지 않고 서버 고정 안내와 `fallback=true`를 반환해 직접 검색으로 유도 |

### 5-5. 노쇼

예약시간 +10분까지는 일반 그레이스타임으로 체크인을 받는다. +10분을 초과하면 스케줄러가 `NO_SHOW_PENDING`으로 전환하고, 직원은 기본 5분의 추가 유예시간 동안 도착 확인할 수 있다. 보호자 예약 목록·상세에는 이 대기 상태를 그대로 보여주며, +15분을 초과해도 미체크인이면 최종 `NO_SHOW`로 판정하고 이때 보호자에게 알린다. 병원은 예약 시작 시각부터 미방문을 수동으로 NO_SHOW 확정할 수 있으며 수동 판단이 자동 판정보다 우선한다. 병원이 "사실 도착했었다"고 정정하면 CHECKED_IN으로 되돌리고 이력에 남긴다. 노쇼는 기록만 되고, 이후 예약 요청 시 병원에 이력으로 제공된다 — 수수료나 제한은 없다.

### 5-6. 결제 실패 (원인별 분기)

```
진료 완료 → 빌링키 결제 승인 요청 → 실패
  재시도 유효(네트워크·타임아웃·일시 장애)
    → 단건 조회로 실제 처리 여부 확인 → 미처리면 제한 횟수 재시도 → 그래도 실패면 오프라인 전환
  재시도 무의미(카드 한도초과·정지·빌링키 만료)
    → 즉시 OFFLINE_REQUIRED 확정
  → 병원 현장 수납 후 오프라인 정산 기록
  → Payment = OFFLINE_PAID (예약은 진료완료 유지, 전체 결제완료는 예약+결제 조합으로 표현)
  ※ 오프라인 기록 후 자동 재시도 파이프라인 중단 (이중 청구 방지)
```

### 5-7. 병원 정상 흐름

예약 요청 목록 확인 → 예약자 이력 참고해 승인/거절 → 체크인 → 진료 시작·완료 → 진료비 입력해 자동 청구 → (실패 최종 확정 시) 오프라인 수납 후 정산 기록.

## 6. 예약과 결제 운영 정책

### 6-1. 병원 검색·데이터 소스

병원 정보는 동물병원 공공데이터(공공데이터포털·행안부 지방행정인허가데이터)를 쓴다. 확보되는 필드는 병원명·전화번호·주소·좌표·인허가일자·영업상태(영업/휴업/폐업)·휴폐업일자·관리번호·지자체코드 등이고, 영업시간과 진료가능종은 원본에 없다. 실시간 프록시가 아니라 자체 DB에 적재해 쓰고, 검색은 항상 자체 DB를 대상으로 한다. 전국 데이터를 자체 DB에 적재하고 매일 03:00(`Asia/Seoul`)에 갱신한다(SA §9-6).

매칭은 이름 문자열이 아니라 관리번호·지자체코드로 더미 제휴 데이터를 조인한다. 노출은 2계층이다 — 제휴 병원은 영업시간·진료가능종·슬롯을 자체 필드로 보강해 예약 가능, 비제휴 병원은 원본 정보만 참고용으로 노출하고 예약 버튼 없이 배지만 붙는다. 제휴 병원이 충분히 늘면 공공데이터 의존도를 낮추는 방향을 재검토한다.

### 6-2. 검색 — QueryDSL + AI Tool Calling

검색 엔진은 자체 DB 대상 QueryDSL 동적 쿼리다(다중 조건 조합·페이징·정렬). 일반 검색은 영업상태가 `OPEN`인 병원만 노출하며 휴업(`CLOSED_TEMP`)·폐업(`CLOSED`) 병원은 Redis 캐시 HIT/MISS와 관계없이 제외한다. 조건 예: 지역·거리·진료역량·검사·처치·수술/입원/야간/응급 여부·장비·운영시간. AI는 이 검색 API를 Tool로 직접 호출하며 사용자 직접 검색과 API를 공유한다. 축종 필터(`supportedSpecies`)는 MVP부터 실제 필터로 적용한다.

사용자가 병원 검색 화면에 최초 진입하면 아직 검색 조건이 없으므로 서비스 운영 정책에 따라 DoctorPet에서 직접 예약할 수 있는 제휴 병원을 기본 페이지 크기 20의 목록 앞쪽에 우선 노출한다. 제휴 병원이 한 페이지 크기보다 적으면 남은 슬롯은 비제휴 병원으로 채우며, 동일한 기본 목록의 뒤쪽 페이지도 제휴 우선 정렬을 유지한다. 사용자가 페이지 크기를 변경하거나 검색 조건을 적용한 뒤에는 일반 검색 정렬로 제휴·비제휴 병원을 모두 조회하고 제휴 상태와 예약 가능 여부를 명확히 표시한다. 모든 사용자가 공통으로 조회하는 기본 첫 페이지는 반복 조회 가능성이 높으므로 이 범위에 한정해 Redis 캐시를 적용한다.

검색 결과의 마지막 페이지보다 큰 페이지를 요청하면 오류로 처리하지 않고 `200 OK`와 빈 `content`를 반환한다. 이때 요청한 `page`와 실제 `totalElements`·`totalPages`를 유지하고 `last=true`로 응답한다.

#### 병원 찜하기

로그인한 보호자는 제휴 여부와 관계없이 검색되거나 상세 조회되는 병원을 별 모양 버튼으로 찜하고, 찜한 상태에서 같은 버튼을 다시 누르면 해제할 수 있으며, 내 찜 병원 목록을 최신 등록순으로 조회한다. 동일 회원이 동일 병원을 여러 번 찜해도 한 건만 유지하고, 요청의 `memberId`가 아니라 인증 주체를 기준으로 소유권을 판단한다.

병원 검색·상세 응답은 로그인한 보호자에게 `favorite` 여부를 제공한다. 비로그인 사용자에게는 `favorite=false`를 반환한다. 이 값은 회원별 정보이므로 모든 사용자가 공유하는 검색 캐시의 원본에는 포함하지 않고 응답을 만들 때 결합한다. 폐업 병원은 일반 검색과 동일하게 검색 결과에서는 제외하되, 내 찜 목록에서는 폐업 상태를 함께 보여 사용자가 직접 해제할 수 있게 한다.

이번 범위에는 찜 등록·해제·내 목록과 검색·상세의 내 찜 여부만 포함한다. 찜 수 공개, 찜 수 기반 인기 정렬, 알림, AI 추천·랭킹 반영은 후속 고도화로 둔다.

#### 예약 가능 슬롯 조회

병원 예약 화면에 처음 진입하면 프론트는 오늘 날짜로 슬롯을 조회하고, 사용자가 날짜를 바꾸면 같은 API에 선택 날짜를 전달한다. 조회 기준 시간대는 `Asia/Seoul`로 고정하며, 오늘부터 오늘+13일까지를 선택 가능한 14일 범위로 사용한다.

응답에는 14일의 날짜별 `reservationAvailable`과 선택 날짜의 전체 슬롯을 함께 담는다. 해당 날짜에 예약 가능한 슬롯이 하나라도 있으면 날짜를 활성화한다. 선택 날짜 슬롯은 DB 상태가 `OPEN`, `RESERVED`인 슬롯을 모두 노출하고, 프론트가 클릭 가능 여부를 결정할 수 있도록 조회용 상태를 반환한다.

- `AVAILABLE`: DB 상태가 `OPEN`이고 `startAt >= 현재 시각+4시간`
- `RESERVED`: DB 상태가 `RESERVED`
- `LEAD_TIME_CLOSED`: DB 상태가 `OPEN`이지만 `startAt < 현재 시각+4시간`

`RESERVED`와 `LEAD_TIME_CLOSED`는 화면에 표시하되 클릭할 수 없고, 예약 생성 시에는 조회 결과와 관계없이 슬롯 상태와 4시간 리드타임을 다시 검증한다. 과거 또는 오늘+14일 이후의 유효한 날짜는 `200 OK`와 빈 슬롯 목록으로 응답하고, 잘못된 날짜 형식은 `400`으로 처리한다. 비제휴·휴업·폐업 병원은 슬롯과 날짜 활성 목록을 비워 반환하며, 존재하지 않는 병원은 `HOSPITAL_NOT_FOUND`로 처리한다.

#### 병원 진료시간·임시 휴무 관리

병원 스태프는 인증된 자기 병원의 요일별 진료시간과 특정 날짜의 임시 휴무를 관리한다. 하루에는 여러 운영 구간을 둘 수 있고 구간 사이의 공백은 점심시간 등 비운영 시간으로 본다. 정기 휴무일은 운영 구간을 두지 않는다. 종료 시각이 시작 시각보다 이르면 다음 날까지 이어지는 야간 진료로 본다(예: 월요일 `20:00~02:00`은 화요일 02:00 종료). 시작·종료 시각이 같거나 실제 운영 시간이 서로 겹치는 입력은 거부한다.

진료시간 변경의 희망 적용일은 요청일 다음 날 이후여야 한다. 서버는 현재 공개된 `오늘~오늘+13일` 범위의 예약을 확인하고, 예약이 없으면 희망 적용일부터, 예약이 있으면 `희망 적용일`과 `가장 늦은 예약일의 다음 날` 중 더 늦은 날부터 새 진료시간을 적용한다. 적용일 전날까지는 기존 진료시간과 슬롯을 유지하고, 적용일부터 예약 없는 기존 슬롯을 제거한 뒤 새 진료시간으로 다시 생성한다. 기존 예약을 삭제·이동·자동 취소하지 않는다. 일 배치·진료시간 교체·임시 휴무 취소 복구를 포함한 모든 슬롯 생성 경로는 병원 행 잠금 안에서 영업상태가 `OPEN`일 때만 실행한다.

특정 날짜의 임시 휴무는 요청일 다음 날 이후라면 14일 공개 범위 밖의 미래 날짜에도 등록할 수 있다. 임시 휴무는 슬롯의 실제 달력 날짜가 아니라 운영 구간이 시작하는 `영업 기준일`에 적용한다. 따라서 15일이 휴무이고 정기 야간 진료가 `20:00~02:00`이면, 14일 20:00에 시작한 영업은 15일 02:00까지 유지하고 15일 20:00에 시작할 영업은 16일 02:00까지 전체를 운영하지 않는다. 휴무 영업일에 속한 예약 슬롯이 하나라도 예약돼 있으면 등록을 거부한다. 예약이 없고 슬롯이 이미 생성돼 있으면 해당 영업일의 예약 가능한 슬롯을 제거하며, 아직 공개 범위 밖이면 휴무 정보만 저장해 향후 슬롯 생성을 제외한다. 임시 휴무는 휴무일 전날 23:59:59까지 취소할 수 있고 당일부터는 취소할 수 없다. 취소한 영업일이 14일 공개 범위와 겹치면 정기 진료시간에 따라 슬롯을 즉시 복구하고, 범위 밖이면 해당 영업일이 공개 범위에 들어올 때 생성한다. 모든 날짜·시각 판정은 `Asia/Seoul` 기준이다.

예약 슬롯 간격은 모든 병원에 동일하게 30분으로 고정한다. 각 운영 구간 안에서만 30분 단위 슬롯을 만들며, 구간 끝에 남는 시간이 30분보다 짧으면 슬롯을 만들지 않는다. 자정을 넘긴 슬롯은 실제 `startAt`의 달력 날짜에 포함한다.

### 6-3. 예약 상태 전이

```
요청됨(REQUESTED)
   → 승인 → 확정(CONFIRMED) → 체크인(CHECKED_IN) → 진료중(IN_TREATMENT) → 진료완료(TREATMENT_COMPLETED)
   → 거절(REJECTED)   [병원 거절, 또는 승인 데드라인까지 미승인]
   → 취소(CANCELED)   [사용자 취소, 예약시각 2시간 전까지]
CONFIRMED → 취소(CANCELED)   [예약시각 2시간 전까지]
CONFIRMED → 노쇼 대기(NO_SHOW_PENDING) → 노쇼(NO_SHOW) [각각 +10분, 추가 5분 경과 자동 판정]
CONFIRMED/NO_SHOW_PENDING → 체크인(CHECKED_IN) [예약시각 +15분까지 직원 도착 확인]
CONFIRMED/NO_SHOW_PENDING → 노쇼(NO_SHOW) [예약 시작 후 병원 수동 확정]
```

예약은 프로필+빌링키 등록 완료 상태에서, 예약시각 최소 4시간 전까지만 요청할 수 있다. 신규 요청은 병원 행을 잠근 뒤 영업상태가 `OPEN`인지 확인하고, 같은 잠금을 유지한 채 슬롯을 점유하고 `REQUESTED` 예약을 저장한다. 공공데이터 휴·폐업 갱신과 병원 승인은 동일한 병원 행 잠금을 사용하므로 갱신이 먼저 확정되면 신규 요청과 승인은 실패한다. 승인 전에는 "예약 요청됨"으로만 보인다. 승인 데드라인은 `min(요청시각+1시간, 예약시각−2시간)` — 고정 시간만 쓰면 임박 슬롯이 즉시 판단을 강요받고, 슬롯 기준만 쓰면 먼 미래 예약은 병원이 며칠씩 응답을 미룬다. 이른 쪽을 택해 둘 다 막는다. 취소도 예약시각 2시간 전까지 가능하고, REQUESTED·CONFIRMED 두 상태 모두 해당한다. 거절 사유는 정형화한다: 직원 부족 / 슬롯 등록 오류 / 진료 불가 / 기타.

### 6-4. 동시성 (필수 과제)

동일 슬롯 동시 예약 요청은 1건만 성립해야 한다. 조건부 UPDATE / 낙관적 락 / Redis 분산 락 중 택1이며, 단일 슬롯 경합엔 조건부 UPDATE가 가장 단순하다. 실제 비교·선정은 SA에서 다룬다 → **SA §9-3에서 낙관적 락으로 확정했다.** 실패 시 "다른 이용자가 방금 예약했습니다"로 안내하고, 다중 스레드 시나리오로 중복 성립 0건을 검증한다.

### 6-5. 취소

예약시각 2시간 전까지는 REQUESTED·CONFIRMED 모두 자유롭게 취소할 수 있다. 그 이후엔 취소가 거부되고 미도착 시 노쇼 대상이 된다. 병원 사정 취소는 REJECTED로 처리하며 사용자 페널티는 없다.

### 6-6. 노쇼 — 수수료·누적제한 없음, 이력 제공형

일반 그레이스타임은 예약시간 +10분이고 `NO_SHOW_PENDING` 추가 유예는 기본 5분이다. 병원은 예약 시작 시각부터 수동으로 NO_SHOW 확정할 수 있고, 스케줄러(1분 주기)는 +10분 초과 시 대기 상태, +15분 초과 시 최종 NO_SHOW로 판정한다. 직원 도착 확인은 두 대기 상태에서 멱등하게 처리하며 최초 처리 시각과 직원 ID를 남긴다. 병원 수동 판단이 항상 우선이며, 정정 시 CHECKED_IN으로 재전이하고 이력을 남긴다. 공공데이터 휴·폐업 전환에 따른 자동 병원 취소는 슬롯 시작 시각이 현재보다 미래인 `CONFIRMED` 예약에만 적용하며, `startAt == now`와 과거 예약은 체크인·노쇼 흐름에 맡긴다. 수수료도, 누적 제한도 두지 않는다. 대신 예약 요청 시 병원에 예약 이력을 제공해 승인 판단에 쓰며, `cancelCount`는 사용자 취소(`CANCELED`)와 병원 취소(`HOSPITAL_CANCELED`)를 모두 합산한다.

```json
{
  "reservationHistory": {
    "totalReservationCount": 15,
    "completedCount": 11,
    "cancelCount": 1,
    "noShowCount": 3
  }
}
```

수수료를 도입하면 금액 산정·사전 동의·오판정 정정·환불·분쟁 처리 같은 부수 정책이 줄줄이 따라온다. 그 복잡도를 병원 승인 판단으로 대체한다. 이력 집계는 특정 병원이 아니라 전 병원 통합이다 — 병원이 "이 사용자가 다른 병원 포함해서 얼마나 노쇼하는가"를 판단할 수 있어야 하기 때문이다. 자동 차단은 하지 않는다.

### 6-7. 결제 (PortOne 빌링키 — 후불형)

예약 요청/확정 시점엔 빌링키만 등록한다(승인·capture 없음). 진료 완료 후 병원 스태프가 청구 항목을 확정하면 서버가 항목 합계로 최종 진료비를 산출해 등록된 빌링키로 결제를 승인 요청한다. 클라이언트가 총액을 입력하거나 결정하지 않으며, 서버가 산출한 청구 금액만 0 초과 & 서비스 절대 상한 이하인지 검증한다(상한값은 SA 참조).

결제 상태는 `PENDING`(청구 시작) → `PAID`(승인 성공) / `OFFLINE_REQUIRED`(자동 결제 불가) → `OFFLINE_PAID`(현장 수납 완료)로 흐른다. 승인 요청 후 응답이 유실되면 별도 상태 없이 `PENDING`에 머문다 — 이미 승인됐을 수 있어 무조건 재시도는 이중 청구 위험이다. 정산 스케줄러가 일정 시간 후 PortOne 단건 조회로 `PAID` 또는 `OFFLINE_REQUIRED`를 확정한다.

실패 원인은 둘로 나뉜다. 네트워크 오류·타임아웃·일시 장애 같은 재시도 유효 건은 단건 조회 후 제한 횟수만큼 재시도하고, 그래도 실패면 `OFFLINE_REQUIRED`로 넘긴다. 카드 한도초과·정지·빌링키 만료처럼 재시도가 무의미한 건은 즉시 `OFFLINE_REQUIRED`로 확정한다. 최종 실패가 예약·진료 기록을 되돌리지 않는다 — 진료완료 상태는 유지되고 병원 화면에 미수금으로 뜬다. 회수는 서비스가 자동 보장하지 않고 병원이 오프라인으로 처리하는 게 원칙이다.

오프라인 정산은 `PATCH /api/hospital/payments/{paymentId}/offline-settle`로 처리한다. 전제조건은 `Payment.status == OFFLINE_REQUIRED`이며, 처리 후 `OFFLINE_PAID`로 바뀌고 `paymentChannel = OFFLINE`(자동결제는 `BILLING_KEY`)로 구분 기록된다. 이 이후엔 자동 재시도 파이프라인을 반드시 중단시켜야 이중 청구가 안 난다.

환불은 MVP 범위 밖이었다. 후불 구조라 취소·거절·노쇼 시점엔 애초에 청구가 없어 환불이 필요 없고, 유일한 케이스가 진료 후 오청구뿐이기 때문이다. MVP+ 고도화에서 그 오청구 케이스를 **전액 환불**로 도입했다(이슈 #37). `POST /api/hospital/payments/{paymentId}/refund`, 전제조건은 `Payment.status == PAID && paymentChannel == BILLING_KEY`이며 처리 후 `REFUNDED`로 바뀐다. 요청은 사유만 받는다 — 금액을 받으면 과·소 환불이 가능해지므로 결제 레코드의 금액을 그대로 취소한다. 환불 이력(사유·처리 스태프·PG 취소 식별자)은 별도 테이블에 남겨 돈을 되돌린 근거를 추적할 수 있게 한다.

현장 현금 수납(`OFFLINE_PAID`)의 환불은 아직 범위 밖이다 — 현금 반환 절차·승인자·증빙 정책이 정해지지 않았고, 정책 없이 기록만 남기면 실제 반환 여부를 시스템이 보증하지 못한다. 부분 환불도 확장으로 유지한다. 정정 재청구는 아래에서 확정 정책으로 도입한다.

#### 청구 항목과 할인·조정

병원 스태프는 진료를 완료한 뒤 청구 항목(명칭·수량·단가)을 작성·수정한다. 작성·수정은 청구를 시작하기 전까지만 가능하고, 청구를 시작한 뒤에는 항목을 수정하지 않는다. 항목은 청구 시점의 스냅샷이며, 이미 시작된 결제의 금액을 바로잡을 때는 항목을 고치지 않고 아래 정정 재청구 절차만 쓴다. 이 금지는 단순한 데이터 정합성 장치가 아니라, 환불·재청구 이력을 남기는 정정 재청구를 우회해 금액을 조용히 바꾸지 못하게 하는 경계다.

"청구를 시작한 뒤에는 수정하지 않는다"는 안내가 아니라 시스템이 막는 규칙이다. 청구와 항목 수정이 동시에 들어오면 한쪽만 성립하며, 청구가 먼저 성립하면 이후 수정 요청은 거부된다. 총 청구 금액은 병원이 보낸 총액이 아니라 서버가 항목 합계로 계산한 값이다(설계는 SA §9-4).

할인·상계 같은 조정은 별도 할인 필드를 두지 않고 음수 금액 항목으로 기록한다. 수량은 항상 양수이고 단가와 항목 금액만 음수를 허용한다. 총 청구 금액은 항목 금액의 합계와 일치해야 하며, 합계는 0보다 크고 기존 절대 상한 이하여야 한다. 항목화 도입 이전에 청구된 결제에는 항목이 없으며, 총액만으로 항목을 만들어 채우지 않는다. 세율·부가세 분리와 진료 항목 마스터 코드 표준화는 범위 밖이다.

#### 결제수단 기본값과 예약 결제수단 재지정

보호자는 등록한 결제수단 하나를 기본값으로 지정할 수 있고, 활성 기본 결제수단은 회원당 최대 한 건이다. 또 진료 전에는 예약에 걸린 결제수단을 본인의 다른 활성 결제수단으로 바꿀 수 있다 — 카드를 교체하면 예약에 고정된 옛 카드가 삭제돼 진료 후 청구가 전부 실패하던 문제를 막는다. 재지정은 결제가 아직 시작되지 않았고 진료도 시작되지 않은 예약에만 허용한다.

#### 결제 실패 셀프 복구

자동 결제가 최종 실패해 현장 수납을 기다리는 상태(`OFFLINE_REQUIRED`)에서는 보호자가 직접 다른 활성 결제수단을 지정한 뒤 재청구를 요청할 수 있다. 요청 없이 서버가 임의로 다시 청구하지는 않는다.

셀프 재청구는 원 결제를 대체하는 새 결제로 남기고 원 결제를 가리키는 복구 체인을 기록한다. 원 결제에 청구 항목이 있으면 그 항목과 총액을 원자적으로 그대로 복제해 같은 금액만 재청구하며, 보호자는 항목·총액을 바꿀 수 없다. 항목화 이전 결제처럼 원 항목이 없으면 실제 내역을 꾸며내지 않고 총액만 승계한다.

보호자의 재청구와 병원의 현장 수납이 겹치면 **먼저 처리된 쪽만 성립한다.** 병원이 먼저 현장에서 받았으면 이후 보호자 재청구는 거부되고, 보호자 재청구가 먼저 시작됐으면 그 건의 현장 수납은 거부된다. 같은 진료비를 자동결제와 현장 수납으로 두 번 받는 일이 없어야 하기 때문이다(설계는 SA §9-4).

결과가 확정되지 않은 상태(`PENDING`)에서는 어떤 셀프 재청구도 허용하지 않는다. 이미 승인됐을 수 있어 다시 청구하면 이중 결제가 되므로, 정산 스케줄러가 단건 조회로 결과를 확정할 때까지 기다린다. 금액 불일치·PG 응답 이상처럼 자동으로 확정하지 않는 `PENDING`은 지금도 운영자 확인 대상이며, 이번 범위에서 자동 복구 정책을 새로 만들지 않는다.

#### 영수증

`PAID`·`OFFLINE_PAID`·`REFUNDED` 결제에 구조화 JSON 영수증을 제공한다. 보호자는 본인 예약의 결제만, 병원 스태프는 자기 병원의 결제만 조회할 수 있다. 영수증에는 결제 항목·총액·결제 일시·카드 브랜드/뒷 4자리처럼 결제 시점에 고정된 값과 병원·보호자의 안정 식별자, `pet_id` 및 예약 시점의 반려동물 이름·종 스냅샷을 담는다. 변경 가능한 병원명·회원명·연락처는 영수증에 넣지 않으므로 프로필 변경 뒤에도 과거 영수증 내용이 바뀌지 않는다. 항목화 도입 이전에 청구된 결제는 항목 없이 총액만 제공한다 — 실제로 입력되지 않은 내역을 증빙에 만들어 넣지 않으며, 그 결제도 실제 수납된 건이므로 발급 자체를 막지는 않는다. 환불된 결제의 영수증에는 환불 상태와 환불 일시를 함께 담고, 환불 사유는 감사용이므로 보호자 알림·보호자 응답에 노출하지 않는다(기존 결정 승계). PDF·전자문서, 세금계산서, 현금영수증 국세청 연동, 진료확인서는 범위 밖이다.

#### 정정 재청구

오청구 금액을 바로잡는 방법은 하나로 고정한다 — 기존 결제를 전액 환불하고 올바른 금액으로 새 결제를 만든다. 새 결제는 자신이 무엇을 정정한 것인지 이전 결제를 가리켜 남기고, 한 예약에는 활성 결제가 항상 한 건만 존재한다. 환불·대체된 과거 결제는 지우지 않고 이력으로 남겨 "얼마를 왜 되돌리고 얼마로 다시 청구했는지"를 추적할 수 있게 한다.

이에 따라 "환불한 예약은 다시 청구할 수 없다"는 기존 제약을 정책으로 해제한다. 다만 예약당 결제를 1건으로 강제하는 현재 제약을 활성 결제 기준으로 바꾸는 작업이 끝나기 전까지는 실제 재청구가 동작하지 않는다(설계는 SA §9-4).

정정은 전액 환불을 반드시 거치므로, **환불 시 리뷰를 삭제하는 기존 정책이 그대로 적용된다** — 정정하면 그 예약에 남아 있던 보호자 리뷰가 삭제되고, 새 결제가 완료되면 리뷰를 다시 쓸 수 있게 되지만 이전 리뷰 본문은 복구되지 않는다.

부분 환불은 정정 재청구와 별개 계약이며 아직 미확정·범위 밖이고, 현장 현금 수납분의 환불도 계속 범위 밖이다.

### 6-8. 병원 리뷰

리뷰 작성 자격은 결제 완료 여부로 확인하되 작성 단위는 예약이다. 로그인한 보호자가 본인의 예약에 대해 현재 `PAID` 또는 `OFFLINE_PAID` 결제를 보유한 경우에만 작성할 수 있고, 예약 1건당 최초 1회만 허용한다. 정정 재청구로 예약과 결제가 1:N이 되어도 리뷰 작성 기회는 늘어나지 않는다.

평점은 1.0~5.0 범위의 0.5 단위다. 작성자는 기간 제한 없이 내용과 평점을 모두 수정할 수 있으며, 수정된 평점은 병원 평균에 즉시 반영한다. 삭제는 Hard Delete다. 사용자가 직접 삭제하면 작성 이력은 유지해 같은 예약으로 다시 작성할 수 없다.

`REFUNDED`는 유효한 결제 완료 상태가 아니므로 리뷰 작성 자격이 없다. 빌링키 결제가 환불되면 기존 리뷰를 Hard Delete하고 예약의 작성 이력을 초기화한다. 정정 재청구로 같은 예약에 다시 유효한 결제가 생기면 리뷰 작성 자격도 복구된다. 정정 재청구는 §6-7에서 확정한 정책이며 구현은 후속이다.

병원 상세에는 실제 존재하는 리뷰의 평균 평점과 리뷰 수를 제공한다. 리뷰가 없으면 평균 평점은 `null`, 리뷰 수는 `0`이다. 신고·숨김·관리자 검수, AI 추천 반영, 리뷰 기반 검색 랭킹은 이번 범위에서 제외한다.

제휴 병원 상세에는 최근 90일의 완료된 예약 응답을 기준으로 예약 응답률과 평균 승인 시간을 제공한다. 응답률은 승인·병원 직접 거절을 응답으로 보고 자동 만료를 미응답으로 보며, 응답 전 보호자 취소와 아직 처리되지 않은 요청은 제외한다. 응답 표본과 승인 표본이 각각 10건 미만이면 해당 지표를 노출하지 않는다. 표본 수는 공개하지 않으며 검색 정렬·AI 추천에는 반영하지 않는다.

클라이언트가 보낸 결제 결과는 신뢰하지 않고 서버가 PortOne 단건 조회로 금액·상태를 검증한다. 빌링키는 암호화 저장하고 카드 원본은 저장하지 않는다.

## 7. AI 진료역량 추천·안전 정책

AI는 병명이나 진료과를 판단하지 않는다. 증상을 "이 병원이 갖추면 좋은 진료 역량" 단위로 구조화하고, 그 값으로 검색 Tool을 호출한다. 최종 선택과 조건 조정은 사용자가 검색 화면에서 직접 한다.

```json
{
  "possibleFocusAreas": ["소화기", "피부"],
  "requiredCapabilities": ["엑스레이", "정형외과 진료"],
  "urgencyLevel": "MODERATE",
  "preVisitCheckpoints": ["최근 식이 변화 여부", "구토·설사 지속 시간"],
  "recommendVetVisit": true
}
```

의심 질환명이나 처치 지침은 스키마에 없다. `requiredCapabilities`는 진단이 아니라 검색 필터값이다. `disclaimer`는 이 스키마에 두지 않는다 — LLM이 누락할 수 있으므로 서버가 응답을 조립하는 마지막 단계에서 고정 문구를 항상 주입한다.

`possibleFocusAreas`와 `preVisitCheckpoints`도 자유 문자열을 허용하지 않는다. 모델은 각각 증상 관찰 범위와 보호자 관찰 항목의 허용 enum만 반환하고, 서버가 검증한 뒤 안전한 한국어 문구로 변환한다. 최종 `message`는 모델이 생성하지 않고 실제 병원 검색 결과와 위치·응급 상태를 바탕으로 서버가 조립한다.

연동은 3단계다. 증상을 스키마로 구조화하고(구조화 출력), `requiredCapabilities`와 위치를 인자로 검색 API를 Tool로 직접 호출하고(Tool Calling), 조회된 실제 DB 결과만 근거로 자연어 응답을 만든다(그라운딩·없는 데이터 생성 차단).

환각·오정보 방어: disclaimer는 서버가 항상 주입한다. 응급 키워드가 감지되면 LLM 호출을 생략하고 "병원 즉시 방문" 고정 응답으로 라우팅한다. 키워드에 걸리지 않아 LLM을 호출했더라도 `urgencyLevel: HIGH`이면 처치성 문구를 차단하고 즉시 병원 방문·연결 안내로 강제 분기한다. 화이트리스트 카테고리 밖은 "정확한 답변이 어렵습니다"로 답한다. 질환명 추정·약물·처치 지시는 생성 자체를 차단한다. 검색 Tool 호출 실패·타임아웃 때는 LLM을 재호출하지 않고 서버 고정 안내와 `fallback=true`를 반환해 사용자가 QueryDSL 검색에서 직접 조건을 고르도록 유도한다. 이 장애는 예약·결제 등 다른 기능으로 전파하지 않는다.

초기 공통 기능은 제공자에 종속되지 않는 `AiGateway`와 실제 LLM을 호출하지 않는 `FakeAiGateway`로 구현한다. 실제 LLM 제공자는 OpenAI, 모델은 Structured Outputs를 지원하는 `gpt-4.1-mini`로 사용한다. Fake 단계의 Gateway 추상화는 유지하되, 실제 Tool Calling 연동 시 `AiGateway` 계약과 상담 오케스트레이션을 함께 확장한다.

실제 OpenAI 연동부터는 `searchNearbyVets`만 허용하는 제한적 Tool Calling을 적용한다. 모델은 증상 구조화와 검색 필요 여부·검색 조건 선택을 담당하고, 서버는 허용 Tool 목록·호출 횟수·인자 스키마를 검증한 뒤 기존 QueryDSL 병원 검색을 실행한다. 응급 키워드 우회, disclaimer, 좌표·축종 주입, 현재 영업 판정, 검색 실패 fallback은 모델이 아니라 서버가 최종 책임진다.

검색에 위치가 필요하지만 좌표와 지역이 없으면 모델은 위치 필요 신호를 반환할 수 있다. 다만 모델이나 서버가 기기 위치를 직접 조회하지는 않는다. 프론트가 사용자에게 위치 제공 동의를 요청하고, 동의해 얻은 좌표만 후속 상담 요청에 포함한다. 거부·실패·응답 지연은 응급 안내를 막지 않는다.

예약 Tool은 1차 검색 Tool 범위에 포함하지 않고 2차 확장으로 분리한다. 도입 시에도 사용자가 예약 의사를 명시적으로 확인한 경우에만 호출하며, AI는 인증 주체와 사용자가 선택한 병원·슬롯·반려동물 정보를 기존 예약 애플리케이션 서비스에 전달하는 역할만 맡는다. 예약 가능 여부·소유권·슬롯 동시성·예약 생성·상태 전이는 예약 도메인이 검증하고, 결제와 결제 상태 전이는 AI Tool 범위에서 제외한다.

`FakeAiGateway` 단계에는 사용하지 않는 프롬프트 파일을 만들지 않는다. 실제 LLM 평가·연동 시 `src/main/resources/prompts` 아래에 종별 프롬프트를 두고 파일명 또는 설정값으로 버전을 구분한다. 별도 버전 매니페스트는 MVP에서 제외하며 실제 호출에 사용한 버전은 `ai_consultations.prompt_version`에 기록한다.

AI 상담 입력은 `symptomText`와 `species`가 모두 필수이며 `region`, `latitude`, `longitude`는 선택이다. `symptomText`는 공백만 입력할 수 없고 1자 이상 1,000자 이하이며, `species`는 축종 화이트리스트의 `DOG`, `CAT`, `BIRD`, `RABBIT`, `HAMSTER`, `GUINEA_PIG`, `FERRET`, `REPTILE`만 허용한다. 위치 권한 요청과 좌표 조회는 프론트가 담당하고 사용자가 동의한 경우에만 위도·경도를 서버로 전달한다. 위도·경도는 병원 검색에만 사용하며 AI가 추측하거나 생성해서는 안 된다.

MVP에서 AI가 증상 문장으로부터 만들 수 있는 병원 검색 조건은 축종, `requiredCapabilities`, 응급 여부, 야간 진료 의도, 현재 영업 의도, 거리순 의도로 제한한다. “지금”, “현재”, “바로”, “문 연”, “지금 진료 가능한”은 현재 영업 의도로, “야간 진료”, “밤늦게”, “새벽에도”, “24시간”은 야간 진료 의도로 해석한다. 다만 “새벽인데 지금 진료 가능한”처럼 현재 방문 가능 여부를 묻는 문장은 현재 영업 조건을 우선 적용하며, 사용자가 현재 영업과 야간 진료를 모두 명시한 경우에만 두 조건을 함께 적용한다. 실제 현재 시각과 영업 여부는 서버가 `Asia/Seoul` 기준으로 판정한다.

“가까운”, “가장 가까운”, “근처”, “주변”은 유효한 사용자 좌표가 있을 때만 거리순으로 검색한다. 좌표가 없고 지역이 있으면 지역 검색 결과를 제공하되 거리순이라고 표현하지 않는다. 좌표와 지역이 모두 없으면 서버 고정 안내로 위치 제공 또는 직접 검색을 유도하며 병원 위치를 추측하지 않는다.

응급 키워드 또는 `urgencyLevel=HIGH`인 경우에는 즉시 방문 안내와 함께 `emergency=true`, `openNow=true`로 실제 병원을 조회한다. 이때 유효한 사용자 좌표가 있으면 사용자가 거리 표현을 하지 않았더라도 `sort=distance`를 자동 적용한다. 좌표가 없으면 거리순을 적용하지 않으며, 응급 안내와 현재 확보한 지역 정보 기반 검색을 중단하지 않고 위치 제공을 권장한다. 지역과 좌표가 모두 없더라도 전국 이름순 결과를 응급 추천으로 제공하지 않으며, 응급 안내와 위치 제공 또는 직접 검색 안내를 반환한다. 위치 제공은 선택 사항이고 거부·실패·응답 지연이 응급 안내를 막아서는 안 된다.

Rate Limit은 로그인 사용자는 `memberId`당 1분 5회, 비로그인 사용자는 IP당 1분 3회와 하루 30회를 적용한다. 횟수와 제한 시간은 설정값으로 관리하며 비로그인 일일 구간은 `Asia/Seoul` 날짜를 기준으로 한다. 로그인 요청에는 IP 제한을 중복 적용하지 않는다.

운영 MVP에는 모델·프롬프트 버전·토큰·지연·오류 지표 저장, 개인정보 패턴을 마스킹한 증상 텍스트의 상담 처리·외부 AI Gateway 전달과 30일 보존·삭제 배치, timeout·fallback, 기본 Circuit Breaker를 포함한다. 요청 검증 후에는 응급 키워드·검색 의도 판정, 외부 제공자 전달, DB 저장까지 모두 마스킹된 텍스트만 사용한다. 세밀한 임계값 튜닝·운영 대시보드·고도화된 모니터링은 확장 범위다.

수의사법 제10조·제12조는 무면허 진료·처방을 금지하고, 규제샌드박스 실증특례는 재진 모니터링에 한정된다. `requiredCapabilities` 추천은 진단이 아니라 검색 필터이므로 이 리스크 영역 밖이다.

## 10. 용어 정의

| 용어 | 정의 |
| --- | --- |
| requiredCapabilities | AI가 증상에서 도출하는 필요 진료역량 키워드. 진단 아님, 검색 필터값 |
| 제휴 병원 / 비제휴 병원 | 제휴 — 더미 상세정보 보강, 예약 가능 / 비제휴 — 원본만 참고용, 예약 불가 |
| QueryDSL 동적 검색 | 자체 DB 대상 다중 조건 조합 검색. AI Tool과 사용자 검색이 공유 |
| 예약 요청(REQUESTED) | 프로필·빌링키를 갖춘 사용자가 예약을 요청한 상태. 병원 승인 전 |
| 확정(CONFIRMED) / 거절(REJECTED) | 병원이 예약 요청을 승인/거절한 상태 |
| 빌링키(BillingKey) | 카드 인증 후 발급되는 재사용 가능한 청구용 식별자. 카드 원본 미포함 |
| 후불 결제 | 진료비 확정 후 등록된 빌링키로 청구하는 방식 |
| 체크인 | 병원이 반려동물의 실제 도착을 기록하는 행위 |
| 그레이스타임 | 예약시간 +10분까지 지각을 허용하는 유예 구간 |
| 노쇼(No-show) | 체크인 없이 그레이스타임이 경과한 상태. 수수료 없이 병원 이력으로 제공 |
| reservationHistory | 예약 요청 시 병원에 제공되는 예약자 이력. 전 병원 통합 집계 |
| 오프라인 정산 | 결제 실패 후 병원이 현장 수납한 사실을 시스템에 기록하는 처리 |
| PetProfile | 반려동물 프로필. 예약 요청의 필수 조건 |
