## 1. 범위

- 프론트엔드는 **보호자(GUARDIAN) 웹 SPA 하나만** 구현한다.
- 병원 스태프 기능(예약 승인·체크인·진료 완료·진료비 청구·오프라인 정산)은 **프론트 화면 없이 운영 API로만** 제공한다(PRD §30·§59). 따라서 프론트 대상이 아니다.
- 대상 화면: 인증(로그인), AI 상담, 병원 검색·상세, 펫 프로필 관리, 결제수단 관리, 예약 요청·취소, 예약·결제 내역.
- **병원 스태프 웹 화면과 환불 화면은 MVP 범위 밖**이며 MVP 이후 확장으로 다룬다(§6 참고).
- 디자인 방향(참고): 밝은 배경 + teal/green 포인트, 카드 기반 레이아웃, 예약·결제 상태 머신과 매칭되는 상태 배지. 와이어프레임은 "느낌" 참고용이며 픽셀 단위로 동일하게 맞추지 않는다.

## 2. 확정 스택

## 3. 스타일링 결정 — Tailwind CSS + shadcn/ui (A안)

- 현업 주류이며 커스텀 자유도가 높아 디자인을 직접 다듬기 좋다.
- shadcn/ui로 접근성 갖춘 기본 컴포넌트를 빠르게 확보하되, 코드를 프로젝트에 복사해 소유하므로 종속성이 얕다.
- (대안이었던 MUI/Ant Design은 기성 컴포넌트로 데모 속도를 높이는 선택지였으나, 완성도·트렌드를 우선해 A안을 채택.)

## 4. 백엔드 연동 전제

- **CORS**: 현재 `SecurityConfig`에 `.cors(...)` 설정이 없어 다른 오리진의 프론트는 브라우저에서 차단된다. 프론트 실연동 전에 CORS 허용 설정을 추가해야 한다.
- **API 문서(선택·권장)**: `springdoc(OpenAPI)`를 도입하면 이 계약으로 프론트 TS 타입을 자동 생성(`openapi-typescript`)할 수 있어 병렬 작업이 매끄러워진다. 미도입이어도 SA §8 계약 기준으로 수기 타입을 둔다.

## 5. 실시간(push)은 MVP 제외 — 향후 확장 전략

- MVP 알림은 **폴링**이다(SA §9-8). 따라서 **STOMP/SockJS·SSE는 지금 도입하지 않는다.**
- 다만 **나중에 추가하기 쉽도록** 아래를 지킨다.
  - 알림 조회를 `useNotifications` 훅(또는 서비스) 하나 **뒤로 캡슐화**한다. 폴링이든 push든 화면은 이 인터페이스만 바라보게 해, 전환 시 변경 범위를 이 한 곳으로 국한한다.
  - 백엔드는 `NotificationPusher` 인터페이스로 추상화돼 있고, MVP2에서 **단방향 SSE로 확정·구현**됐다(티켓 인증 구독, 이벤트명 `notification`, SA §9-8·§8-8). 양방향 WebSocket+STOMP는 채팅 도입 시에만 재논의한다.
- **결론(추가 난이도)**: 추가는 어렵지 않다. 의존성(예: `@stomp/stompjs`+`sockjs-client` 또는 브라우저 내장 `EventSource`)을 얹고 알림 훅 구현체만 교체하면 되며, 기존 REST 코드는 손대지 않는다.
- **다만 유의**: 실제 채택할 방식은 아직 미정이다.
  - **단방향 알림(예약·결제 상태 변화)** 이면 **SSE**가 더 단순하다. 단 `EventSource`는 커스텀 헤더를 못 실어 단기 발급 티켓 등 별도 인증이 필요하다(SA §9-8).
  - **양방향(수의사·보호자 1:1 채팅)** 이 실제로 필요해지면 **WebSocket+STOMP**를 검토하며, 이때 STOMP CONNECT 시점에 JWT 검증(ChannelInterceptor)이 필요하다(SA §9-8).
  - 즉 "STOMP를 다시 붙인다"가 아니라, **요구사항에 따라 SSE 또는 STOMP 중에서 그때 고른다**. 지금은 폴링을 캡슐화해 두는 것으로 충분하다.

## 6. 향후 확장 (MVP 이후)

MVP 범위 밖이며, 아래 항목은 MVP 완료 후 별도로 다룬다.

- **병원 스태프 운영 웹**: 로그인·대시보드·예약 승인/거절·진료 상태 전이·진료비 청구·오프라인 정산 화면. 현재 병원 기능은 프론트 화면 없이 운영 API로만 제공한다(PRD §30·§59). 선행으로 백엔드 #27(병원 예약 운영 API) 등이 필요하다.
- **환불 화면**: 환불이 MVP 제외이므로(SA §4·§9-4) 관련 화면(REFUNDED 등)도 함께 보류한다.
- **실시간 push**: §5 참고.

## 7. 저장소·배포 및 팀 확인

- **저장소: 모노레포 `frontend/` 채택.** 최종적으로 백엔드 저장소 안 `frontend/` 폴더에 둔다(Agora와 동일 방식).
- **초기에는 로컬 전용으로 작업한다.** 백엔드가 아직 개발 중이고 팀원과 섞이지 않도록, 준비되기 전까지 `frontend/`를 커밋·푸시하지 않는다. 로컬 제외는 `.git/info/exclude`로 처리하며 공유 `.gitignore`는 건드리지 않는다. 안정화되면 exclude를 풀고 커밋해 모노레포에 합류한다.
- 배포 방식은 별도 결정한다. 백엔드 CI(gradle)가 프론트 변경에 도는 낭비는 추후 GitHub Actions `paths:` 필터로 회피한다.
- CORS·springdoc 도입 여부는 백엔드 작업으로 연결된다(§4).
- 위 스택은 결정안이나, 팀 최종 합의 후 이 문서 상태를 유지·갱신한다.
